## 1. 为什么需要 AI 编译器

### 1.1 手写 Kernel 的组合爆炸

一个深度学习框架的算子库要覆盖的维度是相乘关系：

$$
\text{Kernel 数量} \approx \underbrace{N_{\text{op}}}_{\text{算子}} \times \underbrace{N_{\text{dtype}}}_{\text{FP32/FP16/BF16/FP8/INT8}} \times \underbrace{N_{\text{layout}}}_{\text{连续/转置/NHWC}} \times \underbrace{N_{\text{arch}}}_{\text{V100/A100/H100/AMD}} \times \underbrace{N_{\text{fusion}}}_{\text{融合组合}}
$$

前四项已经让 PyTorch 的 ATen 库积累了数千个 kernel，而最后一项 $N_{\text{fusion}}$ 才是真正的灾难：`add + relu`、`add + gelu`、`mul + add + layernorm`……融合组合随算子链长度指数增长，不可能为每种组合预写 kernel。cuDNN/cuBLAS 只覆盖了最常见的几种（如 conv+bias+relu），长尾组合要么退化为逐算子执行，要么等人手写——AI 编译器的第一使命就是**按需生成长尾融合 kernel**。

### 1.2 融合收益的本质：减少 HBM 往返

回顾第 5 章的结论：elementwise 算子是典型的 Memory-Bound 运算。以 FP32 的 `y = relu(a + b)` 为例，逐算子执行时：

```
add:  读 a(4N B) + 读 b(4N B) + 写 tmp(4N B)   = 12N Bytes
relu: 读 tmp(4N B) + 写 y(4N B)                =  8N Bytes
合计 HBM 流量：20N Bytes，2 次 kernel launch
```

融合成一个 kernel 后，中间结果 `tmp` 全程留在寄存器中：

```
fused: 读 a + 读 b + 写 y = 12N Bytes，1 次 kernel launch
```

推广到 $n$ 个单输入 elementwise 算子的链：融合前 HBM 流量为 $2n \cdot S$（每个算子一读一写，$S$ 为张量字节数），融合后仅 $2S$，**流量降为 $1/n$**。由于这类 kernel 的耗时几乎与 HBM 流量成正比，融合收益接近 $n$ 倍。这与 FlashAttention 减少 HBM 访问的逻辑一脉相承——**AI 编译器优化的主战场不是减少计算，而是减少数据搬运**。

### 1.3 三个层次的自动化

| 层次 | 优化内容 | 代表工具 |
|------|----------|----------|
| 图层（Graph-level） | 算子融合决策、常量折叠、死代码消除、layout 变换 | TorchInductor 调度器、XLA HLO、TVM Relax |
| Kernel 层（Tile-level） | 分块大小、共享内存分配、访存合并、软件流水线 | Triton、TVM TensorIR、Inductor codegen |
| 运行时层（Runtime） | Launch 开销消除、显存规划、流并发 | CUDA Graph、内存池 |

torch.compile 的价值在于把三层打通成一条自动化流水线，下面逐层拆解。

## 2. torch.compile 全链路

### 2.1 整体架构

```
Python 代码
    │
    ▼  TorchDynamo（字节码级图捕获）
FX Graph（torch 算子级）+ Guards
    │
    ▼  AOTAutograd（前反向联合追踪 + 分解）
前向/反向 ATen 原语图（functionalized）
    │
    ▼  TorchInductor（调度、融合、代码生成）
GPU: Triton kernel   /   CPU: C++/OpenMP
    │
    ▼  （mode="reduce-overhead"）
CUDA Graph 包装，整图回放
```

### 2.2 TorchDynamo：字节码捕获与 Graph Break

TorchDynamo 利用 CPython 的 Frame Evaluation API（PEP 523）拦截 Python 函数的字节码，在**字节码层面**做符号执行：遇到张量操作就记录进 FX Graph，遇到普通 Python 逻辑（int 运算、数据结构操作）就直接常量化或保留在 Python 侧。这带来两个关键机制：

**Guards（守卫）**：捕获的图只对特定前提成立（输入 dtype、shape、全局变量的值等）。Dynamo 为每个前提生成检查条件，下次调用时先跑 guard——全部通过则直接复用编译产物，任何一条失败则触发**重新编译（recompile）**。这就是 torch.compile 既能享受静态图优化、又保持动态图语义的原因：它编译的是"当前这种情况下的静态图"，而不是强行把整个程序静态化。

**Graph Break（图中断）**：遇到无法安全追踪的代码时，Dynamo 不报错，而是把函数切成多段子图，中断处回退到 eager 执行：

```python
import torch
import torch._dynamo as dynamo

def f(x, y):
    z = x + y
    if z.sum() > 0:        # 分支条件依赖张量的值 → graph break
        return z.relu()
    return z.sigmoid()

print(dynamo.explain(f)(torch.randn(8), torch.randn(8)))
# Graph Count: 2, Graph Break Count: 1
# Break Reason: data-dependent branching ...
```

常见的 graph break 来源与对策：

| 触发原因 | 例子 | 对策 |
|----------|------|------|
| 数据依赖的控制流 | `if x.sum() > 0:` | 改用 `torch.where` / `torch.cond` |
| 取标量到 Python 侧 | `x.item()`、`x.tolist()` | 保持张量运算；或开 `capture_scalar_outputs` |
| 副作用/不可追踪调用 | `print()`、日志、numpy 调用 | 移出热路径 |
| 调用 C 扩展/未支持库 | 自定义 pybind 函数 | 注册为 custom op |

每个 graph break 都意味着一次"编译区间断裂"：子图之间无法跨界融合，还要付出图切换开销。诊断手段：

```bash
TORCH_LOGS="graph_breaks" python train.py     # 打印每个 break 的位置与原因
```

对性能敏感的路径应使用 `torch.compile(f, fullgraph=True)`——有 break 直接报错，强迫你修掉。动态 shape 场景用 `dynamic=True` 或 `torch._dynamo.mark_dynamic(x, dim)`，让 Dynamo 以符号维度（SymInt）编译，避免每个 shape 重编一次。

### 2.3 AOTAutograd：提前追踪反向图

Dynamo 捕获的是前向的 torch 级算子图，而训练还需要反向。AOTAutograd（Ahead-Of-Time Autograd）在编译期就把前向图送入 autograd 机制**联合追踪出前向 + 反向图**，再做三件事：

1. **分解（Decomposition）**：把复合算子拆成少量 ATen/Prims 原语（如 `softmax` 拆成 `exp/sum/div`），让后端只需处理小算子集合，也给融合创造原料；
2. **函数化（Functionalization）**：消除 inplace 操作和 view 别名，把图变成纯函数式——融合和重排的前提；
3. **前反向切分**：用 min-cut 算法决定哪些中间值保存给反向、哪些反向时重算（与 FlashAttention 的重计算思想相同：省 HBM 流量优先于省 FLOPs）。

### 2.4 TorchInductor：生成 Triton Kernel

Inductor 是默认后端，把 ATen 图 lower 到自己的 define-by-run 循环级 IR，完成调度决策（融合分组、分块、reduction 策略），最终为 GPU 生成 **Triton** 源码、为 CPU 生成 C++/OpenMP。查看真实产物：

```bash
TORCH_LOGS="output_code" python model.py
```

对 `relu(a + b)` 这类逐点链，Inductor 会产出形如下面的融合 kernel（示意，命名规则 `triton_poi_fused_*` 中 `poi` 即 pointwise）：

```python
@triton.jit
def triton_poi_fused_add_relu_0(in_ptr0, in_ptr1, out_ptr0, xnumel,
                                XBLOCK: tl.constexpr):
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)
    xmask = xindex < xnumel
    a = tl.load(in_ptr0 + xindex, xmask)
    b = tl.load(in_ptr1 + xindex, xmask)
    tmp = a + b
    out = tl.maximum(tmp, 0.0)          # 中间值不落 HBM
    tl.store(out_ptr0 + xindex, out, xmask)
```

三种编译模式的取舍：

| mode | 额外行为 | 适用场景 |
|------|----------|----------|
| `default` | 标准融合 + 代码生成，编译最快 | 通用训练 |
| `reduce-overhead` | 启用 CUDA Graph，消除 launch 开销 | 小 batch 推理、decode |
| `max-autotune` | Triton GEMM 模板参与选型 + 更大调优搜索空间 | 追求极致吞吐，可接受长编译时间 |

## 3. Triton 编程模型

### 3.1 Block 级 vs 线程级

CUDA 让你以**单线程**视角写程序（`threadIdx` 定位到一个标量），线程如何协作（shared memory、`__syncthreads`、warp shuffle）全部手工管理。Triton 把抽象提升到 **Block（program）级**：一个 program 处理一个数据块，你操作的是整块张量（如 `[BLOCK_SIZE]` 的向量），块内如何映射到线程/warp 由编译器决定。

| 维度 | CUDA | Triton |
|------|------|--------|
| 编程粒度 | 线程（标量） | Program（张量块） |
| 访存合并 | 手工保证相邻线程访问相邻地址 | 编译器自动向量化/合并 |
| Shared Memory | 手工声明、加载、`__syncthreads()` | 编译器自动分配与同步 |
| 软件流水线（double buffer） | 手工 `cp.async` + 多缓冲 | `num_stages` 一个参数 |
| Tensor Core | 手写 `mma` PTX 或 CUTLASS | `tl.dot` 自动映射 |
| 剩给程序员的 | 一切 | 网格划分、块大小、mask、算法本身 |

代价是失去线程级的极致控制（如精细的寄存器编排、warp specialization），所以 Triton 通常能到手写 kernel 的 80%~100% 性能，极限优化（FlashAttention V3 这类）仍属于 CUDA/CUTLASS。

### 3.2 例子：Fused Softmax

第 5 章我们用 CUDA 写 softmax 需要处理 warp reduce、shared memory 归约；Triton 版本里"一行就是一次全块归约"。每个 program 负责矩阵的一整行，max、exp、sum、div 四步全部在片上完成，只有一读一写两次 HBM 访问——这就是"fused"的含义：

```python
import torch
import triton
import triton.language as tl

@triton.jit
def softmax_kernel(out_ptr, in_ptr,
                   in_row_stride, out_row_stride, n_cols,
                   BLOCK_SIZE: tl.constexpr):
    row_id = tl.program_id(0)                       # 一个 program 处理一行
    col_offsets = tl.arange(0, BLOCK_SIZE)          # 块内列索引 [0, BLOCK_SIZE)
    mask = col_offsets < n_cols                     # 处理非 2 的幂的列数

    row = tl.load(in_ptr + row_id * in_row_stride + col_offsets,
                  mask=mask, other=-float('inf'))   # 越界补 -inf，不污染 max/sum
    row = row - tl.max(row, axis=0)                 # 全块归约求 max（数值稳定）
    num = tl.exp(row)
    den = tl.sum(num, axis=0)                       # 全块归约求 sum
    tl.store(out_ptr + row_id * out_row_stride + col_offsets,
             num / den, mask=mask)

def softmax(x: torch.Tensor) -> torch.Tensor:
    n_rows, n_cols = x.shape
    BLOCK_SIZE = triton.next_power_of_2(n_cols)     # 整行装进一个块
    num_warps = 4
    if BLOCK_SIZE >= 2048:
        num_warps = 8
    if BLOCK_SIZE >= 4096:
        num_warps = 16
    y = torch.empty_like(x)
    softmax_kernel[(n_rows,)](                      # grid = (n_rows,)
        y, x, x.stride(0), y.stride(0), n_cols,
        BLOCK_SIZE=BLOCK_SIZE, num_warps=num_warps,
    )
    return y

x = torch.randn(1823, 781, device="cuda")
assert torch.allclose(softmax(x), torch.softmax(x, dim=1), atol=1e-6)
```

几个值得咀嚼的点：

1. **mask 是 Triton 的边界处理范式**：`BLOCK_SIZE` 必须是 2 的幂，列数不足就用 mask 屏蔽，`other=-inf` 保证归约语义正确（对照第 6 章 FlashAttention kernel 中同样的技巧）；
2. **`tl.max/tl.sum` 一行完成块内归约**：编译器自动展开成 warp shuffle + shared memory 的树形归约，第 3 章手写的三个版本它一次生成；
3. **`num_warps` 是资源旋钮而非正确性参数**：决定一个 program 映射到多少线程（`num_warps × 32`）；矩阵乘类 kernel 还会用 `num_stages` 控制软件流水线深度，让 `tl.load` 的异步拷贝与 `tl.dot` 重叠。

### 3.3 编译器在背后做了什么

一份 Triton 源码经过 `Triton IR → TritonGPU IR → LLVM IR → PTX` 的多级 lower，途中自动完成：为 `tl.dot` 的操作数规划 shared memory 布局（含 swizzle 消 bank conflict）、把 `tl.load` 合并成 128-bit 向量化访存、跨循环迭代做软件流水线、把矩阵乘映射到 Tensor Core 的 `mma` 指令。你写的 40 行 softmax，编译产物与第 5 章精心手调的版本在结构上高度一致——这正是"把套路交给编译器"的含义。

## 4. XLA 与 TVM 简述

Triton/Inductor 之外，另外两个绕不开的名字。三者不在同一层竞争：

| | XLA | TVM | Triton / Inductor |
|--|-----|-----|-------------------|
| 定位 | 计算图整体编译器 | 跨硬件端到端部署编译器 | Kernel DSL / 框架内 JIT |
| 输入 | HLO（来自 JAX/TF/PyTorch-XLA） | Relax 图 IR + TensorIR | Python 函数（字节码/DSL） |
| 优化重心 | 整图融合、静态显存规划、SPMD 分片 | 自动调度搜索（AutoTVM/Ansor/MetaSchedule） | 按需生成融合 kernel |
| 硬件 | TPU 一等公民，GPU/CPU | ARM CPU、移动 GPU、NPU、长尾加速器 | NVIDIA/AMD GPU |
| 形状 | 偏静态（动态 shape 触发重编译） | 编译期确定为主 | 支持符号化动态 shape |

**XLA** 走"整图先行"路线：拿到完整 HLO 图后做激进的全局优化——大范围融合、buffer 复用、编译期显存规划，这也是 JAX 上 `jit` 一切的性能来源。代价是对动态性不友好：shape 一变就重编译，Python 控制流必须改写成 `lax.cond/scan`。torch.compile 与它的哲学差异就在于用 guard + graph break 换取"渐进式编译"：能编的编，不能编的回退，永远不阻塞用户。

**TVM** 的核心资产是**自动调度搜索**：把一个算子的分块、循环重排、向量化、并行化定义成参数空间，用机器学习代价模型 + 实测搜索最优配置。这让它在没有 cuDNN/cuBLAS 的硬件（手机 GPU、各类 NPU）上也能生成高质量 kernel——所以 TVM 的主场是**跨硬件部署**，而非 NVIDIA GPU 上与 Triton 争高下。国内芯片公司（面试高频方向）的软件栈几乎都借鉴了 TVM/MLIR 的分层 IR 设计。

## 5. 算子融合的类型

### 5.1 垂直融合与水平融合

**垂直融合（producer-consumer fusion）**：生产者的输出直接喂给消费者，中间值留在寄存器/共享内存，不落 HBM。1.2 节的 elementwise 链、softmax 的 max/exp/sum/div、GEMM+bias+activation 都属此类，是收益最大、最常见的融合。

**水平融合（horizontal fusion）**：多个**相互独立**的同构 kernel 合并成一个 launch。典型场景：优化器对几百个参数张量逐个做 `adam update`（PyTorch 的 `foreach`/`fused` 优化器即水平融合）、多头投影的多个小 GEMM 合并成 batched GEMM。收益来源不是省 HBM 流量，而是**省 launch 开销 + 提高 GPU 占用率**（小 kernel 单独跑填不满 SM）。

### 5.2 按结构分类

| 类型 | 模式 | 例子 | 收益机制 |
|------|------|------|----------|
| Elementwise 链 | pointwise → pointwise | bias + gelu + dropout | 中间值不落 HBM |
| Reduction 融合 | pointwise → reduce → pointwise | softmax、layernorm、RMSNorm | 一次读入完成整条链 |
| Epilogue 融合 | GEMM → pointwise | linear + bias + relu | 结果写回前在寄存器里顺手算完 |
| Prologue 融合 | pointwise → GEMM | dequant + GEMM（W4A16） | 读入时顺手反量化 |
| 水平融合 | 并行无依赖算子合并 | foreach 优化器、多路小 GEMM | 省 launch、提占用率 |

**Epilogue 融合**值得单独强调：GEMM 完成时结果就在累加寄存器中，此时顺手加 bias、做激活的边际成本几乎为零；若拆开执行，就要把 $M \times N$ 的结果写回 HBM 再读一遍。CUTLASS 把它抽象成 Epilogue Visitor 模板，Inductor 的 `max-autotune` 模式也会尝试把 pointwise 后缀焊进 Triton GEMM 模板。

### 5.3 什么样的算子链适合融合

判断标准（对应蚂蚁面经的"判断一组算子是否适合融合"）：

1. **访存比高**：链上算子都是 Memory-Bound（elementwise/归约），融合省下的 HBM 流量才显著；两个 Compute-Bound 的大 GEMM 融合几乎无收益；
2. **中间结果无外部引用**：若 `tmp` 还被图中其他分支使用，融合后仍须物化写回，收益消失（编译器在图上做支配关系分析来判断）;
3. **依赖关系简单**：生产者到消费者是逐点或按行的局部依赖；若消费者需要生产者的全局结果（如先全局归约再逐点），需要 split 成两个 kernel 或用持久化 kernel 技巧；
4. **出现频次高**：手工融合有开发成本，优先融热点链——这正是编译器自动融合的优势：长尾也能覆盖。

### 5.4 融合的反面：什么时候会更慢

融合不是免费午餐（面经真题："算子融合后性能反而下降"）：

- **寄存器压力**：融合 kernel 的每线程状态变多，寄存器溢出到 local memory，或 occupancy 骤降，反而更慢（第 2.3 章的资源分配权衡在此重现）；
- **破坏高度调优的库 kernel**：把 pointwise 焊进自研 GEMM，性能可能不如 cuBLAS GEMM + 独立 pointwise 两步——库 kernel 的分块/流水线是极致手调的；
- **shared memory 争抢**：融合后单 kernel 的 SMEM 需求超过阈值，每 SM 常驻 block 数下降；
- **重复计算**：一个生产者被多个消费者融合时其结果会被重算多次。

所以 Inductor 的调度器对每个候选融合估算收益（节省的访存量）与成本（资源占用），并非无脑全融。

## 6. CUDA Graph

### 6.1 Kernel Launch 开销从哪来

一次 kernel launch 的完整链路：Python 调用 → PyTorch dispatcher 分发 → CUDA runtime → 用户态驱动构造命令包 → 提交 GPU 硬件队列。整条 CPU 侧路径是**微秒量级**的固定开销。训练大模型时单 kernel 动辄数百微秒，launch 开销可忽略；但 LLM **decode 阶段** batch 小、kernel 极短（几微秒到几十微秒），一步 decode 要 launch 几百上千个 kernel，CPU 提交速度追不上 GPU 消化速度，timeline 上呈现"GPU 等 CPU"的均匀空隙——这就是 **launch bound**（第 8 章会用 Nsight Systems 亲眼看到这个模式）。

### 6.2 原理：录制一次，整图回放

CUDA Graph 把"一段 kernel 序列及其依赖"录制成 DAG，之后用单次 `cudaGraphLaunch` 整体提交，CPU 侧成本从"$N$ 次 launch"变成"1 次 launch"：

```python
import torch

model = MyDecoderLayer().cuda().eval()
static_in = torch.randn(8, 4096, device="cuda")   # 地址固定的输入 buffer

# 1) warmup：在旁路 stream 上跑几步，让 cuBLAS 等完成惰性初始化
s = torch.cuda.Stream()
s.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(s):
    for _ in range(3):
        model(static_in)
torch.cuda.current_stream().wait_stream(s)

# 2) capture：期间的所有 kernel 被录进 graph，并不真正执行
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    static_out = model(static_in)

# 3) replay：每步只需把新数据拷进固定 buffer，然后一次调用回放全部 kernel
def step(new_input):
    static_in.copy_(new_input)
    g.replay()
    return static_out          # 输出也固定在同一块地址
```

`torch.compile(model, mode="reduce-overhead")` 做的就是自动化这套流程。

### 6.3 与动态 shape 的根本矛盾

Graph 录制时**固化了一切**：kernel 参数、grid 大小、所有中间 buffer 的显存地址。因此：

- **shape 必须静态**：换 batch size 就要另录一张图；
- **地址必须稳定**：capture 期间的分配来自专属内存池（private mempool），回放期间不能释放、不能被其他分配复用；
- **显存占用上升**（小马智行面经真题）：为覆盖多种 batch size，实践中要按 `[1, 2, 4, 8, ..., 256]` 等一组尺寸各录一张图，每张图的中间激活 buffer 都被内存池长期持有，这部分显存无法归还——这就是"CUDA Graph 更吃显存"的原因，也是 vLLM 里 `gpu_memory_utilization` 要给 graph 预留空间的原因。

运行时把实际 batch **padding 到最近的已录制尺寸**再回放，多算的部分丢弃——用少量冗余计算换 launch 开销归零，在 decode 阶段稳赚（kernel 短、launch 占比高）；prefill 阶段 kernel 长且 seq_len 高度动态，一般不用 graph。

### 6.4 vLLM 的 Piecewise CUDA Graph

vLLM V1 给出了工程上最优雅的折中：**分段（piecewise）编译 + 分段 capture**。用 torch.compile 把模型在 attention 算子处切开——attention 的 kernel（PagedAttention/FlashAttention）内部要处理每条请求不同的 KV 长度、查 block table，天然动态，难以安全 capture；而 attention 之外的部分（QKV 投影、MLP、norm、逐点算子）对固定 batch size 是完全静态的。于是：

```
[embed → QKVproj → ...] → [attention] → [Oproj → MLP → ...] → [attention] → ...
 └── piece 1: CUDA Graph ──┘  eager  └── piece 2: CUDA Graph ─┘  eager
```

静态段享受 graph 的零 launch 开销，动态的 attention 保持 eager 灵活性。这个设计把"CUDA Graph vs 动态 shape"的矛盾从"二选一"变成"各取所需"，是面试讲 CUDA Graph 时最好的落地案例。

## 7. 图优化与推理引擎的关系

### 7.1 经典图优化 Pass

推理引擎（TensorRT、ONNX Runtime、TVM）在 kernel 之上还有一层图变换，常见 pass：

| Pass | 内容 |
|------|------|
| 常量折叠 | 权重相关的纯常量子图在编译期算掉 |
| 公共子表达式消除（CSE） | 相同子图只算一次 |
| 死代码消除（DCE） | 输出不可达的节点删除 |
| 算子融合 | 第 5 节的全部内容，图层负责"决定融什么" |
| Layout 变换 | NCHW ↔ NHWC，为 Tensor Core 选最优布局并消除多余 transpose |
| 代数化简 | conv + BN 折叠、`(x*a)*b → x*(ab)` |

conv+BN 折叠是最经典的例子——推理时 BN 的 $\mu, \sigma, \gamma, \beta$ 都是常量，可直接并进卷积权重：

$$
W' = \frac{\gamma}{\sqrt{\sigma^2 + \epsilon}} \cdot W, \qquad
b' = \frac{\gamma (b - \mu)}{\sqrt{\sigma^2 + \epsilon}} + \beta
$$

BN 层在图上被彻底消除，零运行时代价。

### 7.2 动态图为什么要"转静"再优化

上述 pass 都要求"看见整张图"：融合要做支配分析，常量折叠要知道哪些节点无外部依赖，显存规划要知道每个 tensor 的生命周期。动态图逐算子执行，引擎只能看见"当前这一个算子"，任何全局优化都无从谈起——这就是蚂蚁面经"为什么动态图要转静态图再融合优化"的答案。转换本身的开销（Dynamo 捕获、Inductor 编译，秒到分钟级）靠**编译缓存 + guard 复用**摊销：服务启动时编译一次，之后每步只付出纳秒级的 guard 检查。

### 7.3 LLM 推理引擎的分工格局

现代 LLM 推理引擎的图优化呈现清晰的分工：

- **热点算子手写**：attention（FlashAttention/FlashInfer）、MoE dispatch、量化 GEMM——这些是决定性能上限的 20%，用 CUDA/CUTLASS/Triton 精工打造；
- **长尾交给编译器**：norm、rope、激活、残差等胶水算子由 torch.compile 自动融合——vLLM V1 的模型代码就是普通 PyTorch，性能靠 `torch.compile` + custom op 注册获得；
- **运行时层用 CUDA Graph**：按 6.4 节的 piecewise 方式消除 launch 开销；
- **TensorRT-LLM 路线**：更接近传统引擎，pattern 匹配 + 预编译 engine，静态性更强、峰值更高、灵活性更低。

一句话总结：**编译器覆盖长尾，手写 kernel 守住热点，CUDA Graph 兜底 launch 开销**——这三件套就是当下推理引擎的标准性能配方。

## 📝 总结

1. **AI 编译器解决组合爆炸**：算子 × 精度 × 硬件 × 融合组合无法靠人力覆盖，编译器按需生成长尾 kernel；融合的收益本质是减少 HBM 往返，而非减少计算；
2. **torch.compile 三级火箭**：Dynamo 在字节码层捕获图（guard 保动态语义、graph break 保兼容性），AOTAutograd 联合追踪前反向并分解到 ATen 原语，Inductor 调度融合并生成 Triton kernel；
3. **Triton 把抽象提到 Block 级**：程序员管分块和 mask，编译器管共享内存、访存合并、流水线和 Tensor Core，以少量性能上限换数量级的开发效率；
4. **XLA 整图静态编译、TVM 跨硬件搜索调度**，与 Triton/Inductor 处于不同生态位；
5. **CUDA Graph 用"录制-回放"消除 launch 开销**，代价是静态 shape 与额外显存；vLLM 的 piecewise 方案让静态段吃 graph 红利、动态 attention 保持 eager。

**4. 能说明 Guards 与 Graph Break 各自的作用机制和常见触发场景**

<details>
<summary>参考答案</summary>

**8. 能说出垂直融合、水平融合与 epilogue 融合各自的收益机制**

<details>
<summary>参考答案</summary>

垂直融合（producer-consumer）：生产者输出直接喂消费者，中间值留在寄存器/共享内存不落 HBM——elementwise 链、softmax、GEMM+bias+activation 都属此类，收益最大。水平融合：多个相互独立的同构 kernel 合并成一个 launch（foreach 优化器、多路小 GEMM），收益来自省 launch 开销 + 提高 GPU 占用率，而非省流量。Epilogue 融合：GEMM 完成时结果就在累加寄存器中，顺手加 bias/激活的边际成本几乎为零，拆开则要把 $M \times N$ 的结果写回 HBM 再读一遍。（对应正文第 5.1/5.2 节）

</details>

**9. 能判断一条算子链是否值得融合，并举出融合反而更慢的原因**

<details>
<summary>参考答案</summary>

值得融合的四个条件：链上算子 Memory-Bound（省下的流量才是收益）、中间结果无外部引用（否则仍须物化）、依赖是逐点/按行的局部关系、出现频次高。融合更慢的四类原因：寄存器压力增大导致 spill 或 occupancy 骤降；把 pointwise 焊进自研 GEMM 不如高度手调的 cuBLAS 两步执行；SMEM 需求超阈值使每 SM 常驻 block 数下降；一个生产者被多个消费者融合导致重复计算——所以 Inductor 的调度器对每个候选融合估算收益与成本，并非无脑全融。（简答，另见 Q4/Q5；对应正文第 5.3/5.4 节）

</details>

**10. 能解释 CUDA Graph 的录制-回放原理、显存代价与 vLLM 的 piecewise 折中**

<details>
<summary>参考答案</summary>

原理：把一段 kernel 序列及其依赖录制成 DAG，之后单次 `cudaGraphLaunch` 整体提交，CPU 侧从 $N$ 次微秒级 launch 变成 1 次——专治 decode 阶段的 launch bound。代价：录制固化了 kernel 参数、grid 大小和所有中间 buffer 地址，shape 必须静态、分配来自专属内存池不能复用归还；为覆盖多种 batch size 要按一组尺寸各录一张图，运行时把实际 batch padding 到最近档位，因此更吃显存。vLLM V1 的 piecewise 方案：用 torch.compile 在 attention 算子处切图，静态段（QKV 投影、MLP、norm）capture 成 graph，动态的 attention 保持 eager，各取所需。（简答，另见 Q6；对应正文第 6.2–6.4 节）

</details>

## 🎯 高频面试题解析

以下题目均来自本站收录的真实面经（`docs/interview/`）。

**Q1：Triton 与 CUDA 在算子开发中的主要区别？（拼多多；遂原科技一面："选择 Triton 而不是 CUDA 的原因"）**

抽象粒度不同：CUDA 是线程级编程，shared memory、同步、访存合并、流水线全手工；Triton 是 Block 级编程，一个 program 操作一个张量块，上述套路由编译器自动完成（`tl.dot` 自动上 Tensor Core，`num_stages` 一个参数开软件流水线）。选 Triton 的理由：开发效率高一个数量级、与 PyTorch 无缝集成（Inductor 的 codegen 目标）、性能通常达到手写的 80%+；仍选 CUDA 的场景：需要 warp 级精细控制的极限优化（如 FlashAttention V3）。呼应第 3.1/3.3 节。

**Q2：torch.compile 的工作原理？什么情况会发生 graph break，如何避免？（中科曙光二面"PyTorch 的图优化机制"延伸）**

三级流水：Dynamo 通过 PEP 523 拦截字节码符号执行捕获 FX 图并生成 guard；AOTAutograd 联合追踪前反向、分解到 ATen 原语并函数化；Inductor 融合调度后生成 Triton/C++ kernel。graph break 由数据依赖控制流、`.item()`、print 副作用、不可追踪的 C 扩展触发，用 `TORCH_LOGS="graph_breaks"` 或 `torch._dynamo.explain` 诊断，用 `fullgraph=True` 强制暴露。呼应第 2.2 节。

**Q3：静态图和动态图各有什么特点？为什么通常要将动态图转为静态图后再做融合优化？转换开销如何处理？（蚂蚁实习一面）**

动态图逐算子分发，灵活可调试，但引擎每步只见单算子，无法做融合/常量折叠/显存规划等全局优化；静态图先建图后执行，能整图优化但牺牲灵活性。融合必须"看见"生产者-消费者关系与中间值的引用情况，所以必须先成图。转换开销靠一次编译 + 缓存复用摊销：torch.compile 用 guard 机制让后续调用只付轻量检查成本，shape 变化用 SymInt 动态维度避免反复重编。呼应第 2.2/7.2 节。

**Q4：在什么情况下可以判定算子融合是有收益的？哪些典型场景适合融合？（OPPO 二面；蚂蚁一面"判断标准：算子链长度、频次、依赖关系、中间输出是否被其他分支引用"）**

有收益的条件：链上算子 Memory-Bound（省下的 HBM 流量即收益）、中间结果无外部引用（否则仍需物化）、依赖是逐点/按行的局部关系、链条出现频次高。典型场景：elementwise 链（bias+gelu+dropout）、reduction 链（layernorm/softmax）、GEMM epilogue（+bias+激活）、水平融合（foreach 优化器）。呼应第 5.2/5.3 节。

**Q5：是否遇到过算子融合后性能反而下降的情况？原因是什么？（AI-Infra 综合题库-4）**

四类原因：寄存器压力增大导致 spill 或 occupancy 下降；融合进自研 kernel 后性能不如高度手调的 cuBLAS/cuDNN 库 kernel 两步执行；shared memory 需求超限使每 SM 常驻 block 减少；一个生产者被多个消费者融合导致重复计算。所以编译器要做收益/成本估算而非无脑融合。呼应第 5.4 节。

**Q6：什么是 CUDA Graph？为何使用 CUDA Graph 会占用更多显存？推理过程中哪个阶段更适合使用？（小马智行实习）**

CUDA Graph 把 kernel 序列录制成 DAG，单次 launch 整体回放，把 $N$ 次微秒级 CPU 提交开销压成 1 次。显存更多的原因：录制固化了所有中间 buffer 地址，分配来自专属内存池不能复用归还，且为覆盖多个 batch size 要录多张图、各自持有 buffer。适合 decode 阶段：kernel 短、数量多、launch 开销占比高，且 batch 可 padding 到固定档位；prefill kernel 长、seq_len 动态，收益小。呼应第 6.2/6.3 节。

**Q7：kernel launch 的完整流程是什么？有哪些方法可以降低 launch 开销？（AI-Infra 综合题库-6；腾讯实习一面）**

流程：框架 dispatcher 分发 → CUDA runtime → 用户态驱动构造命令包 → 提交 GPU 硬件队列，CPU 侧微秒量级固定成本。降低手段按层次：算子融合直接减少 kernel 数量（编译器/手写）；水平融合合并同构小 kernel；CUDA Graph 把 N 次 launch 变 1 次（`mode="reduce-overhead"`）；异步提交让 CPU launch 与 GPU 执行流水重叠（避免频繁同步打断流水）。呼应第 5.1/6.1/6.2 节。

**Q8：对 AI 编译器（如 TVM、XLA）的了解程度？（北极雄芯一面；快手校招 JD 明确要求 XLA/MLIR/TVM/Triton）**

按定位区分作答：XLA 是整图编译器（HLO IR），激进整图融合 + 静态显存规划，JAX/TPU 生态核心，动态性弱；TVM 是跨硬件部署编译器（Relax + TensorIR），核心竞争力是自动调度搜索，主场在没有厂商算子库的硬件；Triton 是 kernel 级 DSL，torch.compile/Inductor 是框架内 JIT，用它做 codegen 后端。国产芯片软件栈普遍参考 TVM/MLIR 的多级 IR 设计，面向该方向岗位可重点展开。呼应第 4 节。
