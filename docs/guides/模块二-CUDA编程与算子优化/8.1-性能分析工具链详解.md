## 1. 性能分析方法论

### 1.1 先 Timeline 后 Kernel

GPU 性能问题分两大类，用错工具会白忙一场：

1. **系统级问题**：GPU 大量空转——CPU 喂不上数据、kernel launch 间隙、H2D 拷贝阻塞、不必要的同步。此时优化任何单个 kernel 都是徒劳，因为时间根本没花在 kernel 上；
2. **Kernel 级问题**：GPU 一直忙，但某些 kernel 本身效率低——访存不合并、occupancy 不足、没吃到 Tensor Core。

因此标准流程是两步下钻：

```
第一步：Nsight Systems 看 timeline（宏观）
  ├─ GPU 利用率低、有空隙 → 系统级问题：找空隙对应的 CPU 行为
  └─ GPU 持续忙碌         → 找占比最高的热点 kernel
                              │
第二步：Nsight Compute 下钻热点 kernel（微观）
  ├─ SOL 面板：判断 Memory / Compute / Latency Bound
  ├─ Occupancy、访存合并度、Warp Stall 原因
  └─ 对照 Roofline：距离硬件上限还有多远
```

配套心法：**每次只改一个变量，改完复测**；优化到什么程度算完——用第 2 节的 Roofline 算出该算子的理论上限，达到上限的 70%~90% 就该停手，继续磕性价比为负。

### 1.2 工具分工

| 工具 | 层次 | 回答的问题 | 粒度 |
|------|------|-----------|------|
| Nsight Systems（nsys） | 系统级 timeline | 时间花在 CPU/GPU/拷贝/空隙的哪里 | 微秒级事件流 |
| Nsight Compute（ncu） | 单 kernel 剖析 | 这个 kernel 为什么慢 | 指令/流水线级计数器 |
| PyTorch Profiler | 框架级 | 哪个算子/模块最耗时，显存去哪了 | 算子级，含 Python 栈 |
| CUDA Event / 手工计时 | 代码级 | 这段代码改前改后差多少 | 毫秒~微秒 |

注意分工边界（卓驭面经考点）：nsys 只做事件级追踪，**不做指令级流水线分析**——它知道 kernel 何时开始结束，但不知道 kernel 内部发生了什么；指令级、warp 级的分析属于 ncu，其代价是需要回放（replay）kernel 多次采集计数器，开销大且会序列化执行，所以只用于下钻少数热点。

## 2. Roofline 模型

### 2.1 算术强度与两道屋顶

一个 kernel 的**算术强度（Arithmetic Intensity）**定义为计算量与 HBM 访问量之比：

$$
\text{AI} = \frac{\text{FLOPs}}{\text{Bytes}_{\text{HBM}}} \quad [\text{FLOP/Byte}]
$$

kernel 的可达性能被两道"屋顶"共同封顶——算力峰值 $P_{\text{peak}}$ 与带宽 $BW$ 能供上数据的速率：

$$
P_{\text{attainable}} = \min\left(P_{\text{peak}},\ \text{AI} \times BW\right)
$$

两道屋顶的交点称为 **ridge point（脊点）**：

$$
\text{AI}^{*} = \frac{P_{\text{peak}}}{BW}
$$

- $\text{AI} < \text{AI}^{*}$：**Memory Bound**，性能上限 $= \text{AI} \times BW$，优化方向是减少字节数（融合、量化、复用）；
- $\text{AI} > \text{AI}^{*}$：**Compute Bound**，性能上限 $= P_{\text{peak}}$，优化方向是吃满计算单元（Tensor Core、流水线）。

### 2.2 A100 / H100 的 Ridge Point

用官方公开规格代入（A100 80GB SXM：FP16 Tensor Core 312 TFLOPS、FP32 19.5 TFLOPS、HBM2e 2039 GB/s；H100 SXM：FP16 Tensor Core 989 TFLOPS、HBM3 3.35 TB/s）：

$$
\text{AI}^{*}_{\text{A100, FP16 TC}} = \frac{312 \times 10^{12}}{2039 \times 10^{9}} \approx 153 \ \text{FLOP/B}
\qquad
\text{AI}^{*}_{\text{A100, FP32}} = \frac{19.5 \times 10^{12}}{2039 \times 10^{9}} \approx 9.6 \ \text{FLOP/B}
$$

$$
\text{AI}^{*}_{\text{H100, FP16 TC}} = \frac{989 \times 10^{12}}{3350 \times 10^{9}} \approx 295 \ \text{FLOP/B}
$$

一个关键趋势：H100 的算力相对 A100 涨了约 3.2 倍，带宽只涨了约 1.6 倍，ridge point 从 153 升到 295——**硬件代际演进中"算力跑得比带宽快"，越来越多算子被推向 Memory Bound**，这正是算子融合和 FlashAttention 这类 IO 优化越来越重要的硬件根源。

### 2.3 三个典型算子的定位

**Elementwise（FP32 add）**：每个元素 1 FLOP，读 8B 写 4B：

$$
\text{AI} = \frac{1}{12} \approx 0.083 \ \text{FLOP/B} \ll 9.6 \Rightarrow \text{极度 Memory Bound}
$$

其性能上限完全由带宽决定：$0.083 \times 2039\,\text{GB/s} \approx 0.17$ TFLOPS，距 19.5 TFLOPS 的算力峰值差两个数量级——所以 elementwise kernel 的唯一优化指标是**带宽利用率**。

**FP16 方阵 GEMM（$N \times N \times N$）**：FLOPs $= 2N^3$，读写三个矩阵共 $3 \times 2N^2$ Bytes：

$$
\text{AI} = \frac{2N^3}{6N^2} = \frac{N}{3}
$$

$N = 4096$ 时 AI $\approx 1365 \gg 153$，深度 Compute Bound；而 $N < 459$（$N/3 < 153$）的小 GEMM 落回 Memory Bound——同一个算子，shape 不同结论不同，这是 Roofline 分析必须带 shape 讨论的原因。

**LLM decode 的 GEMV**（batch=1，权重 $[K, N]$ FP16）：FLOPs $= 2KN$，仅权重就要读 $2KN$ Bytes：

$$
\text{AI} \approx 1 \ \text{FLOP/B} \Rightarrow \text{Memory Bound}
$$

因此 decode 的每 token 延迟下限 $\approx$ 权重字节数 / 带宽，与算力几乎无关——这是"decode 看带宽、prefill 看算力"的量化依据，也是权重量化（减少字节数）能直接加速 decode 的原因。

### 2.4 实测判断 Bound 类型

理论 AI 给方向，实测靠 ncu 的 SOL 指标交叉验证：

| Compute SOL | Memory SOL | 判断 | 方向 |
|-------------|------------|------|------|
| 高（>60%） | 低 | Compute Bound | 提高计算效率（Tensor Core、降精度） |
| 低 | 高（>60%） | Memory Bound | 减少/合并访存、融合 |
| 双低 | 双低 | **Latency Bound** | 提高并行度：occupancy、ILP、增大负载 |
| 双高 | 双高 | 已接近极限 | 只能改算法（如 FlashAttention 之于 Attention） |

"双低"最容易被误读：不是硬件够用了，而是并行度不足以掩盖延迟——kernel 太小、occupancy 太低或依赖链太长。

## 3. Nsight Systems 实操

### 3.1 采集命令

```bash
# 基本采集：CUDA API、kernel、NVTX 区间、OS 系统调用、cuBLAS/cuDNN
nsys profile -o train_report \
  --trace=cuda,nvtx,osrt,cublas,cudnn \
  python train.py

# 只抓稳定阶段的几个 iteration（跳过 warmup），配合代码中的开关
nsys profile -o iter_report \
  --capture-range=cudaProfilerApi --capture-range-end=stop \
  python train.py

# 不开 GUI 先看命令行摘要：kernel 耗时排行、memcpy 统计
nsys stats train_report.nsys-rep
```

配合 `--capture-range` 的代码开关：

```python
import torch

for step, batch in enumerate(loader):
    if step == 10:
        torch.cuda.profiler.start()   # 从第 10 步开始录制
    train_step(batch)
    if step == 15:
        torch.cuda.profiler.stop()    # 只录 5 个 iteration
```

### 3.2 NVTX 打标：让 timeline 讲人话

裸 timeline 上只有几千个 kernel 名，先用 NVTX 把语义标上去：

```python
import torch.cuda.nvtx as nvtx

for step, batch in enumerate(loader):
    with nvtx.range(f"step_{step}"):
        with nvtx.range("data_to_gpu"):
            x = batch.cuda(non_blocking=True)
        with nvtx.range("forward"):
            loss = model(x)
        with nvtx.range("backward"):
            loss.backward()
        with nvtx.range("optimizer"):
            opt.step(); opt.zero_grad(set_to_none=True)
```

采集时加 `--trace=nvtx`，timeline 上就有了 forward/backward/optimizer 的彩色区间，可直接回答"反向占了多少、优化器占了多少"。PyTorch 自带的 `torch.autograd.profiler.emit_nvtx()` 还能把每个 ATen 算子自动标成 NVTX 区间。

### 3.3 看图要点：三条泳道

打开 GUI 后重点看三条泳道的**对齐关系**：

1. **CUDA HW（GPU kernel 行）**：理想状态是 kernel 首尾相接无空隙。凡有空隙，垂直对齐到同一时刻的 CPU 线程行，看 CPU 正在干什么——那就是空隙的原因；
2. **CPU 线程行**：Python 解释器忙（数据预处理、日志）、还是卡在 `cudaStreamSynchronize`/`cudaMemcpy` 上等 GPU；
3. **Memory 行（H2D/D2H）**：拷贝是否与计算重叠。同步版 `cudaMemcpy` 会同时卡住 CPU 和计算流；异步拷贝（pinned memory + 独立 stream）应与 kernel 并行。

### 3.4 三种经典空隙形态

| Timeline 形态 | 诊断 | 对应第 7 节药方 |
|---------------|------|----------------|
| kernel 极短且间隙均匀，CPU 侧 launch 调用密集 | Kernel Launch Bound | CUDA Graph / 融合 |
| 每个 iteration 开头一段长 H2D，期间 GPU 空转 | 数据加载阻塞 | pinned memory + 预取 |
| 空隙对齐到 `cudaStreamSynchronize` / `cudaMemcpyD2H` | 隐性同步点（`.item()`、`.cpu()`、打日志取 loss） | 移除热路径同步 |

## 4. Nsight Compute 关键指标

### 4.1 采集与 SOL 面板

ncu 通过**回放** kernel 多次采集硬件计数器，开销大，务必用过滤器只抓热点：

```bash
# 抓名字匹配 softmax 的 kernel，各采 3 次，完整指标集
ncu -o softmax_report --set full -k "regex:softmax" -c 3 python bench.py

# 只看两个核心 SOL 指标（快速分诊）
ncu --metrics sm__throughput.avg.pct_of_peak_sustained_elapsed,\
dram__throughput.avg.pct_of_peak_sustained_elapsed \
  -k "regex:softmax" python bench.py
```

**SOL（Speed of Light）**：把 kernel 的实测吞吐表示为**硬件理论峰值的百分比**——`Compute (SM) Throughput` 与 `Memory Throughput` 两个数，是 ncu 报告的第一屏，按 2.4 节的矩阵直接分诊 bound 类型。

### 4.2 Occupancy 怎么读

- **Theoretical Occupancy**：由每线程寄存器数、每 block 共享内存、block 大小三者与 SM 资源上限共同决定的理论 warp 驻留比例（第 2.3 章的资源模型）；
- **Achieved Occupancy**：实际运行中活跃 warp 的平均比例。

两个陷阱：理论高、实测低 → grid 太小填不满 SM 或 warp 间负载不均（tail effect）；occupancy 不是越高越好——它只是**掩盖延迟的手段**，寄存器充足、ILP 高的 kernel（如手写 GEMM）在 30%~50% occupancy 也能打满算力，盲目提高 occupancy 反而挤掉寄存器分块。

### 4.3 Warp Stall 原因速查

Warp State 面板告诉你 warp 平均每条指令卡在什么状态：

| Stall 原因 | 含义 | 药方 |
|-----------|------|------|
| Long Scoreboard | 等全局内存/L2 数据返回 | 改善合并、提高 occupancy、预取到共享内存 |
| Short Scoreboard | 等共享内存（MIO） | 消 bank conflict（padding/swizzle） |
| Barrier | 等 `__syncthreads()` | 减少同步次数、平衡 warp 间工作量 |
| Wait | 等固定延迟的 ALU 依赖 | 展开循环增加 ILP |
| Math Pipe Throttle | 计算管线饱和 | 已 Compute Bound，是好消息 |
| Not Selected | 就绪但调度器选了别的 warp | 无需处理，延迟已被掩盖 |

### 4.4 访存合并度：Sectors per Request

L1TEX 面板的 `sectors/req` 是量化第 2.2 章合并访存的直接指标：一个 warp 的 FP32 连续访问 = 128B = **4 个 32B sector**，即理想值 4；若每线程跨大步长访问，最坏 32 个线程落在 32 个不同 sector，`sectors/req = 32`，有效带宽只剩 1/8。看到高 DRAM 流量 + 高 sectors/req，药方就是调整数据布局（AoS→SoA）或用 `float4` 向量化。

## 5. PyTorch Profiler

### 5.1 标准用法

框架层的第一手信息：哪个算子最耗时、CPU 和 GPU 时间怎么分布、显存峰值在哪：

```python
import torch
from torch.profiler import profile, record_function, ProfilerActivity, schedule

with profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    schedule=schedule(wait=1, warmup=2, active=3, repeat=1),  # 跳过前 3 步
    on_trace_ready=torch.profiler.tensorboard_trace_handler("./tb_log"),
    record_shapes=True,      # 记录算子输入 shape
    profile_memory=True,     # 追踪显存分配
    with_stack=True,         # 关联 Python 调用栈
) as prof:
    for step in range(6):
        with record_function("train_step"):   # 自定义区间，作用类似 NVTX
            train_step()
        prof.step()                            # 告知 profiler 步进

print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=10))
prof.export_chrome_trace("trace.json")         # chrome://tracing 或 Perfetto 打开
```

`tensorboard --logdir ./tb_log` 后可看算子排行、kernel 视图、显存曲线和 trace 时间线；`schedule` 必须跳过 warmup 步，否则首次 cuDNN 选算法、编译等一次性开销会污染统计。

### 5.2 读表的两个关键区分

- **CPU total vs CUDA total**：某算子 CPU 时间长但 CUDA 时间短，说明瓶颈在 Python/分发层而非 GPU——这是发现"CPU 喂不上"的框架层证据，与 nsys 的 timeline 结论互相印证；
- **Self time vs total time**：`aten::linear` 的 total 包含其调用的 `aten::matmul`，看 self time 才能定位真正干活的底层算子。

PyTorch Profiler 的定位是**日常快速诊断**：开销小、不换工具链、能关联到模型代码行（`with_stack`）；当需要 kernel 内部细节时，再升级到 nsys/ncu。

## 6. CUDA Event 计时的正确姿势

### 6.1 为什么 time.time() 会骗人

CUDA kernel **异步执行**：`kernel<<<...>>>()` 或 PyTorch 算子调用只是把任务提交进 stream 就立即返回。不加同步直接用 `time.time()` 计时，测到的只是 **CPU 提交（launch）时间**，可能比真实执行时间短几个数量级。

### 6.2 标准模板

```python
import torch

def bench(fn, warmup=10, iters=100):
    # 1) warmup：触发 JIT 编译、cuDNN 算法选择、内存池预热
    for _ in range(warmup):
        fn()
    torch.cuda.synchronize()                 # 2) 清空队列，从干净状态起测

    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    start.record()                           # 3) event 随 stream 入队，在 GPU 上打点
    for _ in range(iters):
        fn()
    end.record()
    torch.cuda.synchronize()                 # 4) 等 end event 真正发生
    return start.elapsed_time(end) / iters   # 毫秒，GPU 侧时间戳之差

t = bench(lambda: torch.softmax(x, dim=-1))
print(f"{t*1000:.1f} us/iter")
```

要点逐条对应常见翻车现场：

1. **不 warmup**：首次调用包含 cuDNN benchmark、Triton/torch.compile 编译、显存池扩容，能差出数量级；
2. **不同步就 record/读数**：`elapsed_time` 前必须确保 `end` 已发生（`synchronize` 或 `end.query()`）；
3. **循环内同步**：把 `synchronize` 放进计时循环会打断 CPU-GPU 流水，测出来的是"同步版"性能，掩盖了真实的异步行为；
4. **单次测量**：GPU 频率会动态调整（DVFS），应多次取中位数/均值，严格对比时锁频（`nvidia-smi -lgc`）；
5. **忽略 L2 缓存**：小张量反复跑同一 kernel，数据常驻 L2，测出的"带宽"会超过 HBM 物理带宽——严谨的 kernel 基准（如 Triton 的 `do_bench`）会在迭代间清 L2。

这套"GPU 侧打点"的思路也是自研轻量 Timing 工具的底层原理（蚂蚁面经考点）：在框架关键路径插 CUDA Event，常态化低开销采集线上耗时；而 Nsight 系列开销大、需要独占式抓取，适合离线深度分析，两者互补而非替代。

## 7. 常见性能问题模式手册

四种高频模式的"症状 → 诊断 → 药方"：

| 模式 | Timeline/指标症状 | 确诊手段 | 药方 |
|------|-------------------|----------|------|
| Kernel Launch Bound | kernel 短（≈µs 级）且间隙均匀；CPU 侧 launch 调用铺满 | nsys：GPU 空隙对齐 CPU launch；kernel 数量巨大 | 算子融合减 kernel 数；CUDA Graph（`mode="reduce-overhead"`）；增大 batch |
| H2D 拷贝阻塞 | iteration 开头长 memcpy，GPU 空转；拷贝与计算不重叠 | nsys Memory 行；`cudaMemcpy`（同步版）出现在 CPU 行 | `pin_memory=True` + `non_blocking=True`；DataLoader 多 worker + 预取；独立 copy stream |
| 低 Occupancy / Latency Bound | ncu：SOL 双低，achieved occupancy 低 | ncu Occupancy 面板看限制因子（寄存器/SMEM/block 大小） | 调 block size；`__launch_bounds__` 限寄存器；小任务合并（水平融合） |
| 非合并访存 | Memory SOL 高但有效数据率低；耗时远超字节数/带宽的估算 | ncu：`sectors/req` 远大于 4；Long Scoreboard stall 高 | 改布局 AoS→SoA；对齐 + `float4` 向量化；共享内存中转重排 |

补充三条工程经验：

1. **H2D 与 D2H 可以重叠**（快手面经考点）：PCIe 全双工，现代 GPU 有独立的上行/下行拷贝引擎，两个方向的异步拷贝放不同 stream 即可同时进行，还能同时与 kernel 计算重叠——前提都是 pinned memory；
2. **警惕隐性同步**：`.item()`、`.cpu()`、`print(loss)`、`tensor.tolist()` 都会触发 D2H 同步拷贝，把异步流水拦腰截断；训练日志应攒多步一起取回；
3. **优化收敛判据**：药方生效的标志不是"感觉快了"，而是指标回归正常——launch bound 消失后 GPU 空隙闭合、拷贝重叠后 memcpy 藏进计算区间、合并修复后 sectors/req 回到 4 附近、最终 kernel 耗时逼近 Roofline 上限。

---

## 📝 总结

1. **方法论**：先 nsys 看 timeline 分清系统级还是 kernel 级问题，再 ncu 下钻热点；每次一个变量，以 Roofline 上限为收敛判据；
2. **Roofline**：$P = \min(P_{\text{peak}}, \text{AI} \times BW)$；A100 FP16 的 ridge point 约 153 FLOP/B、H100 约 295——算力增速快于带宽，算子普遍滑向 Memory Bound；
3. **nsys** 管宏观（launch 空隙、H2D、同步点，用 NVTX 标语义），**ncu** 管微观（SOL 分诊、occupancy、warp stall、sectors/req），**PyTorch Profiler** 管框架层（算子排行、CPU/GPU 时间、显存），**CUDA Event** 管代码层（warmup + 同步 + 多次取中位数）;
4. **模式手册**：launch bound 用融合/CUDA Graph，H2D 阻塞用 pinned memory + 预取重叠，低 occupancy 调资源配比，非合并访存改布局/向量化。

**1. 能说出"先 Timeline 后 Kernel"的两步下钻流程与每步的工具分工**

<details>
<summary>参考答案</summary>

第一步用 Nsight Systems 看 timeline：GPU 利用率低、有空隙 → 系统级问题（CPU 喂不上、launch 间隙、拷贝阻塞、不必要同步），先找空隙对应的 CPU 行为，此时优化单 kernel 是徒劳；GPU 持续忙碌 → 找占比最高的热点 kernel。第二步用 Nsight Compute 下钻热点：SOL 面板分诊 bound 类型，再看 occupancy、访存合并度、warp stall，并对照 Roofline 看距硬件上限多远。配套心法：每次只改一个变量、改完复测；达到理论上限的 70%~90% 就该停手。（对应正文第 1.1 节）

</details>

**2. 能写出 Roofline 的封顶公式并解释 ridge point 两侧的优化方向**

<details>
<summary>参考答案</summary>

算术强度 $\text{AI} = \text{FLOPs} / \text{Bytes}_{\text{HBM}}$，可达性能 $P_{\text{attainable}} = \min(P_{\text{peak}}, \text{AI} \times BW)$，两道屋顶的交点即脊点 $\text{AI}^* = P_{\text{peak}}/BW$。AI 小于脊点为 Memory Bound，上限是 $\text{AI} \times BW$，优化方向是减少字节数（融合、量化、复用）；AI 大于脊点为 Compute Bound，上限是 $P_{\text{peak}}$，方向是吃满计算单元（Tensor Core、流水线）。（简答，另见 Q2；对应正文第 2.1 节）

</details>

**3. 能代入 A100/H100 规格算出 ridge point，并解释"算子普遍滑向 Memory Bound"的硬件趋势**

<details>
<summary>参考答案</summary>

A100（FP16 Tensor Core 312 TFLOPS、HBM2e 2039 GB/s）：$\text{AI}^* \approx 153$ FLOP/B，FP32 则约 9.6；H100（FP16 TC 989 TFLOPS、HBM3 3.35 TB/s）：$\text{AI}^* \approx 295$ FLOP/B。H100 算力相对 A100 涨约 3.2 倍而带宽只涨约 1.6 倍，脊点从 153 升到 295——硬件代际演进中算力跑得比带宽快，越来越多算子被推向 Memory Bound，这正是算子融合与 FlashAttention 这类 IO 优化越来越重要的硬件根源。（对应正文第 2.2 节）

</details>

**4. 能算出 elementwise、GEMM、decode GEMV 三类算子的算术强度并定位其 bound 类型**

<details>
<summary>参考答案</summary>

FP32 add：每元素 1 FLOP、读 8B 写 4B，$\text{AI} = 1/12 \approx 0.083$ FLOP/B，极度 Memory Bound，唯一优化指标是带宽利用率。FP16 方阵 GEMM：$\text{AI} = 2N^3 / 6N^2 = N/3$，$N=4096$ 时约 1365、深度 Compute Bound，而 $N < 459$ 的小 GEMM 落回 Memory Bound——Roofline 分析必须带 shape 讨论。LLM decode 的 GEMV（batch=1）：$\text{AI} \approx 1$ FLOP/B，每 token 延迟下限约等于权重字节数除以带宽，与算力几乎无关——这是"decode 看带宽、prefill 看算力"的量化依据，也是权重量化能直接加速 decode 的原因。（对应正文第 2.3 节）

</details>

**5. 能用 Compute/Memory SOL 双指标矩阵分诊四种 bound 类型，并解释"双低"的真实含义**

<details>
<summary>参考答案</summary>

Compute SOL 高（>60%）、Memory 低 → Compute Bound，提高计算效率；Memory 高、Compute 低 → Memory Bound，减少/合并访存；双低 → Latency Bound；双高 → 已接近极限，只能改算法（如 FlashAttention 之于 Attention）。"双低"最容易被误读：不是硬件够用了，而是并行度不足以掩盖延迟——kernel 太小、occupancy 太低或依赖链太长，方向是提 occupancy、ILP 或增大负载。（简答，另见 Q5；对应正文第 2.4/4.1 节）

</details>

**6. 能写出 nsys 的采集命令要点，并说出 timeline 上三条泳道各看什么**

<details>
<summary>参考答案</summary>

采集：`nsys profile --trace=cuda,nvtx,osrt,cublas,cudnn`；用 `--capture-range=cudaProfilerApi` 配合代码里的 `torch.cuda.profiler.start()/stop()` 只录稳定阶段的几个 iteration；先用 `nsys stats` 看命令行摘要；用 NVTX（`nvtx.range` 或 `emit_nvtx()`）给 timeline 标上 forward/backward/optimizer 语义。看图重点是三条泳道的对齐关系：CUDA HW 行看 kernel 是否首尾相接、有空隙就垂直对齐到 CPU 行找原因；CPU 线程行看是 Python 忙还是卡在同步/拷贝；Memory 行看 H2D/D2H 是否与计算重叠。（对应正文第 3.1–3.3 节）

</details>

**7. 能正确解读 occupancy 与 warp stall：为什么 occupancy 不是越高越好？Long/Short Scoreboard 各卡在哪？**

<details>
<summary>参考答案</summary>

Theoretical Occupancy 由寄存器、共享内存、block 大小与 SM 资源上限决定，Achieved 是实测活跃 warp 比例；理论高实测低说明 grid 太小填不满 SM 或 warp 负载不均（tail effect）。Occupancy 只是掩盖延迟的手段：寄存器充足、ILP 高的 kernel（如手写 GEMM）在 30%~50% occupancy 也能打满算力，盲目提高反而挤掉寄存器分块。Warp stall 速查：Long Scoreboard = 等全局内存/L2 数据；Short Scoreboard = 等共享内存（消 bank conflict）；Barrier = 等 `__syncthreads()`；Math Pipe Throttle = 计算管线饱和（好消息）；Not Selected 无需处理。（对应正文第 4.2/4.3 节）

</details>

**8. 能解释 sectors/req 指标的理想值与最坏值，以及它对应的药方**

<details>
<summary>参考答案</summary>

L1TEX 面板的 `sectors/req` 是访存合并度的直接量化：一个 warp 的 FP32 连续访问是 128B = 4 个 32B sector，理想值为 4；若每线程跨大步长访问，最坏 32 个线程落在 32 个不同 sector，`sectors/req = 32`，有效带宽只剩 1/8。看到高 DRAM 流量 + 高 sectors/req，药方是调整数据布局（AoS→SoA）、对齐 + `float4` 向量化，或经共享内存中转重排。（对应正文第 4.4 节）

</details>

**9. 能写出 CUDA Event 计时的标准模板，并列出五个常见翻车点**

<details>
<summary>参考答案</summary>

模板：warmup 若干次 → `torch.cuda.synchronize()` 清空队列 → `start.record()` → 计时循环 → `end.record()` → `synchronize()` → `start.elapsed_time(end) / iters`。五个翻车点：(1) 不 warmup，首次调用含 cuDNN 选算法/编译/显存池扩容，能差出数量级；(2) 不同步就读数，`elapsed_time` 前必须确保 end 事件已发生；(3) 把同步放进计时循环，打断 CPU-GPU 流水，测的是"同步版"性能；(4) 单次测量受 DVFS 影响，应多次取中位数或锁频；(5) 小张量常驻 L2，测出的"带宽"会超过 HBM 物理带宽，严谨基准要在迭代间清 L2。根因是 kernel 异步执行，不同步的 `time.time()` 只测到 CPU 提交时间。（对应正文第 6 节）

</details>

**10. 能默写四种高频性能问题模式的"症状 → 药方"对应关系**

<details>
<summary>参考答案</summary>

(1) Kernel Launch Bound：kernel 微秒级且间隙均匀、CPU 侧 launch 铺满 → 算子融合减 kernel 数、CUDA Graph（`reduce-overhead`）、增大 batch；(2) H2D 拷贝阻塞：iteration 开头长 memcpy、GPU 空转 → `pin_memory` + `non_blocking`、DataLoader 多 worker 预取、独立 copy stream；(3) 低 Occupancy / Latency Bound：SOL 双低 → 调 block size、`__launch_bounds__` 限寄存器、水平融合小任务；(4) 非合并访存：sectors/req 远大于 4、Long Scoreboard 高 → 改布局/向量化/共享内存中转。另记两条：PCIe 全双工，H2D 与 D2H 用不同 stream 可同时进行并与计算重叠（前提 pinned memory）；`.item()/.cpu()/print(loss)` 都是隐性同步，会拦腰截断异步流水。（对应正文第 7 节）

</details>

## 🎯 高频面试题解析

以下题目均来自本站收录的真实面经（`docs/interview/`）。

**Q1：从 profiling 到最终落地，算子优化的完整流程是什么？如何判断算子属于 memory-bound 还是 compute-bound？（卓驭校招一面）**

流程：nsys 抓 timeline → 确认 GPU 是否空转（先解决系统级问题）→ 找热点 kernel → ncu 下钻看 SOL 分诊 → 对症优化（访存/计算/并行度）→ CUDA Event 回归测试 → 对照 Roofline 上限决定是否继续。判断 bound：理论上算 AI 与 ridge point 比较（$\text{AI} \lessgtr P_{\text{peak}}/BW$）；实测上看 ncu 的 Compute/Memory SOL 哪个先顶到高位，双低则是 latency bound。呼应第 1.1、2.4 节。

**Q2：请阐述 Roofline 模型的基本原理，如何利用该模型判断一个算子是否已达到计算瓶颈？（AI-Infra 一面）**

性能被 $\min(P_{\text{peak}}, \text{AI} \times BW)$ 封顶，AI 是 FLOPs 与 HBM 字节数之比，交点 $\text{AI}^* = P_{\text{peak}}/BW$（A100 FP16 约 153 FLOP/B）。算子 AI 大于脊点则上限是算力：实测 FLOPS 接近峰值（Compute SOL 高）即已达计算瓶颈，继续优化只能换算法或降精度；AI 小于脊点则上限是带宽，应比较实测带宽与 HBM 峰值。加分项：给出 GEMM AI $= N/3$、elementwise $\approx 0.083$ 的量化例子。呼应第 2 节。

**Q3：如何利用 profiling 工具判断一个 GPU 算子的性能瓶颈在于访存还是计算？有哪些通用的优化思路？（B站实习一面）**

用 ncu 的 SOL 面板：Memory Throughput 高、Compute 低 → 访存瓶颈；反之为计算瓶颈；双低为延迟瓶颈。访存瓶颈思路：合并访存（sectors/req 降到 4）、共享内存复用、向量化加载、算子融合减少 HBM 往返；计算瓶颈思路：用 Tensor Core、降精度、增大分块提高数据复用；延迟瓶颈思路：提高 occupancy 与 ILP。呼应第 2.4、4 节。

**Q4：GPU 性能优化中，Nsight 工具链如何使用？应关注哪些计算效率与带宽效率指标？（飞腾校招二面；腾讯实习"Nsight 工具的用途与使用方法"）**

Nsight Systems 抓全链路 timeline（`nsys profile --trace=cuda,nvtx`），配 NVTX 标注，关注 GPU 空隙、memcpy、同步点；Nsight Compute 下钻单 kernel（`ncu --set full -k <name>`）。计算效率指标：SM Throughput（Compute SOL）、Tensor Core 利用率、achieved occupancy、warp stall 分布；带宽效率指标：DRAM Throughput（Memory SOL）、L1/L2 命中率、sectors per request（合并度）、有效带宽与 HBM 峰值之比。呼应第 3、4 节。

**Q5：SOL（Speed of Light）指标的含义是什么？（腾讯实习一二面）**

ncu 把 kernel 实测的 SM 计算吞吐与显存吞吐分别表示为对应硬件理论峰值（"光速"）的百分比。它是分诊指标：计算 SOL 高为 compute bound，显存 SOL 高为 memory bound，双低为 latency bound（并行度不足掩不住延迟），双高说明 kernel 已近极限、只能改算法。呼应第 4.1、2.4 节。

**Q6：常用的 profiling 工具有哪些？Nsight Systems 是否支持指令级流水线分析？（卓驭校招一面）**

分层作答：nsys（系统 timeline）、ncu（kernel 级）、PyTorch Profiler（框架算子级）、CUDA Event（代码级）、nvidia-smi/dcgm（设备级监控）。nsys **不支持**指令级流水线分析——它只记录 API 与 kernel 的起止事件；指令级、warp stall、流水线利用率要用 ncu，其原理是回放 kernel 采集硬件计数器，开销大且序列化执行，故只用于热点下钻。呼应第 1.2 节。

**Q7：PyTorch 中有哪些常用的性能分析工具和方法？（中科曙光二面）**

`torch.profiler`（CPU+CUDA activity、schedule 跳 warmup、tensorboard/chrome trace 可视化、`record_function` 自定义区间、`profile_memory` 查显存）；`torch.autograd.profiler.emit_nvtx()` 配合 nsys；`torch.cuda.Event` 精确计时；`torch.cuda.memory_summary()`/`memory_snapshot()` 查显存碎片。方法上强调：先 `key_averages` 排行找热点，区分 CPU time 与 CUDA time 判断瓶颈在框架层还是 GPU。呼应第 5、6 节。

**Q8：自研 Timing 工具的底层实现是什么？为什么不直接使用 Nsight/NCU 等 Profiling 工具？（蚂蚁实习一面）**

底层用 CUDA Event 在 GPU stream 上打点（异步、GPU 侧时间戳、单点开销极低），配合 warmup 与同步收尾聚合统计。不直接用 Nsight 的原因：ncu 回放 kernel 开销巨大且序列化执行，nsys 需要独占抓取并产出离线文件，都不适合**常态化、线上、低开销**的持续监控；自研 Event 打点可嵌入框架关键路径长期运行，发现异常后再用 Nsight 离线深挖——两者是"日常体检"与"住院检查"的互补关系。呼应第 6.2 节末尾与第 1.2 节。
