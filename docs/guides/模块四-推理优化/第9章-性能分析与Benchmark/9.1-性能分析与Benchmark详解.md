"我们的推理引擎吞吐提升了 3 倍"——这句话在没有说清测量条件之前毫无意义：输入输出长度分布是什么？并发多少？流式还是非流式？延迟涨了多少？前面的章节讲了一堆优化手段（PagedAttention、量化、投机解码、PD 分离），它们各自"快"在完全不同的指标上，甚至彼此以对方为代价。本文建立一套能把这些优化放到同一杆秤上的度量体系：先给 TTFT/TPOT/ITL/Goodput 下准确的定义并讲清它们之间的权衡，再讲 SLO 怎么定、latency-throughput 曲线怎么画、拐点怎么找，然后给出 vllm bench 与 genai-perf 的可运行压测命令、盘点最常见的 Benchmark 造假与踩坑方式，最后落到"指标异常 → 瓶颈定位"的排查路径和 vLLM 的指标观测实践。

## 1. 推理核心指标体系

LLM 推理的特殊性在于：一个请求不是"一问一答"的单点事件，而是**流式吐 token 的过程**。所以延迟必须拆成多个阶段分别度量。

### 1.1 延迟侧：TTFT / TPOT / ITL / E2E

- **TTFT（Time To First Token，首 token 延迟）**：从请求发出到收到第一个输出 token 的时间。它包含**排队时间 + Prefill 时间**——用户"等它开口"的体感。
- **ITL（Inter-Token Latency，token 间延迟）**：流式输出中**相邻两个 token 之间的间隔**，一个请求会产生 $N_{\text{out}} - 1$ 个 ITL 样本。它是用户"看它打字流不流畅"的体感，卡顿（个别 ITL 突刺）只有它能暴露。
- **TPOT（Time Per Output Token，平均每 token 时间）**：首 token 之后，平均每生成一个 token 花的时间。通常按请求级定义为：

$$
\text{TPOT} = \frac{T_{\text{E2E}} - \text{TTFT}}{N_{\text{out}} - 1}
$$

- **E2E Latency（端到端延迟）**：从发请求到收到最后一个 token。四者的关系：

$$
T_{\text{E2E}} = \text{TTFT} + \sum_{i=1}^{N_{\text{out}}-1} \text{ITL}_i = \text{TTFT} + \text{TPOT} \times (N_{\text{out}} - 1)
$$

🔑 **核心概念**：**TPOT 是 ITL 的请求内均值，均值会抹平突刺**。一个请求 TPOT 很好看，但如果某个 ITL 因为抢占/重调度冲到 2 秒，用户看到的就是"卡住了"。所以严谨的压测报告应同时给 TPOT 和 ITL 的分位数（genai-perf 和 vllm bench 都分开输出这两项）。

### 1.2 吞吐侧：Throughput 与 Goodput

- **Throughput（吞吐）**：单位时间完成的量。同一个词有三种口径，混用是事故之源：
  - **请求吞吐**：requests/s（即 QPS 的完成侧）；
  - **输出 token 吞吐**：output tokens/s——生成侧的产能；
  - **总 token 吞吐**：(input + output) tokens/s——长输入场景下会显得非常"虚高"。
- **Goodput（有效吞吐）**：**满足 SLO 的**请求（或 token）吞吐。这是 DistServe 论文推广开的概念：把延迟约束内建到吞吐指标里——一个把 batch 拉满、吞吐翻倍但 p99 TPOT 全部超标的系统，Goodput 可能是零。

📌 **关键点**：延迟与吞吐天然对抗——batch 越大，GPU 利用率越高、吞吐越高，但每个请求分到的算力/带宽变少，TTFT 和 TPOT 都变差。**报吞吐必须带延迟约束，报延迟必须带负载条件**，否则都是单方面宣传。Goodput 就是把这句话做成了一个指标。

## 2. 尾延迟：为什么 P99 比均值重要

所有延迟指标都应报分位数（P50/P95/P99）而不是均值，原因有三层：

1. **分布是重尾的**：推理延迟受排队、抢占、Prefill 插队、GC 等偶发因素影响，分布右侧拖着长尾。均值被长尾拉高却又掩盖长尾——它既不代表典型用户（P50），也不代表最差体验（P99）。
2. **用户体验按"最差的那次"记忆**：一个多轮对话会话包含几十个请求，只要有一次撞上 P99，用户就经历了一次"卡死"。请求量越大，撞上尾部的用户绝对数越多。
3. **均值可以被刷**：把一批短请求塞进统计窗口就能拉低均值；P99 刷不了，它逼着你正视调度和抢占的行为。

⚠️ **注意**：分位数**不能跨机器/跨窗口直接平均**（P99 的均值不是全局 P99）。多实例服务要么在网关层集中采样原始延迟，要么用直方图（如 Prometheus histogram）在查询侧合并分桶后再算分位数——vLLM 的 metrics 端点导出的正是直方图（见第 8 节）。

## 3. SLO 怎么定：在线对话与批处理

SLO（Service Level Objective）是把"用户体验"翻译成"指标阈值"。不同场景翻译出来的东西完全不同：

### 3.1 在线对话：约束 TTFT 与 TPOT 的分位数

体验拆成两段："多久开口"和"打字够不够快"。

- **TTFT**：对话产品普遍要求亚秒级的 P99——超过一两秒，用户就开始怀疑卡死。
- **TPOT/ITL**：只要生成速度**快于用户阅读速度**，更快的收益就急剧递减。人的阅读速度是每秒几个词的量级，工业界与论文（如 DistServe 的实验设定）常把对话场景的 TPOT SLO 设在几十到一百毫秒/token 的量级。
- 典型写法：`TTFT P99 < 1s 且 TPOT P99 < 100ms，SLO 达成率 > 99%`。

### 3.2 批处理（离线）：约束吞吐与成本

摘要生成、数据蒸馏、评测跑分这类离线任务没有人在等首 token：

- 核心指标是**总 token 吞吐**和**单位成本**（元 / 百万 token），延迟约束放宽到任务级（如"12 小时内跑完"）；
- 因此可以把 batch 压满、拉高 `max_num_batched_tokens`、接受高 TTFT，换极致吞吐——与在线场景的调参方向完全相反。

📌 **关键点**：SLO 决定优化方向。同一套引擎，在线场景该关注"限并发、保尾延迟"，离线场景该关注"塞满卡、保吞吐"。面试被问"如何优化推理服务"时，先反问场景与 SLO，是区分背题者和实践者的第一道分水岭。混合部署时更进一步——在线离线分池，或用 PD 分离把 Prefill 干扰隔离出去（见第 7 章）。

## 4. Benchmark 方法论：把变量钉死

一次有效的压测 = 固定所有无关变量 + 只扫描一个自变量 + 完整记录条件。标准流程：

### 4.1 固定工作负载

- **输入/输出长度分布**：要么固定长度（如 1024 in / 256 out，便于对照与复现），要么用真实分布（如 ShareGPT 采样，更接近生产）。**报告里必须写明**，因为 Prefill 代价 $\propto$ 输入长度、Decode 代价 $\propto$ 输出长度，长度分布一变，所有结论作废。
- **输出长度要强制**：用 `--ignore-eos`（或等价 `max_tokens` 钉死），否则不同引擎/采样参数下 EOS 出现早晚不同，输出长度不同，比较不成立。
- **请求到达模式**：一次性全发（`--request-rate inf`，测极限吞吐）、固定速率泊松到达（模拟真实流量）、固定并发（`--max-concurrency`，画曲线最常用）三选一并写明。

### 4.2 并发扫描：画 latency-throughput 曲线

单点数据没有意义，曲线才有。把并发从 1 扫到饱和（1, 2, 4, ..., 256），每个点记录吞吐与延迟分位数，画两条曲线：

```text
吞吐                                  P99 延迟
 ▲                  ____________       ▲                        /
 │              __/     ← 饱和区        │                      /
 │           _/                        │                    /
 │        _/  ← 拐点(knee)             │        ____----‾‾  ← 拐点后延迟陡增
 │     _/                             │____----
 └──────────────────────► 并发         └──────────────────────► 并发
```

- **线性区**：并发翻倍吞吐近似翻倍，延迟平稳——GPU 还没吃饱；
- **拐点（knee）**：吞吐增速放缓、延迟开始陡增——batch 效应吃满，请求开始排队；
- **饱和区**：吞吐封顶（受算力/带宽/KV Cache 容量限制），再加并发只是把排队时间加进 TTFT。

**运营点应选在拐点附近**：往左浪费 GPU，往右吞吐几乎不涨、纯粹用尾延迟换账面并发。找拐点，就是"在 SLO 约束下最大化吞吐"的图形解，也就是 Goodput 最大的位置。

### 4.3 Warmup 与稳态

- **先热身再计数**：首次请求会触发 CUDA Graph 捕获、编译缓存、权重页载入、Python 层懒初始化，前几十个请求的延迟不具代表性，必须丢弃（genai-perf 有 `--warmup-request-count`，自写脚本要自己丢）。
- **测稳态而非瞬态**：压测时长要足够（分钟级），并保证发压端先于统计窗口开始、晚于统计窗口结束，避免"排队还没建立起来"或"尾部只剩长请求"的偏差。
- **多跑几轮取分布**：同配置至少 3 轮，报告波动范围；轮间差异大本身就是问题信号（碎片化、后台任务、温度降频）。

## 5. 压测工具实操：vllm bench 与 genai-perf

以下命令基于 vLLM 与 GenAI-Perf 的近期版本，具体 flag 以 `--help` 为准（两者的参数都在持续演进）。

### 5.1 起被测服务

```bash
# 压吞吐/延迟曲线时，先关掉前缀缓存，避免命中率污染结果（见第 6 节）
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --max-model-len 8192 \
  --no-enable-prefix-caching \
  --disable-log-requests
```

### 5.2 vllm bench serve：在线服务压测（最常用）

```bash
vllm bench serve \
  --backend vllm \
  --base-url http://localhost:8000 \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 256 \
  --num-prompts 512 \
  --max-concurrency 32 \
  --request-rate inf \
  --ignore-eos \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,95,99 \
  --save-result
```

要点：`--dataset-name random` + 固定长度钉死工作负载（换成 `sharegpt` 即真实分布）；`--ignore-eos` 钉死输出长度；`--percentile-metrics`/`--metric-percentiles` 让报告直接输出 TTFT/TPOT/ITL/E2E 的 P50/P95/P99。

**并发扫描画曲线**，套一层循环即可：

```bash
for c in 1 2 4 8 16 32 64 128 256; do
  vllm bench serve \
    --backend vllm --base-url http://localhost:8000 \
    --model meta-llama/Llama-3.1-8B-Instruct \
    --dataset-name random --random-input-len 1024 --random-output-len 256 \
    --num-prompts $((c * 16)) --max-concurrency ${c} --ignore-eos \
    --save-result --result-filename "sweep_c${c}.json"
done
```

### 5.3 vllm bench latency / throughput：离线单点基准

```bash
# 静态 batch 的端到端延迟（引擎内直跑，不走 HTTP）：适合测 kernel/配置改动
vllm bench latency \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --input-len 1024 --output-len 128 \
  --batch-size 8 \
  --num-iters-warmup 5 --num-iters 15

# 离线极限吞吐：一次性喂入全部请求，测 tokens/s 上限
vllm bench throughput \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --input-len 1024 --output-len 256 \
  --num-prompts 1000
```

三个子命令的分工：`latency` 测固定 batch 的单步性能（开发内环）、`throughput` 测离线产能上限、`serve` 测真实在线行为（含 HTTP、流式、排队、调度）——**对外报告只能用 `serve` 的数字**，前两者不含排队与并发调度，天然偏乐观。

### 5.4 genai-perf：跨引擎统一口径

NVIDIA 的 GenAI-Perf 走标准 OpenAI 接口压测，适合横向对比不同引擎（vLLM/TRT-LLM/SGLang）时统一度量口径：

```bash
genai-perf profile \
  -m meta-llama/Llama-3.1-8B-Instruct \
  --endpoint-type chat \
  --url http://localhost:8000 \
  --streaming \
  --synthetic-input-tokens-mean 1024 --synthetic-input-tokens-stddev 0 \
  --output-tokens-mean 256 \
  --extra-inputs ignore_eos:true \
  --concurrency 32 \
  --request-count 512 \
  --warmup-request-count 32
```

它会输出 TTFT / ITL / Request Latency / Output Token Throughput 等指标的完整分位数表。注意 `--streaming` 必须开——没有流式就没有 TTFT/ITL 可言（见下一节陷阱 4）。

💡 **提示**：横向对比引擎时，让**同一个客户端工具**压所有引擎，绝不要拿各引擎自带工具的自报数字互比——TTFT 从哪一刻起算、token 怎么数（tokenizer 不同）、是否含网络栈，各家口径都有差异。

## 6. 常见 Benchmark 陷阱

以下每一条都是真实世界里"3 倍加速"的常见来源：

1. **用 batch=1 比吞吐**。batch=1 下 Decode 完全 memory-bound，测出的是"单请求延迟"而不是"系统产能"；连续批处理引擎的优势恰恰在高并发下。反过来，**只报饱和吞吐、不报延迟**也是同一枚硬币的另一面。
2. **忽略输入/输出长度分布**。用 128 in / 2048 out 测出的"tokens/s"和 8192 in / 128 out 是两个世界（前者几乎全是 Decode，后者几乎全是 Prefill）。对比实验长度分布不一致，结论直接作废。
3. **前缀缓存污染结果**。压测数据集里大量请求共享前缀（同一 system prompt、数据集重复采样），开着 prefix caching 时 Prefill 大面积命中缓存，TTFT 好得虚假；换一批不重复的数据立刻打回原形。要么压测时 `--no-enable-prefix-caching`，要么用随机数据集，要么明确声明"测的就是含缓存命中的场景"并报告命中率。
4. **流式与非流式混比**。非流式接口只有 E2E 一个时间戳，"TTFT"要么测不了要么等于 E2E；拿 A 引擎流式的 TTFT 对比 B 引擎非流式的 E2E，属于指标错位。同理，客户端不消费流（或缓冲区攒批）也会把 ITL 测成锯齿。
5. **热身不足 / 时长不足**。把 CUDA Graph 捕获、编译、冷启动算进延迟；或只压 10 秒，队列还没进入稳态就出报告。
6. **输出长度不钉死**。不加 `ignore_eos`，两个引擎在同一数据集上生成长度不同（采样参数、tokenizer、模板差异），per-token 指标全部失真。
7. **客户端自己成为瓶颈**。单进程 Python 客户端在高并发下发不出足够压力，测出的"饱和吞吐"其实是客户端的；压测时要观察发压端 CPU 与连接数，必要时多进程/多机发压。

⚠️ **注意**：读别人的 benchmark 报告时，就按这七条清单反向审查：长度分布、并发条件、流式与否、缓存状态、warmup、输出钉死、发压端。七项写不全的报告，数字不必当真。

## 7. 瓶颈定位：从指标反推病因

压测出了"不达标"的指标之后，排查路径可以按指标归类成一张决策表：

| 症状 | first check | 常见病因 → 处方 |
|---|---|---|
| **TTFT 高** | 排队时间 vs Prefill 时间 | 排队长（`num_requests_waiting` 高涨）→ 并发超出容量：限流、加副本、PD 分离；Prefill 本身慢 → 输入太长：chunked prefill 防止长 Prefill 阻塞、开 prefix caching 吃共享前缀、算子层优化 |
| **TPOT/ITL 高** | batch 大小与显存带宽 | Decode 是 memory-bound：batch 拉太大每 token 分到的带宽变少 → 压 `max_num_seqs`；权重读取占大头 → 量化（W4/W8）减少搬运量；ITL 偶发突刺 → 看抢占次数与 Prefill 插队（chunked prefill 可平滑） |
| **吞吐上不去、GPU 利用率也低** | KV Cache 与调度配置 | `gpu_cache_usage_perc` 顶满、`num_preemptions` 增长 → KV Cache 容量瓶颈：提高 `gpu_memory_utilization`、量化 KV Cache、缩 `max_model_len`、加卡；cache 没满但 running 数封顶 → 调度参数卡住：`max_num_seqs` / `max_num_batched_tokens` 太小 |
| **吞吐上不去、GPU 利用率高** | 算力/带宽已饱和 | 已到硬件上限：量化、投机解码（降每 token 成本）、换更高带宽卡、水平扩容 |

三条主线值得展开：

- **TTFT 异常 ≠ Prefill 慢**。TTFT = 排队 + Prefill，绝大多数线上 TTFT 事故是**排队**（容量不足或长请求阻塞调度），而不是 Prefill 计算本身。所以第一步永远是拆开这两段——vLLM 的 metrics 里排队时间（`request_queue_time`）与 Prefill 时间是分开导出的。
- **TPOT 与 batch 的关系是结构性的**。Decode 每步要把全部权重和 KV Cache 从 HBM 读一遍，batch 内请求共享权重读取、分摊带宽——batch 越大总吞吐越高，但每请求的 TPOT 单调变差。这就是"吞吐与延迟对抗"在微观层面的机制（呼应第 1 章的 roofline 分析）。
- **KV Cache 容量决定并发上限**。能同时驻留的请求数 ≈ KV Cache 总块数 / 每请求平均块数。cache 用满后新请求排队、老请求被抢占重算，吞吐曲线提前封顶——此时任何 kernel 优化都无济于事，要么省 KV（量化、GQA 模型、缩上下文），要么加显存。

📌 **关键点**：面试答"如何优化推理服务"最忌上来就报菜名（量化、蒸馏、算子融合……）。正确姿势是先立指标（哪个指标不达标）、再定位（排队还是计算、算力还是带宽还是容量）、最后对症下药——上面这张表就是答题模板。

## 8. 推理引擎指标观测：vLLM 的 metrics 端点

压测工具看到的是"外部视角"，定位问题还需要引擎的"内部视角"。vLLM 在 OpenAI 兼容服务上暴露 Prometheus 格式的 `/metrics` 端点：

```bash
curl -s http://localhost:8000/metrics | grep -E "^vllm:" | head -30
```

关键指标按用途分组（指标名以所用版本为准，V0/V1 引擎间有增删）：

| 指标 | 含义 | 怎么用 |
|---|---|---|
| `vllm:num_requests_running` | 当前正在跑的请求数 | 封顶在 `max_num_seqs` 且 waiting 堆积 → 调度并发卡住 |
| `vllm:num_requests_waiting` | 排队中的请求数 | 持续 > 0 即容量不足，TTFT 事故的第一现场 |
| `vllm:gpu_cache_usage_perc` | KV Cache 块池使用率 | 长期接近 1.0 → 容量瓶颈，并发上限被 KV 卡死 |
| `vllm:num_preemptions_total` | 累计抢占次数 | 持续增长 → 显存压力大，正在"扔 KV 重算"，ITL 突刺来源 |
| `vllm:time_to_first_token_seconds` | TTFT 直方图 | 与压测端交叉验证；多实例下在 Prometheus 聚合分位数 |
| `vllm:time_per_output_token_seconds` | 每输出 token 时间直方图 | 服务端视角的 TPOT/ITL |
| `vllm:request_queue_time_seconds` | 请求排队时长 | 把 TTFT 拆成"排队 vs Prefill"的关键证据 |
| `vllm:prompt_tokens_total` / `generation_tokens_total` | 累计输入/输出 token 数 | rate() 之后就是实时吞吐，接 Grafana 看长期趋势 |
| `vllm:gpu_prefix_cache_hit_rate` | 前缀缓存命中率 | 压测时验证缓存是否污染结果（第 6 节陷阱 3） |

实践建议：

- **压测时同步抓取 metrics**：压测端只能看到延迟结果，`/metrics` 才能告诉你"为什么"——一边 sweep 并发一边记录 `gpu_cache_usage_perc` 与 `num_requests_waiting`，拐点出现的原因（KV 满了还是调度满了）当场可判。
- **生产环境接 Prometheus + Grafana**：vLLM 官方提供了 Grafana dashboard 示例；告警建议盯 waiting 队列长度、preemption 速率、TTFT/TPOT 直方图分位数三类。
- **直方图聚合分位数**：多副本部署时用 `histogram_quantile(0.99, sum(rate(vllm:time_to_first_token_seconds_bucket[5m])) by (le))` 这类查询合并各实例分桶——这正是第 2 节"分位数不能直接平均"的正确工程解。

## 📝 总结

- **指标体系**：TTFT（排队 + Prefill）、ITL（逐 token 间隔）、TPOT（请求内 ITL 均值）、$T_{\text{E2E}} = \text{TTFT} + \text{TPOT} \times (N_{\text{out}}-1)$；吞吐分请求/输出 token/总 token 三种口径；Goodput = 满足 SLO 的吞吐，把"延迟-吞吐对抗"内建进单一指标。
- **报分位数不报均值**：延迟分布重尾，均值既不代表典型也不代表最差；P99 决定用户对"卡"的记忆；分位数聚合要靠直方图。
- **SLO 分场景**：在线对话约束 TTFT/TPOT 的 P99（对齐人的感知与阅读速度）；批处理约束吞吐与单位成本——两者的调参方向相反。
- **方法论**：钉死长度分布与输出长度（ignore_eos）、声明到达模式、并发 sweep 画 latency-throughput 曲线、运营点选拐点、warmup 后测稳态。
- **工具**：`vllm bench serve/latency/throughput` 各司其职（对外只报 serve）；genai-perf 统一跨引擎口径；横向对比必须同一客户端。
- **七大陷阱**：batch=1 比吞吐、长度分布不一致、prefix cache 污染、流式与非流式混比、热身/时长不足、输出长度不钉死、发压端瓶颈。
- **瓶颈定位**：TTFT 高先拆排队 vs Prefill；TPOT 高看 batch 与显存带宽；吞吐封顶分"KV 容量/调度参数"与"硬件饱和"两条路——先立指标、再定位、后开方。
- **观测**：vLLM `/metrics` 的 waiting/running、`gpu_cache_usage_perc`、preemptions、延迟直方图是内部视角四件套，压测与观测必须同时开。

## ✅ 自我检验清单

**1. 能给 TTFT/ITL/TPOT/E2E 下准确定义并写出四者的关系式**

<details>
<summary>参考答案</summary>

TTFT = 排队时间 + Prefill 时间，是用户"等它开口"的体感；ITL 是流式输出中相邻两个 token 的间隔，一个请求产生 $N_{\text{out}}-1$ 个样本，只有它能暴露卡顿突刺；TPOT $= \frac{T_{\text{E2E}} - \text{TTFT}}{N_{\text{out}}-1}$，是 ITL 的请求内均值，均值会抹平突刺；四者满足 $T_{\text{E2E}} = \text{TTFT} + \text{TPOT} \times (N_{\text{out}}-1)$。所以严谨的压测报告要同时给 TPOT 和 ITL 的分位数。（对应正文第 1.1 节）

</details>

**2. 能说出吞吐的三种口径并解释 Goodput 为什么必要**

<details>
<summary>参考答案</summary>

三种口径：请求吞吐（requests/s）、输出 token 吞吐（output tokens/s）、总 token 吞吐（input + output，长输入场景显得虚高）——混用口径是事故之源。Goodput 是**满足 SLO 的**请求（或 token）吞吐（DistServe 推广的概念）：延迟与吞吐天然对抗，batch 拉满、吞吐翻倍但 p99 TPOT 全部超标的系统 Goodput 可能是零——它把"报吞吐必须带延迟约束"做成了一个指标。（对应正文第 1.2 节；另见 Q2）

</details>

**3. 能给出"报分位数不报均值"的三层理由与分位数聚合的正确做法**

<details>
<summary>参考答案</summary>

三层理由：推理延迟分布重尾（排队、抢占、Prefill 插队、GC），均值被长尾拉高又掩盖长尾，既不代表 P50 也不代表 P99；用户按"最差的那次"记忆体验，一次撞上 P99 就是一次"卡死"；均值可以靠塞短请求刷低，P99 刷不了。聚合上，分位数不能跨机器/跨窗口直接平均（P99 的均值不是全局 P99），要么网关层集中采样原始延迟，要么用直方图在查询侧合并分桶后再算分位数。（对应正文第 2 节）

</details>

**4. 能分场景写出 SLO 并解释两类场景的调参方向为何相反**

<details>
<summary>参考答案</summary>

在线对话约束延迟分位数：TTFT 要求亚秒级 P99，TPOT 对齐人的阅读速度设在几十到一百毫秒/token，典型写法 `TTFT P99 < 1s 且 TPOT P99 < 100ms，SLO 达成率 > 99%`。批处理没有人等首 token，核心指标是总 token 吞吐与单位成本（元/百万 token），延迟放宽到任务级。同一套引擎，在线要"限并发、保尾延迟"，离线要"塞满卡、保吞吐"——方向完全相反，所以答优化题先反问场景与 SLO。（对应正文第 3 节；另见 Q3）

</details>

**5. 能画出 latency-throughput 曲线并说明运营点为何选拐点**

<details>
<summary>参考答案</summary>

并发从 1 倍增扫到饱和，每档记录吞吐与延迟分位数。曲线分三段：线性区（并发翻倍吞吐近似翻倍、延迟平稳，GPU 没吃饱）、拐点（吞吐增速放缓、延迟开始陡增，batch 效应吃满）、饱和区（吞吐封顶，加并发只是把排队时间加进 TTFT）。运营点选拐点附近：往左浪费 GPU，往右吞吐几乎不涨、纯用尾延迟换账面并发——拐点就是"SLO 约束下最大化吞吐"的图形解，即 Goodput 最大的位置。（对应正文第 4.2 节；另见 Q1）

</details>

**6. 能列出一次可信压测必须钉死的条件**

<details>
<summary>参考答案</summary>

- **长度分布**：固定长度或真实分布（如 ShareGPT），报告必须写明——Prefill 代价 ∝ 输入长度、Decode 代价 ∝ 输出长度；
- **输出长度强制**：`--ignore-eos` 或钉死 `max_tokens`，否则 EOS 早晚不同、比较不成立；
- **到达模式**：一次性全发 / 泊松到达 / 固定并发，三选一并写明；
- **热身与稳态**：丢弃触发 CUDA Graph 捕获、编译缓存的前几十个请求，压分钟级稳态窗口；
- **多轮**：同配置至少 3 轮报波动范围，轮间差异大本身就是问题信号。（对应正文第 4.1/4.3 节）

</details>

**7. 能说明 vllm bench 三个子命令的分工与"对外只能报 serve"的原因**

<details>
<summary>参考答案</summary>

`latency` 在引擎内直跑固定 batch 的单步性能，适合开发内环测 kernel/配置改动；`throughput` 一次性喂入全部请求测离线产能上限；`serve` 走 HTTP 测真实在线行为，含流式、排队与并发调度。前两者不含排队与调度、天然偏乐观，所以对外报告只能用 serve 的数字。横向对比引擎要用同一个客户端（如 genai-perf 走标准 OpenAI 接口）压所有引擎——TTFT 起算点、token 计数、是否含网络栈各家口径不同，自报数字不可互比。（对应正文第 5 节）

</details>

**8. 能背出七大 Benchmark 陷阱并用它反向审查报告**

<details>
<summary>参考答案</summary>

① batch=1 比吞吐（测的是单请求延迟不是系统产能，只报饱和吞吐不报延迟是同一枚硬币的另一面）；② 输入/输出长度分布不一致；③ prefix caching 命中污染 TTFT（压测要关缓存、用随机数据或声明命中率）；④ 流式与非流式混比（非流式没有 TTFT/ITL 可言）；⑤ 热身/时长不足；⑥ 输出长度不钉死；⑦ 客户端自己成为发压瓶颈。读别人的报告按这七条反向审查，写不全的数字不必当真。（对应正文第 6 节）

</details>

**9. 能按症状分类给出瓶颈定位路径**

<details>
<summary>参考答案</summary>

TTFT 高：先拆排队 vs Prefill——绝大多数线上事故是**排队**（waiting 堆积 → 限流、加副本、PD 分离），Prefill 本身慢才用 chunked prefill / prefix caching / 算子优化。TPOT/ITL 高：Decode 是 memory-bound，batch 拉太大每 token 分到的带宽变少 → 压 `max_num_seqs`、量化减少权重搬运；ITL 突刺看抢占与 Prefill 插队。吞吐上不去分两路：GPU 利用率低是 KV Cache 顶满或调度参数（`max_num_seqs`/`max_num_batched_tokens`）卡住；利用率高是硬件饱和 → 量化、投机解码、扩容。总纲：先立指标、再定位、后开方。（对应正文第 7 节；另见 Q4）

</details>

**10. 能列出 vLLM /metrics 里定位问题的关键指标及各自判读**

<details>
<summary>参考答案</summary>

`num_requests_waiting` 持续 > 0 即容量不足，是 TTFT 事故的第一现场；`gpu_cache_usage_perc` 长期接近 1.0 说明并发上限被 KV Cache 卡死；`num_preemptions_total` 持续增长意味着正在"扔 KV 重算"，是 ITL 突刺来源；`request_queue_time_seconds` 是把 TTFT 拆成"排队 vs Prefill"的关键证据；`gpu_prefix_cache_hit_rate` 用于验证压测是否被缓存污染。压测时同步抓取 metrics，一边 sweep 并发一边看 cache 与 waiting，拐点出现的原因当场可判。（对应正文第 8 节）

</details>

## 💼 高频面试题解析

以下题目均出自本仓库 `docs/interview/` 收录的真实面经。

### Q1：在高并发条件下，如何对推理服务进行压力测试以确定其能承受的最大并发量？测试过程中需要重点监控哪些指标？

**来源**：Teleai-AI-Infra-实习-一面

**答题要点**：核心方法是**并发扫描 + SLO 判据**：钉死输入输出长度分布与输出长度（ignore_eos），并发从 1 倍增扫描，每档跑到稳态（先 warmup），画 latency-throughput 曲线；"最大并发量"不是吞吐封顶点，而是 **P99 TTFT/TPOT 仍满足 SLO 的最大并发**（即 Goodput 最大点，呼应第 4 节）。监控两侧：客户端侧 TTFT/TPOT/ITL/E2E 的 P50/P95/P99 与错误率，服务端侧 `num_requests_waiting`、`gpu_cache_usage_perc`、preemption 次数、GPU 利用率（呼应第 8 节）——waiting 开始堆积或 cache 顶满，就是容量边界的物理信号。

### Q2：吞吐量的定义是什么？在推理场景中如何衡量／计算？

**来源**：卓驭-AI-Infra-实习、传音-AI-Infra-校招-一面

**答题要点**：先给三种口径——requests/s、output tokens/s、total tokens/s——并说明必须声明口径（长输入场景 total 口径虚高，呼应第 1.2 节）。计算方式：稳态窗口内完成的 token 数 / 窗口时长；用 `vllm bench throughput` 测离线上限、`vllm bench serve` 测在线真实值。加分项：指出吞吐必须带延迟约束才有意义，引出 Goodput；再补一句吞吐的物理上限来源——Decode 是 memory-bound，吞吐随 batch 增长直到 KV Cache 容量或带宽饱和（呼应第 7 节）。

### Q3：设计高吞吐、低延迟的模型推理服务时，架构层面与工程层面需要重点考虑哪些问题？

**来源**：网易-AI-Infra-校招

**答题要点**：先立 SLO（在线还是离线，TTFT/TPOT 的 P99 目标，呼应第 3 节），承认吞吐与延迟对抗、目标是 SLO 约束下最大化 Goodput。架构层：连续批处理引擎选型、在线离线分池、PD 分离隔离 Prefill 干扰、网关限流与副本扩缩容。工程层：chunked prefill 平滑 ITL、prefix caching 吃共享前缀、量化降 Decode 带宽压力、KV Cache 容量规划（`gpu_memory_utilization`）、以及压测验证与 metrics 观测闭环（呼应第 5、7、8 节）。

### Q4：线上服务推理场景下如何提升吞吐量？

**来源**：太初-AI-Infra-实习-一面-1

**答题要点**：按第 7 节的定位表答"先诊断后开方"：若 KV Cache 顶满 → 提高显存配比、KV 量化、缩短 max_model_len；若调度参数卡住 → 调大 `max_num_seqs`/`max_num_batched_tokens`；若硬件已饱和 → 权重量化、投机解码、扩容。同时声明约束：所有提吞吐手段几乎都以 TTFT/TPOT 变差为代价，提升幅度要在 SLO 内衡量（Goodput 口径），并用并发扫描曲线前后对比验证（呼应第 4 节）。

### Q5：是否使用 vLLM 部署过模型？实测吞吐量为多少？

**来源**：小米-AI-Infra-校招

**答题要点**：这题考的不是背一个数字，而是**你会不会报数**：正确回答范式是"模型 X / 卡型 Y / 输入输出长度分布 Z / 并发 C / 是否流式 / 是否开 prefix caching 下，output tokens/s 为 N，P99 TTFT/TPOT 为 M"——把第 4 节的实验条件和第 6 节的陷阱清单反过来用。能主动说出用 `vllm bench serve` 做并发扫描、报告拐点位置与对应延迟，远比一个孤立的"几千 tokens/s"可信。

### Q6：某 Agent 推理流程需依次调用 3 个外部工具，高并发下端到端延迟偏高，你会采取哪些工程手段降低整体延迟？

**来源**：MiniMax-AI-Infra-一面

**答题要点**：先分解 E2E：多轮 LLM 调用的 TTFT/TPOT + 工具执行 + 串行依赖。LLM 侧：多轮共享前缀极多，prefix caching 收益巨大；流式 + 提前解析（边生成边解析工具调用参数）压缩关键路径；限并发保 P99（呼应第 3、7 节）。链路侧：可并行的工具调用并行化、工具结果缓存、投机执行。观测侧：为每一跳打点，先用分位数找到贡献最大的一跳再优化——本质还是"先测量、再定位、后优化"的方法论（呼应第 7 节）。

### Q7：优化一个部署在云端的推理服务，目标是提升单卡吞吐并降低响应延迟，你会如何展开？

**来源**：OPPO-云-AI-Infra-实习-一面

**答题要点**：展示完整闭环：① 建基线——固定工作负载压测出 latency-throughput 曲线与各分位延迟（呼应第 4 节）；② 定位——用 metrics/profiler 判断排队、容量、带宽还是算力瓶颈（呼应第 7、8 节）；③ 优化——按病因选批处理策略、量化、缓存、算子优化；④ 回归——同一压测配置复测，确认吞吐提升且 P99 不超 SLO，并把该配置固化成性能回归门禁（本章概览 9.5 节的方向）。强调"每一步优化都要过同一把尺子"，避免第 6 节的陷阱式对比。
