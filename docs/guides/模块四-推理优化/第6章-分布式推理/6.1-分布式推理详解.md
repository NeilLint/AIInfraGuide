一张 80GB 的 GPU，连 FP16 的 70B 模型权重（140GB）都装不下，更别提 KV Cache。这时"分布式"就不再是训练团队的专利——推理也必须把模型拆到多卡甚至多机上。但如果你直接把训练里学的 3D 并行搬过来，会发现目标函数完全变了：训练优化的是"每秒处理多少样本、梯度同步别拖后腿"，推理优化的是"首 Token 多快出来（TTFT）、后续每个 Token 间隔多短（TPOT）、单位成本吞吐多高"。这一节把推理场景下的 TP、PP、DP、EP 逐个讲透：怎么切、通信发生在哪、对延迟和吞吐分别是什么影响，最后落到 vLLM 多机部署的可运行命令和一套完整的显存估算推演。

## 1. 推理并行为什么不能照搬训练并行

TP、PP、DP、EP 这些名词训练和推理是共用的，切分数学也一样，但三个根本差异决定了选型逻辑完全不同：

**第一，推理没有梯度同步。**训练里 DP 的代价是每步一次全量梯度 AllReduce，通信量与参数量同阶；推理的 DP 副本之间**零通信**，天然线性扩展。训练里让人头疼的"通信计算重叠藏梯度同步"在推理里根本不存在——推理的通信全部来自模型本身被切开后的激活聚合（TP 的 AllReduce、PP 的点对点、EP 的 All-to-All），而且全部在**关键路径**上，藏无可藏。

**第二，推理是延迟敏感的在线服务。**训练是吞吐型批处理，一个 step 慢 10ms 没人在意；推理的 Decode 每生成一个 Token 都要走完一遍完整前向，任何附加在单步前向上的通信延迟都会**逐 Token 累积**，直接体现在用户看到的打字速度（TPOT）上。这就是为什么推理对"每层几次通信、每次多大、走什么链路"锱铢必较。

**第三，显存的大头从优化器状态变成了 KV Cache。**训练显存 = 权重 + 梯度 + 优化器状态 + 激活，Adam 混合精度下光"权重+梯度+优化器"就要约 16 倍参数量的字节数；推理显存 = 权重 + KV Cache + 少量峰值激活。权重是固定的，激活是瞬态的，**唯一随负载增长的就是 KV Cache**——并发越高、上下文越长，它吃得越多。所以推理并行的一个隐藏目标是：切完权重后，给每张卡留出尽量大的 KV Cache 池，因为 KV 池大小直接决定能拼多大的 Batch，而 Decode 是 Memory Bound，Batch 大小几乎就是吞吐（第 1 章的结论）。

| 📊 维度 | 训练并行 | 推理并行 |
|---|---|---|
| 优化目标 | 单位时间处理的样本数、收敛 | TTFT / TPOT / 单位成本吞吐 |
| 梯度同步 | 有（DP 的主要通信） | 无 |
| 通信位置 | 部分可与反向计算重叠 | 全在前向关键路径上 |
| 显存大头 | 权重 + 梯度 + 优化器状态 + 激活 | 权重 + KV Cache |
| 负载形态 | 静态、规则的大 Batch | 动态到达、长度参差的请求流 |
| 失败容忍 | 可从 checkpoint 重来 | 在线服务，要求高可用 |

📌 **关键点**：推理并行选型的第一性原理是三个问题——**权重装不装得下（显存容量）、单 Token 延迟能不能达标（通信在关键路径上的开销）、KV Cache 池还剩多少（并发上限）**。下面每种并行策略都用这三个问题来审视。

## 2. 张量并行（TP）：切头、切 MLP 与每层两次 AllReduce

TP 是推理中最常用的层内并行：把每一层的权重矩阵切到 $N$ 张卡上，$N$ 张卡协同完成一层的计算。它同时解决"权重装不下"和"单请求太慢"两个问题——每张卡只算 $1/N$ 的矩阵乘，Prefill 和 Decode 的计算时间都近似除以 $N$。代价是卡间必须频繁同步。

### 2.1 怎么切：Attention 按头、MLP 先列后行

沿用 Megatron-LM 的经典切法。**MLP** 的计算是 $Y = \mathrm{GeLU}(XA)\,B$（SwiGLU 结构同理，gate/up 两个矩阵都按 $A$ 的方式切）：

- 第一个矩阵 $A$ **按列切**：$A = [A_1, A_2]$，每张卡计算 $\mathrm{GeLU}(XA_i)$。列切的输出天然是完整结果的一个分片，且 GeLU 逐元素作用在各自分片上**不需要任何通信**。
- 第二个矩阵 $B$ **按行切**：$B = \begin{bmatrix} B_1 \\ B_2 \end{bmatrix}$，每张卡计算部分和 $Y_i = \mathrm{GeLU}(XA_i)\,B_i$，最后 **AllReduce 求和**得到 $Y = Y_1 + Y_2$。

顺序不能反：如果先行切，部分和必须先求和才能过 GeLU（非线性函数不满足 $\sigma(a+b) = \sigma(a)+\sigma(b)$），中间就要多一次通信。**先列后行**让两个矩阵乘之间零通信，整个 MLP 只在出口处一次 AllReduce。

**Attention** 天然可切——多头本来就是独立计算的。$W_Q, W_K, W_V$ 按列切（等价于按头分组，每卡分到 $h/N$ 个头），各卡独立完成自己头上的 attention；输出投影 $W_O$ 按行切，出口处一次 AllReduce 求和。

于是**每层 Transformer 前向恰好两次 AllReduce**：Attention 出口一次、MLP 出口一次。（训练时反向传播对输入梯度还需两次，所以训练每层每迭代是 4 次；推理只有前向的 2 次。）

💡 **提示**：GQA 模型的 KV 头数少于 Q 头数（如 Llama-3.1-70B 有 64 个 Q 头、8 个 KV 头）。TP 度不超过 KV 头数时，KV Cache 也均匀切分（TP=4 时每卡 2 个 KV 头）；TP 度超过 KV 头数时，KV 头要在多卡间**复制**，KV Cache 的切分收益就打了折扣——这是"TP 度不是越大越好"的原因之一。

### 2.2 通信量与 TPOT 的账

每次 AllReduce 同步的是激活张量，大小为 $b \times s \times h$（batch × 序列长 × 隐层维度）。Ring AllReduce 下每卡收发数据量约为张量大小的 $2\frac{N-1}{N}$ 倍。关键在于 Prefill 和 Decode 的形态完全不同：

- **Prefill**：$s$ 是整个 prompt 长度，单次消息可达几十上百 MB，通信是**带宽敏感**的。
- **Decode**：$s = 1$，单次消息只有 $b \times h \times 2$ 字节（FP16）——batch 32、$h=8192$ 时仅 512KB。这么小的消息，传输时间趋近于零，开销主要是**每次操作的固定延迟**（kernel 发射、NCCL 协议开销、同步等待），即**延迟敏感**。

| 📊 | Prefill 的 AllReduce | Decode 的 AllReduce |
|---|---|---|
| 单次消息大小 | $b \times s \times h$，几十~上百 MB | $b \times h$，百 KB 量级 |
| 开销主导项 | 带宽（传输时间） | 延迟（固定开销 × 次数） |
| 发生频率 | 每请求一轮（$2L$ 次） | 每 Token 一轮（$2L$ 次/Token） |
| 主要伤害 | TTFT | TPOT |
| 对链路的诉求 | 高带宽 | 低延迟 |

Decode 每生成一个 Token，要执行 $2L$ 次 AllReduce（$L$ 为层数）。以 80 层的 70B 模型为例，每个 Token 的关键路径上有 **160 次同步点**。做个量级推演：即使单次小消息 AllReduce 在 NVLink 上只有约 10μs 量级的固定开销，160 次也会给每个 Token 增加毫秒级的纯通信时间——而 Decode 单步计算本身往往也就是十几到几十毫秒。这就是 TP 的基本面：**计算时间除以 N，但要付出一笔不随 N 减小、反而随 N 略增的每层通信税**。TP 度存在收益递减点，超过之后 TPOT 不降反升。

### 2.3 为什么 TP 通常不出节点

把上面的账放到跨节点链路上就明白了。节点内 8 卡之间走 NVLink/NVSwitch，H100 每卡聚合带宽 900GB/s，延迟亚微秒级；跨节点走 InfiniBand，NDR 单端口 400Gb/s（50GB/s），延迟微秒级。带宽差一个数量级以上，延迟同样差一个量级——而 Decode 的小消息 AllReduce 恰恰是延迟敏感的，每 Token 160 次同步全部乘上这个放大系数，TPOT 会明显劣化；Prefill 的大消息则直接撞上带宽墙。

所以工程惯例是：**TP 度 ≤ 单节点 GPU 数（通常 8），跨节点用 PP 或 DP 扩展**。vLLM 官方文档给出的建议正是"TP 设为每节点卡数、PP 设为节点数"。

⚠️ **注意**：这条惯例的本质是"TP 不出**高速互联域**"。在 GB200 NVL72 这类机架级 NVLink 域（72 卡同域）上，"节点"边界被 NVLink 域重新定义，TP 可以切得更大——判断标准始终是链路，不是机箱。

## 3. 流水线并行（PP）：吞吐型的跨节点扩展

PP 把模型**按层**切成 $K$ 段（stage），每段放在一张卡或一组卡上，请求像流水线上的工件一样依次流过。它和 TP 的通信画像截然相反：

- 相邻 stage 之间只传**一份隐层激活**（$b \times s \times h$），且是点对点 send/recv，不是集合通信；
- 每个 Token 全程只需 $K-1$ 次传递，而不是每层都通信。

通信次数少、单次量小、点对点——这正好是跨节点链路能承受的形态，所以 **PP 是跨节点扩展的首选**。

但 PP 有两个先天特性必须认清：

**第一，PP 不降低单 Token 延迟。**一个 Token 还是要顺序穿过所有层，只是这些层分布在不同卡上，还多了 $K-1$ 次跨卡传递。TTFT 和 TPOT 相对单卡（假设装得下）不会变好，甚至略差。PP 换来的是"装得下更大的模型"和"多个 micro-batch 同时在不同 stage 上流动"带来的**吞吐**。

**第二，流水线气泡（Bubble）。**同一时刻只有塞满 $K$ 个 micro-batch，所有 stage 才都有活干；流水线填充和排空阶段总有 stage 空转。训练里靠攒大 batch 切 micro-batch 来压 bubble，推理里的解法则是 **continuous batching 天然供给了源源不断的"工件"**：不同请求、同一请求的不同 Decode 步，都可以作为独立的 micro-batch 交错填进流水线。vLLM 的 PP 实现正是为每个 stage 维持多个 in-flight micro-batch，让上一个 batch 的 stage-2 计算与下一个 batch 的 stage-1 计算重叠。

用一张时序表看 2 段流水线（PP=2）上 4 个 micro-batch 的交错：

| ⏱️ 时刻 | Stage 1（前 40 层） | Stage 2（后 40 层） |
|---|---|---|
| $t_1$ | mb1 | 空转（填充期 bubble） |
| $t_2$ | mb2 | mb1 |
| $t_3$ | mb3 | mb2 |
| $t_4$ | mb4 | mb3 |
| $t_5$ | 空转（排空期 bubble） | mb4 |

稳态（$t_2 \sim t_4$）时两个 stage 都满载；bubble 只出现在填充和排空的边缘。continuous batching 的作用就是让"排空"几乎永不发生——上一波 micro-batch 还没流完，新的请求和新的 Decode 步已经补进来了。只有请求断流（低负载）时，这张表退化成一列有活、一列空转。

这也揭示了 PP 与 continuous batching 交互的微妙之处：

- **高负载**时请求充足，流水线始终满载，bubble 被摊薄，PP 的吞吐扩展接近线性；
- **低负载**时在飞请求少，填不满 $K$ 个 stage，bubble 直接暴露为 GPU 空转——此时 PP 的资源利用率明显差于同等卡数的 TP 或 DP 副本。

| 📊 维度 | TP | PP |
|---|---|---|
| 切分方式 | 层内切矩阵（横着切每一层） | 按层切段（竖着切模型） |
| 通信模式 | 每层 2 次 AllReduce（集合通信） | 每 stage 边界 1 次点对点 |
| 通信频率 | 高（$2L$ 次/Token） | 低（$K-1$ 次/Token） |
| 对链路要求 | 极高，需 NVLink 域内 | 宽松，可跨节点 |
| 单 Token 延迟 | 近似除以 $N$（有通信税） | 不变或略增 |
| 吞吐 | 提升 | 满载时近线性提升 |
| 短板 | 通信税随 N 增长、不出节点 | Bubble、低负载利用率差 |

📌 **关键点**：组合原则一句话——**节点内 NVLink 用 TP 消化显存与延迟，跨节点用 PP 消化容量，两者相乘覆盖总卡数**。例如 2 机 16 卡部署 405B：`TP=8 × PP=2`。

## 4. 数据并行与副本扩展：横向扩吞吐与路由

当单个引擎实例（不管内部是 TP 还是 TP×PP）已经满足延迟要求、瓶颈只剩吞吐时，最朴素也最有效的手段是**复制整个引擎**——推理 DP。副本之间无任何通信，加一份副本就多一份吞吐，唯一的新问题是**路由**：请求发给谁？

- **轮询 / 最少连接**：无状态，简单可靠，适合请求长度均匀的场景。
- **负载感知**：按各副本的在飞请求数、KV Cache 水位调度，避免长请求把某个副本堵死。
- **前缀感知（prefix-aware / cache-aware）**：把带相同前缀（同一 system prompt、同一多轮会话）的请求路由到同一副本，最大化 Prefix Cache 命中率——SGLang Router 和 NVIDIA Dynamo 的 KV-aware routing 都属于这一类。路由器从"无状态分流器"演化成了"带全局缓存视图的调度器"。

工程形态上，DP 可以由外部组件承担（Kubernetes + 网关、vLLM production-stack 的 router），也可以由引擎内建：新版 vLLM 提供 `--data-parallel-size`，在 MoE 场景下尤其重要——**Attention 部分做 DP、专家部分做 EP**，多个 DP rank 的 Token 汇聚到同一组专家上做大 batch 计算（下一节展开）。

💡 **提示**：DP 副本各自持有完整权重，显存成本随副本数线性增长。它回答的是"吞吐不够"，回答不了"装不下"和"太慢"——三个问题对症下药，不要拿 DP 去救显存。

## 5. MoE 推理与大 EP

MoE 模型（如 DeepSeek-V3：每层 256 个路由专家 + 1 个共享专家，每 Token 激活 top-8）把"装不下"推到了极致：总参数 671B，但每个 Token 只用约 37B。如果对专家继续用 TP 切，每个专家本来就不大，切碎后矩阵乘的规模太小，GPU 利用率极低。**专家并行（EP）**的思路是：专家不切，**整只**分布到不同 GPU 上，每张卡持有一部分专家。

计算流程由两次 **All-to-All** 集合通信支撑：

1. **Dispatch**：每张卡上的 Token 经过路由器打分后，按 top-k 结果被发送到持有对应专家的卡上——每张卡给每张卡发的内容都不同，这正是 All-to-All 的语义；
2. 各卡在本地专家上完成 FFN 计算；
3. **Combine**：结果按原路 All-to-All 送回，加权求和。

**为什么推理要"大 EP"？**一笔简单的账：设专家总参数为 $P_{\text{exp}}$，则每卡专家权重占用为

$$
M_{\text{expert/GPU}} = \frac{P_{\text{exp}} \times \text{bytes}}{\text{EP 度}}
$$

EP 从 8 扩到 64，每卡专家权重直接降 8 倍——对专家参数占绝对大头的 MoE 模型（DeepSeek-V3 的 671B 里路由专家占了绝大部分），这意味着每卡腾出几十 GB 显存，全部变成 KV Cache 池和更大的 batch。同时每个专家收到的是**全 EP 域汇聚来的 Token**，batch 足够大才能把专家的矩阵乘喂饱。DeepSeek-V3 技术报告给出的生产部署是：Prefill 阶段最小部署单元 4 节点 32 卡（Attention 做 TP4+DP、MoE 做 **EP32**）；Decode 阶段最小部署单元 40 节点 320 卡（MoE 做 **EP320**，接近每卡一个专家）。支撑这种规模 All-to-All 的是专门优化的通信库（DeepSeek 开源的 DeepEP），跨节点走 RDMA、节点内走 NVLink。

大 EP 带来一个新麻烦：**专家负载不均**。路由是数据相关的，真实流量里总有"热点专家"被高频命中，持有它的 GPU 成为木桶短板，其他卡等它。工程对策：

- **冗余专家（Redundant Experts）**：为高负载专家在多张卡上维护副本，把热点流量摊开；DeepSeek-V3 按线上统计负载周期性地重排冗余专家的放置。
- **EPLB（Expert Parallelism Load Balancer）**：DeepSeek 开源的放置算法，依据负载估计生成专家到 GPU 的均衡映射，配合分层/全局两种策略。
- **容量因子与丢弃**：限制单专家单步接收的 Token 上限，超出部分走共享专家或残差路径（训练期手段，推理侧慎用，影响质量）。

📌 **关键点**：大 EP 的本质是一笔交换——**用两次 All-to-All 的通信成本，换每卡权重占用的大幅下降和专家计算的规模效应**。这笔账只在高并发下划算：并发不足时专家喂不饱，All-to-All 的固定开销反而成为负担。

## 6. 多机部署实操：vLLM 与 Ray 集群

vLLM 的多机执行靠 Ray 编排：Ray 集群负责发现节点、按 Placement Group 把 worker 进程钉到各节点的 GPU 上，NCCL 负责实际的张量通信。以下命令基于 vLLM 官方分布式部署文档（参数以你所用版本 `vllm serve --help` 为准）。

**单机多卡（TP=4，跑 70B）**——不需要 Ray，vLLM 默认用多进程后端：

```bash
vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 8192
```

**两机 16 卡（TP=8 × PP=2，跑 405B）**——先拉起 Ray 集群，再在头节点启动 vLLM：

```bash
# 步骤 1：头节点上
ray start --head --port=6379

# 步骤 2：每个工作节点上（HEAD_IP 换成头节点内网 IP）
ray start --address='HEAD_IP:6379'

# 步骤 3：任一节点验证集群资源（应能看到 16 张 GPU）
ray status

# 步骤 4：头节点上启动服务，TP×PP 必须等于总卡数
vllm serve meta-llama/Llama-3.1-405B-Instruct \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 2 \
  --distributed-executor-backend ray
```

vLLM 仓库还提供 `examples/online_serving/run_cluster.sh`，用同一份 Docker 镜像一键拉起头/工作节点，保证多机环境一致——官方推荐的生产做法。

**部署后验证**——两条命令确认并行切分真的生效了：

```bash
# 冒烟测试：确认服务端到端可用
curl http://HEAD_IP:8000/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "meta-llama/Llama-3.1-405B-Instruct",
       "prompt": "解释一下张量并行", "max_tokens": 32}'

# 观察各卡显存与利用率：权重占用应约等于 总权重/(TP×PP)，
# 各卡数值接近说明切分均匀；Decode 压测时利用率应同步起伏
watch -n 1 "nvidia-smi --query-gpu=index,memory.used,utilization.gpu --format=csv"
```

两个典型异常形态：某张卡显存显著高于其余（切分不均或该卡还跑了别的进程）；GPU 利用率轮流起伏而非同步起伏（PP stage 间在互相等待，检查 micro-batch 并发与负载是否足够填满流水线）。

**常用环境变量与排错**：

```bash
# 多网卡机器上显式指定通信网卡与本机 IP，避免 NCCL/Gloo 选错网卡
export NCCL_SOCKET_IFNAME=eth0
export GLOO_SOCKET_IFNAME=eth0
export VLLM_HOST_IP=<本机内网IP>

# 通信 hang 住时打开 NCCL 日志定位
export NCCL_DEBUG=TRACE

# 部署前检查节点内 GPU 拓扑：NV# 表示 NVLink 直连，PIX/PHB 表示走 PCIe
nvidia-smi topo -m
```

三类高频故障：（1）多机 hang 在启动——通常是网卡选择错误或防火墙拦了 NCCL 端口；（2）`ray status` 看不到全部 GPU——工作节点没入集群或版本不一致；（3）跨节点吞吐远低于预期——TP 被错误地切到了节点间（检查 TP/PP 与节点的映射），或 IB/RoCE 没启用 GPUDirect RDMA。

## 7. 显存估算：70B 模型 4 卡 TP 完整推演

面试和容量规划都绕不开这道算术题。显存构成三项：

$$
M_{\text{总}} = M_{\text{权重}} + M_{\text{KV Cache}} + M_{\text{激活及杂项}}
$$

**权重**：参数量 × 每参数字节数，再除以 TP 度。**KV Cache 每 Token**（GQA 模型）：

$$
M_{\text{KV/token}} = 2 \times L \times n_{\text{kv}} \times d_{\text{head}} \times \text{bytes}
$$

其中 2 代表 K 和 V 两份，$L$ 层数，$n_{\text{kv}}$ KV 头数，$d_{\text{head}}$ 每头维度。**激活**在推理中是瞬态的，峰值近似与 `max_num_batched_tokens × hidden` 同阶（逐层复用缓冲），vLLM 启动时会实际 profile 一次峰值，再把剩余显存全部划给 KV 块池。

**完整推演：Llama-3.1-70B，4 × A100 80GB，TP=4，FP16。**模型配置：$L=80$，$h=8192$，64 个 Q 头、$n_{\text{kv}}=8$，$d_{\text{head}}=128$。

1. **权重**：$70\text{B} \times 2\text{B} = 140\,\text{GB}$，TP=4 均摊后每卡 $35\,\text{GB}$。
   （顺带回答"为什么不能 TP=2"：$140/2 = 70\,\text{GB}$，逼近 80GB 单卡物理上限，KV Cache 几乎没有生存空间，所以 80GB 卡上 70B FP16 的最小合理 TP 就是 4。）
2. **KV Cache 每 Token（全模型）**：$2 \times 80 \times 8 \times 128 \times 2\text{B} = 320\,\text{KB}$。
   TP=4 时 8 个 KV 头均分到 4 卡（每卡 2 个头），每卡每 Token $80\,\text{KB}$。
3. **每卡预算**：$80 \times 0.9 = 72\,\text{GB}$（`gpu_memory_utilization=0.9`）。减去权重 35GB，再预留约 4~5GB 给峰值激活、CUDA Graph、NCCL 缓冲，**KV 块池约 32GB/卡**。
4. **并发容量**：每卡 $32\,\text{GB} \div 80\,\text{KB} \approx 40$ 万 Token（4 卡整体口径一致：$128\,\text{GB} \div 320\,\text{KB}$）。按平均每请求 4K 上下文算，可同时容纳约 **100 个并发请求**；8K 上下文则约 50 个。

把第 4 步按不同上下文长度展开，就是这套部署的容量地图（4 卡 KV 池共 128GB，每 Token 320KB）：

| 📊 每请求上下文 | 单请求 KV 体量 | 可容纳并发（量级） |
|---|---|---|
| 4K | ≈ 1.3 GB | ≈ 100 |
| 8K | ≈ 2.6 GB | ≈ 50 |
| 32K | ≈ 10.5 GB | ≈ 12 |
| 128K | ≈ 42 GB | ≈ 3 |

长上下文对并发的挤压一目了然——128K 上下文时 4 张 A100 只能同时伺候 3 个请求，这正是长文场景必须上 KV 量化、Prefix Cache 或更多卡的原因。这套推演也可以反着用：给定目标并发和上下文长度，倒推需要多少 KV 池，进而决定 TP 度、卡型和是否要上 KV FP8（每 Token 减半到 160KB，并发翻倍）。

⚠️ **注意**：两个常见错算。其一，KV Cache 用 $h=8192$ 而不是 $n_{\text{kv}} \times d_{\text{head}} = 1024$ 来算——GQA 模型的 KV 宽度只有隐层的 1/8，差 8 倍；其二，忘了 KV Cache 也随 TP 均摊（前提 TP ≤ KV 头数）。

## 8. 通信硬件：NVLink、PCIe 与 InfiniBand

并行策略的所有取舍，最终都锚定在链路的物理参数上。记住量级即可（均为官方标称值，实测有效带宽通常打七到九折）：

| 📊 链路 | 典型带宽 | 延迟量级 | 在推理中的角色 |
|---|---|---|---|
| NVLink 3（A100） | 600 GB/s 每卡聚合（双向） | 亚微秒 | 节点内 TP 的地板 |
| NVLink 4（H100） | 900 GB/s 每卡聚合（双向） | 亚微秒 | 同上，更宽 |
| NVLink 5（B200）/ NVL72 | 1.8 TB/s 每卡聚合 | 亚微秒 | 机架级 NVLink 域，TP/EP 可扩到 72 卡 |
| PCIe 4.0 x16 | 约 32 GB/s 单向 | 微秒级 | 无 NVLink 桥接的消费级/推理卡多卡互联 |
| PCIe 5.0 x16 | 约 64 GB/s 单向 | 微秒级 | 同上 |
| InfiniBand NDR | 400 Gb/s ≈ 50 GB/s 每端口单向 | 微秒级 | 跨节点 PP / EP All-to-All / KV 传输 |
| RoCE v2（400G 以太） | 与 NDR 同量级 | 微秒级，抖动更大 | IB 的以太网替代 |

三条推论直接对应前文的工程惯例：

- **NVLink 与 IB 差一个数量级以上** → TP 的每层小消息 AllReduce 只应发生在 NVLink 域内（第 2.3 节）；8 卡节点通常配 4~8 张 IB 网卡，聚合跨节点带宽 200~400GB/s，也仍然只适合 PP 的点对点和 EP 的 All-to-All 这类低频通信。
- **PCIe 互联的多卡机器**（无 NVLink 桥接）上 TP 的通信税急剧放大，Decode 的 TPOT 会明显劣于 NVLink 机型——同样的 `tensor-parallel-size`，不同拓扑结果天差地别，先跑 `nvidia-smi topo -m` 再定并行度。
- **GPUDirect RDMA** 让网卡直接读写 GPU 显存、绕过 CPU 中转，是跨节点 EP 和下一章 PD 分离 KV 传输的性能前提；没有它，跨节点通信还要多付一次 Host 内存往返。

## 📝 总结

- 推理并行与训练并行共享切分数学，但目标函数不同：**无梯度同步、延迟敏感、显存大头是 KV Cache**。选型永远回到三问：装不装得下、单 Token 延迟达不达标、KV 池剩多少。
- **TP**：Attention 按头切、MLP 先列后行，每层前向恰好 2 次 AllReduce；Decode 的小消息通信是延迟敏感的，每 Token $2L$ 次同步构成"通信税"，因此 TP 度有收益递减点，且**不出 NVLink 域**。
- **PP**：按层切段、点对点低频通信，适合跨节点；不降低单 Token 延迟，吞吐收益依赖 continuous batching 持续填充流水线，低负载时 bubble 暴露。
- **DP**：副本零通信、线性扩吞吐，配前缀感知路由提升缓存命中；只解决吞吐，不解决显存。
- **MoE 大 EP**：专家整只分布、两次 All-to-All 换每卡权重骤降与专家规模效应；热点专家靠冗余副本与 EPLB 重排治理。
- **实操**：节点内 TP、跨节点 PP，`TP × PP = 总卡数`；vLLM 多机靠 Ray 编排，网卡选择与 GPU 拓扑是排错第一现场。
- **估算**：权重除以 TP，KV 每 Token $2 L\, n_{\text{kv}}\, d_{\text{head}}\, \text{bytes}$，70B 在 4×A100 上每卡约 32GB KV 池、40 万 Token 容量。

## ✅ 自我检验清单

**1. 能从"无梯度同步、延迟敏感、KV Cache 吃显存"三点说清推理并行与训练并行的目标差异**

<details>
<summary>参考答案</summary>

- **无梯度同步**：训练 DP 每步要做一次与参数量同阶的梯度 AllReduce；推理 DP 副本之间零通信、天然线性扩展。推理的通信全部来自模型被切开后的激活聚合（TP 的 AllReduce、PP 的点对点、EP 的 All-to-All），且全部在前向关键路径上，无法像训练那样藏进反向计算。
- **延迟敏感**：训练是吞吐型批处理，一个 step 慢 10ms 无所谓；推理的 Decode 每生成一个 Token 都要走完一遍前向，任何附加在单步上的通信延迟都逐 Token 累积进 TPOT。
- **显存大头换位**：训练显存 = 权重 + 梯度 + 优化器状态 + 激活；推理显存 = 权重 + KV Cache + 少量瞬态激活，唯一随负载增长的是 KV Cache——KV 池大小决定能拼多大的 Batch，而 Decode 是 Memory Bound，Batch 大小几乎就是吞吐。

因此选型回到三问：权重装不装得下、单 Token 延迟达不达标、KV 池还剩多少。（对应第 1 节）

</details>

**2. 能画出 Megatron 式 TP 切分：Attention 按头、MLP 先列后行，并推导出每层前向恰好 2 次 AllReduce**

<details>
<summary>参考答案</summary>

- **MLP**（$Y = \mathrm{GeLU}(XA)\,B$）：第一个矩阵 $A$ 按列切，每卡输出天然是完整结果的一个分片，GeLU 逐元素作用在分片上无需通信；第二个矩阵 $B$ 按行切，每卡得到部分和，出口处一次 AllReduce 求和。
- 顺序不能反：非线性不满足 $\sigma(a+b) = \sigma(a)+\sigma(b)$，先行切就得在 GeLU 前多一次求和通信；先列后行让两个矩阵乘之间零通信。
- **Attention**：多头天然独立，$W_Q, W_K, W_V$ 按列切（等价于按头分组，每卡 $h/N$ 个头），$W_O$ 按行切、出口一次 AllReduce。
- 于是每层前向恰好 2 次 AllReduce：Attention 出口一次 + MLP 出口一次；训练时反向对输入梯度再加 2 次，每层每迭代共 4 次。（对应第 2.1 节；推导细节可参照面试题 Q1~Q3）

</details>

**3. 能解释 Decode 的 AllReduce 为什么是延迟敏感而非带宽敏感，以及它如何逐 Token 累积进 TPOT**

<details>
<summary>参考答案</summary>

- 每次 AllReduce 同步的激活大小为 $b \times s \times h$。Prefill 时 $s$ 是整个 prompt，单次消息几十上百 MB，是带宽敏感的；Decode 时 $s=1$，单次消息只有 $b \times h \times 2$ 字节——batch 32、$h=8192$ 时仅 512KB，传输时间趋近于零。
- 此时开销的主导项变成每次操作的固定延迟：kernel 发射、NCCL 协议开销、同步等待——所以是延迟敏感。
- Decode 每生成一个 Token 要执行 $2L$ 次 AllReduce：80 层的 70B 模型即每 Token 160 个同步点。即使 NVLink 上单次固定开销只有约 10μs 量级，160 次也累积成毫秒级纯通信时间，而 Decode 单步计算本身才十几到几十毫秒。
- 这就是 TP 的"通信税"：计算时间除以 $N$，通信税却不随 $N$ 减小反而略增，因此 TP 度存在收益递减点，超过之后 TPOT 不降反升。（对应第 2.2 节）

</details>

**4. 能用 NVLink 与 IB 的带宽/延迟量级差，论证"TP 不出节点（高速互联域）"**

<details>
<summary>参考答案</summary>

- 量级对比：节点内 NVLink/NVSwitch（H100 每卡聚合 900GB/s、亚微秒延迟）；跨节点 InfiniBand NDR（单端口 400Gb/s ≈ 50GB/s、微秒级延迟）——带宽差一个数量级以上，延迟同样差一个量级。
- Decode 的小消息 AllReduce 恰恰是延迟敏感的，每 Token 160 次同步全部乘上这个放大系数，TPOT 明显劣化；Prefill 的大消息则直接撞上带宽墙。
- 所以工程惯例是 TP 度 ≤ 单节点 GPU 数（通常 8），跨节点用 PP 或 DP 扩展（vLLM 官方建议"TP 设为每节点卡数、PP 设为节点数"）。
- 本质是"TP 不出高速互联域"而非"不出机箱"：GB200 NVL72 机架级 NVLink 域（72 卡同域）上 TP 可以切得更大——判断标准始终是链路。（对应第 2.3、8 节）

</details>

**5. 能说明 PP 为什么不降低单 Token 延迟，以及 continuous batching 如何压制流水线气泡**

<details>
<summary>参考答案</summary>

- PP 按层切成 $K$ 段，一个 Token 仍要顺序穿过所有层，只是层分布在不同卡上，还多出 $K-1$ 次跨卡点对点传递——TTFT/TPOT 相对单卡（假设装得下）不变甚至略差。PP 换来的是"装得下更大的模型"和多 micro-batch 同时流动带来的吞吐。
- Bubble 出现在流水线填充和排空阶段：不足 $K$ 个 micro-batch 时总有 stage 空转。
- Continuous batching 天然供给源源不断的"工件"：不同请求、同一请求的不同 Decode 步都能作为独立 micro-batch 交错填进流水线，让"排空"几乎永不发生。
- 因此高负载时 bubble 被摊薄、吞吐扩展接近线性；低负载时在飞请求填不满 $K$ 个 stage，bubble 直接暴露为 GPU 空转，利用率明显差于同等卡数的 TP 或 DP。（对应第 3 节）

</details>

**6. 能解释 MoE 大 EP 的显存收益公式与两次 All-to-All 的通信代价，以及冗余专家/EPLB 治理热点的思路**

<details>
<summary>参考答案</summary>

- 显存收益：专家不切、整只分布，每卡专家权重 $M_{\text{expert/GPU}} = \dfrac{P_{\text{exp}} \times \text{bytes}}{\text{EP 度}}$。EP 从 8 扩到 64，每卡专家权重直接降 8 倍，腾出的几十 GB 显存全部变成 KV 池与更大的 batch；同时全 EP 域的 Token 汇聚到每个专家上，把专家的矩阵乘喂饱。
- 通信代价：每层两次 All-to-All——Dispatch 按路由 top-k 把 Token 发到持有对应专家的卡，Combine 把结果原路送回加权求和。这笔账只在高并发下划算。
- 参照系：DeepSeek-V3 生产部署 Prefill 用 EP32（4 节点 32 卡）、Decode 用 EP320（40 节点 320 卡），通信靠 DeepEP（跨节点 RDMA、节点内 NVLink）。
- 热点治理：冗余专家——为高负载专家在多卡维护副本、按线上统计负载周期性重排；EPLB——依据负载估计生成专家到 GPU 的均衡映射。（对应第 5 节）

</details>

**7. 能徒手完成 70B 模型 4 卡 TP 的显存推演：权重 35GB/卡、KV 每 Token 320KB、KV 池约 32GB/卡**

<details>
<summary>参考答案</summary>

以 Llama-3.1-70B、4 × A100 80GB、TP=4、FP16 为例（$L=80$、$n_{\text{kv}}=8$、$d_{\text{head}}=128$）：

1. 权重：$70\text{B} \times 2\text{B} = 140\,\text{GB}$，TP=4 均摊后每卡 35GB（TP=2 时每卡 70GB 逼近 80GB 物理上限、KV 没有生存空间，故最小合理 TP 是 4）。
2. KV 每 Token（全模型）：$2 \times 80 \times 8 \times 128 \times 2\text{B} = 320\,\text{KB}$；TP=4 时 8 个 KV 头均分到 4 卡，每卡每 Token 80KB。
3. 每卡预算 $80 \times 0.9 = 72\,\text{GB}$，减权重 35GB，再预留约 4~5GB 给峰值激活、CUDA Graph、NCCL 缓冲，KV 块池约 32GB/卡。
4. 并发容量：$32\,\text{GB} \div 80\,\text{KB} \approx 40$ 万 Token；按 4K 上下文约 100 个并发请求，8K 约 50 个，128K 时仅约 3 个。（对应第 7 节）

</details>

**8. 能写出 vLLM 两机 16 卡（TP8×PP2）部署的完整命令序列，并说出三类常见故障的排查入口**

<details>
<summary>参考答案</summary>

命令序列四步：头节点 `ray start --head --port=6379` → 每个工作节点 `ray start --address='HEAD_IP:6379'` → `ray status` 验证能看到 16 张 GPU → 头节点 `vllm serve <模型> --tensor-parallel-size 8 --pipeline-parallel-size 2 --distributed-executor-backend ray`（TP×PP 必须等于总卡数）。三类故障：

1. 多机 hang 在启动——通常是网卡选择错误或防火墙拦了 NCCL 端口，用 `NCCL_SOCKET_IFNAME`/`GLOO_SOCKET_IFNAME`/`VLLM_HOST_IP` 显式指定网卡，`NCCL_DEBUG=TRACE` 打日志定位；
2. `ray status` 看不到全部 GPU——工作节点没入集群或版本不一致；
3. 跨节点吞吐远低于预期——TP 被错误切到节点间（检查 TP/PP 与节点的映射、`nvidia-smi topo -m` 看拓扑），或 IB/RoCE 没启用 GPUDirect RDMA。（对应第 6 节）

</details>

**9. 能按 GQA 口径正确计算 KV Cache（用 $n_{\text{kv}} \times d_{\text{head}}$ 而非隐层宽度）**

<details>
<summary>参考答案</summary>

- 每 Token KV Cache 公式：$M_{\text{KV/token}} = 2 \times L \times n_{\text{kv}} \times d_{\text{head}} \times \text{bytes}$，其中 2 代表 K 和 V 两份。
- GQA 模型的 KV 头数少于 Q 头数（Llama-3.1-70B：64 个 Q 头、8 个 KV 头），KV 宽度是 $n_{\text{kv}} \times d_{\text{head}} = 1024$，只有隐层 $h=8192$ 的 1/8——误用 $h$ 会把 KV Cache 高估 8 倍。
- 第二个常见错算：忘了 KV Cache 也随 TP 均摊，前提是 TP ≤ KV 头数；TP 度超过 KV 头数时 KV 头要在多卡间复制，切分收益打折。（对应第 2.1 节提示与第 7 节）

</details>

## 🎯 高频面试题解析

以下题目均出自本仓库 `docs/interview/` 收录的真实面经。

**Q1：一层 Transformer 包含几个线性层？TP 时如何切分？为什么这样切？AllReduce 有哪些优化思路？**（快手一面）
经典结构 4 个：QKV 投影（分开数就是 3 个）、输出投影 $W_O$、MLP 上投影与下投影；LLaMA 类 SwiGLU 结构是 7 个矩阵（Q/K/V/O/gate/up/down）。切分：QKV 与 gate/up 按列切（输出天然分片、非线性可本地做），$W_O$ 与 down 按行切（出口 AllReduce 求和），使每层只在两个出口处各通信一次（见第 2.1 节）。AllReduce 优化思路：通信计算重叠（如把 AllReduce 拆成 reduce-scatter + all-gather 并与后续 GEMM 交错、async-TP）、通信量压缩（FP8/低精度通信）、减少通信域（TP 限制在 NVLink 域内）、硬件卸载（NVSwitch 的 SHARP 在交换机内做归约）。

**Q2：Tensor Parallelism 中 AllReduce 需要执行多少次？如何推导？**（阿里巴巴控股一面）
推导抓"部分和出现在哪"：行切矩阵的输出是部分和，必须求和——每层恰好两处（Attention 的 $W_O$ 之后、MLP 的 down 之后），所以前向每层 2 次；训练时反向对输入梯度在列切矩阵处再各 1 次，每层每迭代共 4 次。推理只有前向：$L$ 层模型每生成一个 Token 需 $2L$ 次（见第 2.2 节）。

**Q3：张量并行为什么存在按行和按列两种切分方式？先列后行与先行后列有何区别？**（小米实习一二面 / 综合题库-5）
列切：权重按输出维切，每卡拿到输出的一个分片，无需通信但要求输入完整；行切：权重按输入维切，输入也随之切分，输出是部分和、需要 AllReduce。两者必须搭配使用：先列后行时，中间激活正好以分片形式衔接（列切的分片输出 = 行切需要的分片输入），且逐元素非线性可以在分片上本地完成；先行后列则中间就要多一次求和通信，还破坏非线性的正确性（$\sigma(a+b) \neq \sigma(a) + \sigma(b)$）（见第 2.1 节）。

**Q4：大规模集群中（节点内 NVLink，节点间部分机器有 RDMA），如何设计分布式推理方案？**（腾讯实习一面）
按链路分层设计：节点内 NVLink 域承载 TP（和 MoE 的节点内 All-to-All）；有 RDMA 的机器分组承载跨节点 PP、MoE 大 EP、以及 PD 分离的 KV 传输这类低频/可重叠通信；无 RDMA 的机器不参与任何跨机张量通信，作为独立 DP 副本用路由器接入。核心原则：高频小消息通信钉死在最快的域内，跨节点只留点对点与可重叠的通信（见第 2.3、3、8 节）。

**Q5：设计一个分布式推理框架，阐述整体架构与关键模块。**（小厂一面）
自上而下五层：（1）接入与路由层——负载感知 + 前缀感知调度，SLO 准入控制；（2）引擎副本层——每副本内部 TP×PP，continuous batching 调度器；（3）显存与缓存层——PagedAttention 块池、Prefix Cache、多级 KV 存储；（4）通信层——NCCL 集合通信 + RDMA 点对点，拓扑感知的并行度映射；（5）控制面——副本扩缩容、健康检查与故障摘除、TTFT/TPOT/goodput 指标闭环。答题时把每个模块与"三问"（容量/延迟/并发）挂钩（见第 1、4 节）。

**Q6：多卡协同场景下，卡间通信有哪些方式？NVLink 和 RDMA 各自的特点？**（阿里云实习二面）
节点内：共享内存经 PCIe（P2P）、NVLink 直连、NVSwitch 全互联；跨节点：TCP/以太、RDMA（InfiniBand 或 RoCE），配合 GPUDirect RDMA 让网卡直读显存。NVLink：卡间专用点对点链路，H100 每卡聚合 900GB/s、亚微秒延迟，但只覆盖节点（或 NVL 机架）内；RDMA：内核旁路、零拷贝的跨机通信，单端口 50GB/s（NDR）量级、微秒延迟，可扩展到整个集群。带宽/延迟差一个量级，决定了 TP 与 PP/EP 的分工（见第 8 节）。

**Q7：All-Reduce、All-Gather、All-to-All 分别完成了什么数据交换？各适用于哪些并行策略？**（B站实习一面）
AllReduce：各卡持有同形张量，逐元素归约后**每张卡都得到完整求和结果**（可分解为 reduce-scatter + all-gather），用于 TP 的部分和聚合、训练 DP 的梯度同步。AllGather：各卡持有不同分片，交换后每张卡拿到**全量拼接**，用于序列并行与 TP 的边界转换、EP 场景收集路由元信息。All-to-All：每张卡给每张卡发送**互不相同**的分片（分布式转置语义），是 EP 中 Token dispatch/combine 的载体（见第 2、5 节）。

**Q8：MoE 路由模块的运行机制是怎样的？哪些因素会造成专家负载不均？**（MiniMax 实习一面）
路由器是一个小线性层：对每个 Token 的隐状态打分，softmax/sigmoid 后取 top-k 专家，输出按门控权重加权组合。负载不均的来源：真实数据的领域/语言分布偏斜使某些专家天然高频；训练期路由塌缩（少数专家被强化、其余退化）；推理 batch 内 Token 高度相关（同一会话、同一模板）造成瞬时热点；辅助均衡损失权重不足。推理侧治理靠冗余热点专家副本与 EPLB 式的负载感知放置重排（见第 5 节）。
