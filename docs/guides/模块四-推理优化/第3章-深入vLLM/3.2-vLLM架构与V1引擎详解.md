## 1. 全景：一个请求穿过 vLLM 的完整旅程

### 1.1 分层总览

vLLM V1 的架构可以切成五层，每层职责单一、边界清晰。先上全景图（以在线服务为例）：

```text
        HTTP 请求                                    流式响应 (SSE)
           │                                              ▲
┌──────────┼──────────────────────────────────────────────┼──────────┐
│          ▼               API Server 进程（进程 0）       │          │
│  ┌────────────────┐   ┌──────────────┐   ┌──────────────────────┐  │
│  │ OpenAI 兼容层  │──▶│   AsyncLLM   │──▶│   OutputProcessor    │  │
│  │ (FastAPI 路由) │   │  (异步入口)  │   │ (增量 Detokenize、   │  │
│  └────────────────┘   │  ┌─────────┐ │   │  组装流式返回)       │  │
│                       │  │Processor│ │   └──────────────────────┘  │
│                       │  │Tokenize │ │              ▲              │
│                       │  └─────────┘ │              │              │
│                       └──────┬───────┘              │              │
└──────────────────────────────┼──────────────────────┼──────────────┘
                        ZeroMQ │ IPC（进程间消息队列）  │ ZeroMQ IPC
┌──────────────────────────────┼──────────────────────┼──────────────┐
│          EngineCore 进程（进程 1）— 核心忙循环 (busy loop)          │
│                              ▼                      │              │
│  ┌──────────────────────────────────────────────────┴───────────┐  │
│  │ EngineCore:  while True:                                     │  │
│  │   1. scheduler.schedule()        ← 决定这一步算谁、算多少     │  │
│  │   2. executor.execute_model()    ← 跑一次前向 + 采样          │  │
│  │   3. scheduler.update_from_output() ← 更新请求状态、发结果    │  │
│  └───────┬───────────────────────────────────┬──────────────────┘  │
│          ▼                                   ▼                     │
│  ┌───────────────┐  allocate_slots   ┌───────────────────────┐     │
│  │   Scheduler   │──────────────────▶│    KVCacheManager     │     │
│  │ waiting 队列  │  get_computed_    │  (块表/BlockPool，    │     │
│  │ running 队列  │      blocks       │   见 2.1 节)          │     │
│  │ token budget  │◀──────────────────│                       │     │
│  └───────┬───────┘   命中/分配结果    └───────────────────────┘     │
│          │ SchedulerOutput（本步的"排产计划"）                      │
│          ▼                                                         │
│  ┌───────────────────────────────────────────────────────────┐     │
│  │ Executor ──▶ Worker(每 GPU 一个) ──▶ GPUModelRunner       │     │
│  │   TP/PP 分发     持有模型分片         persistent batch、  │     │
│  │                                       前向计算、采样      │     │
│  └───────────────────────────────────────────────────────────┘     │
│                              │                                     │
│                              ▼  GPU: 模型权重 + KV Cache 块池      │
└────────────────────────────────────────────────────────────────────┘
```

### 1.2 各层职责

| 层 | 核心类 | 一句话职责 |
|---|---|---|
| 入口层 | `LLM` / `AsyncLLM` | 离线批量用 `LLM`（同步封装 `LLMEngine`），在线服务用 `AsyncLLM`；负责接收请求、Tokenize、回传结果 |
| 引擎核心 | `EngineCore` | 独立进程里的忙循环：调度 → 执行 → 更新，一步一迭代，不掺杂任何 API/编解码逻辑 |
| 调度层 | `Scheduler` | 管 waiting/running 两条队列，按 Token 预算决定"这一步每个请求算多少个 Token" |
| 显存层 | `KVCacheManager` | 为调度决策提供块分配/释放/前缀命中查询（内部即 2.1 节讲的块表 + `BlockPool`） |
| 执行层 | `Executor` / `Worker` / `ModelRunner` | Executor 按 TP/PP 把任务分发给各 GPU 上的 Worker，`GPUModelRunner` 维护持久化批次、跑前向、采样出 Token |

🔑 **核心概念**：这套分层的精髓是**"决策"与"执行"彻底分离**。Scheduler 只做决策（算谁、算多少、块够不够），从不碰张量；ModelRunner 只做执行（拿到排产计划就跑前向），从不做决策。中间的 `SchedulerOutput` 就是两者之间的"工单"。想给 vLLM 做二次开发，第一步就是认清自己要改的是哪一层。

### 1.3 数据流走读：从 HTTP 请求到流式返回

把镜头对准一个具体请求，走一遍完整链路：

1. **到达**：HTTP 请求打到 OpenAI 兼容层（FastAPI 路由），解析出 prompt、采样参数、流式开关。
2. **预处理**：`AsyncLLM` 内的 `Processor` 做 Tokenize 与多模态输入处理，打包成引擎请求，经 ZeroMQ 序列化后发给 EngineCore 进程。**注意：这一步发生在 API Server 进程，不占用 GPU 循环的时间。**
3. **入队**：EngineCore 的输入线程收到消息，反序列化后把请求加入 Scheduler 的 waiting 队列。
4. **调度**：下一次 `schedule()` 时，调度器先查前缀缓存（`get_computed_blocks`，能命中就跳过对应 Prefill），再向 KVCacheManager 申请块（`allocate_slots`），把该请求纳入本步的 Token 预算。
5. **执行**：`SchedulerOutput` 交给 Executor 分发到各 Worker。`GPUModelRunner` 按 diff 更新持久化批次，执行一次前向（规整部分走 CUDA Graph 重放，见 2.5 节），采样出新 Token。
6. **更新**：模型输出回到 `update_from_output()`：追加 Token、判断是否命中停止条件（EOS / max_tokens），产出增量结果，经输出线程和 ZeroMQ 推回 API Server 进程。
7. **返回**：`OutputProcessor` 做**增量 Detokenize**，组装成 SSE chunk 流式发给客户端。与此同时，EngineCore 已经在跑下一步了——两个进程各干各的，互不等待。

一个 Decode 中的请求会在第 4~6 步之间反复循环，每步产出一个 Token，直到结束。这就是 Continuous Batching（2.2 节）在架构里的落点：**循环的主体是"步"，不是"请求"**，每步都可以有请求加入或离开。

### 1.4 离线与在线：同一个核，两种入口

上面走的是在线服务链路。离线批量推理（`LLM.generate()`，3.1 节用过）走的是同一套引擎，只是入口不同：

- **离线 `LLM`**：同步封装，把一批 prompt 全部提交后循环调用引擎 step，直到所有请求完成再一次性返回。没有 HTTP、没有流式，但 Scheduler、KVCacheManager、ModelRunner 与在线完全共用。
- **在线 `AsyncLLM`**：异步入口，请求随到随进、结果逐 Token 流出，配合双进程隔离（第 2.1 节）。

📌 **关键点**：这解释了为什么用 `LLM` 做离线评测得到的吞吐结论，大体可以迁移到在线服务——**引擎核心是同一个**；差异主要出现在请求到达模式（批量一次性 vs 泊松流）对调度器的压力上，做容量规划时要用贴近真实到达分布的压测，而不是拿离线跑分直接换算。

## 2. V1 引擎：五项重构要点

V0 时代的 vLLM 是单进程的：API 处理、Tokenize、调度、模型执行、Detokenize 全挤在一个 Python 进程里排队。模型前向被各种 CPU 工作切碎，GPU 大量时间在等 Python。V1 重构的主线就一句话：**把 GPU 循环从一切 CPU 工作中解放出来**。按官方博客的口径，V1 相比 V0 的吞吐提升约 1.7 倍——而且这是在几乎没改任何 Kernel 的前提下拿到的，纯靠架构。

### 2.1 进程隔离：API Server 与 EngineCore 分家

第 1 节架构图里那条 ZeroMQ 虚线是 V1 最重要的一刀：

```text
V0（单进程）:
  [接收│Tokenize│调度│★GPU前向★│Detokenize│发送│接收│Tokenize│...]
   ──────── GPU 在非 ★ 的时间片里全部闲置 ────────

V1（双进程，时间轴重叠）:
  进程0: [接收│Tokenize│发送]      [Detokenize│流式返回]  [接收│...]
  进程1:        [★前向★][★前向★][★前向★][★前向★][★前向★] ...
                 ↑ EngineCore 忙循环几乎不间断地喂 GPU
```

- API Server 进程承担所有"重 CPU"工作：HTTP 解析、Tokenize、增量 Detokenize、流式组包。
- EngineCore 进程只干一件事：调度 + 执行的忙循环，输入输出各挂一个线程对接消息队列。
- 两者用 ZeroMQ 传消息，CPU 工作与 GPU 执行**在时间上重叠**而非串行排队。

📌 **关键点**：这本质上是把 2.5 节"CPU 拖 GPU 后腿"的诊断从 Kernel 级推广到了系统级——Kernel 级用 CUDA Graph 消掉 launch 开销，系统级用进程隔离消掉 Tokenize/Detokenize 开销。两级优化叠加，才有 V1 的吞吐提升。

### 2.2 统一 Token 预算调度：抹平 Prefill 与 Decode 的边界

V0 的调度器要区分"这一步是 Prefill step 还是 Decode step"，两类步交替执行，逻辑分叉多、还容易互相饿死。V1 把这个二分法整个扔掉了：

- 调度的产出不再是"哪类步"，而是一张简单的分配表：`{请求A: 3 个 Token, 请求B: 512 个 Token, 请求C: 1 个 Token}`。
- 每步只有一个约束：**所有请求本步 Token 数之和 ≤ token budget（`max_num_batched_tokens`）**。
- 在调度器眼里，Prefill 只是"这一步要算很多 Token 的请求"，Decode 只是"这一步算 1 个 Token 的请求"，**Chunked Prefill（2.4 节）不再是特性，而是自然结果**——预算不够装下整段 Prompt，就只调度装得下的那部分，剩下的下一步继续。

这套统一表示还让 Prefix Cache 命中（跳过若干 Token）、投机解码（一步验证多个 Token）都能塞进同一个调度框架，不需要各开一条特殊路径。

### 2.3 零开销 Prefix Cache：从"可选优化"到"默认开启"

V0 的 Prefix Cache 在缓存命中率低时反而拖慢系统（哈希与管理开销白付），所以默认关闭。V1 重写了这套机制，目标是把"没命中时的开销"压到可以忽略：

- **哈希分块**：以 Block 为粒度算哈希（哈希值 = 前序块哈希 + 本块 Token），查询是常数时间的字典查找。
- **零成本驱逐**：复用 2.1 节讲的设计——`ref_cnt` 归零的块只是回到空闲链表、内容不清空，驱逐无需任何额外数据结构维护成本。
- 官方博客给出的结论：即使缓存命中率为 0%，吞吐下降也不到 1%；命中率高时则大幅提速。**代价近零、收益可观，于是 V1 敢默认开启。**

### 2.4 Persistent Batch：只传增量

V0 每一步都要在 CPU 上把整个批次的输入张量从头构建一遍——请求几百个时，这份 Python 开销每步都要付。V1 改成**持久化批次（Persistent Batch）**：

- 输入批次的张量常驻缓存，每步只应用 **diff**：谁进来了、谁结束了、每个请求追加了哪个 Token。
- 批次更新用 Numpy 向量化操作替代 Python 循环，进一步压低 CPU 成本。

这和 2.5 节的 CUDA Graph 是一对搭档：CUDA Graph 消掉"发射 Kernel"的开销，Persistent Batch 消掉"准备输入"的开销，两头一起把 Decode 步的 CPU 时间榨干。

### 2.5 Piecewise CUDA Graph：衔接上一章

V1 默认启用 `torch.compile` + 分段 CUDA Graph（在 Attention 算子处切图，规整部分录制重放、Attention 保持 eager）。这部分机制、切图方式与调优开关在 2.5 节已完整展开，此处不再重复——只需记住它在架构中的位置：**发生在 `GPUModelRunner` 的前向执行里，是执行层的优化，对调度层完全透明**。

💡 **提示**：面试被问"V1 相比 V0 改了什么"，最好的回答结构就是上面五点 + 一句总纲："所有改动都指向同一个目标——让 GPU 循环不被 CPU 工作打断。"提升数字只引用官方博客的约 1.7 倍，不要报道听途说的 benchmark。

## 3. 调度器：一个 step 里到底发生了什么

调度器（`vllm/v1/core/sched/` 下的 `Scheduler` 类）是 vLLM 的大脑。这一节按源码的设计骨架走读它的决策过程（代码持续演进，方法名以你所用版本为准，这里讲稳定的逻辑主线）。

### 3.1 两条队列

- **waiting 队列**：新到达的请求、以及被抢占后等待恢复的请求。
- **running 列表**：正在推进的请求——包括 Decode 中的，也包括 Prefill 只算了一半（Chunked Prefill 进行中）的。

请求的一生就是在这两个容器间流转，画成状态机是这样：

```text
                    调度成功(分到预算+KV块)
   新请求 ──▶ [WAITING] ─────────────────────▶ [RUNNING]
                 ▲                               │    │
                 │        KV 块不足被抢占         │    │ 命中 EOS /
                 │  (释放全部块, 回 waiting 队头) │    │ 达到 max_tokens
                 └───────────────────────────────┘    ▼
                     恢复时: 原Prompt+已生成Token   [FINISHED]
                     重新 Prefill(常被前缀缓存命中)  释放全部 KV 块
```

注意两条边的不对称：进入 RUNNING 要同时过"预算"和"KV 块"两道闸，而被踢回 WAITING 只由 KV 块短缺触发——预算不足只会让请求在本步轮空，并不会把它抢占出去。

### 3.2 Token Budget 怎么分

每次 `schedule()` 的核心是分掉一份预算 `token_budget = max_num_batched_tokens`。分配遵循一个明确的优先次序：

**第一轮：先保 running。** 遍历 running 中的每个请求：

- Decode 中的请求要 1 个 Token（若开投机解码则多几个）；Chunked Prefill 进行中的请求要"剩余 Prompt 与剩余预算的较小值"。
- 为其调用 `allocate_slots` 申请 KV 块。申请成功就计入本步计划、扣减预算。
- 预算扣完，后面的 running 请求本步轮空（下一步优先）。

**第二轮：预算有剩余，再放 waiting。** 从 waiting 队头依次取请求：

- 受两个闸门约束：剩余 token budget > 0，且 running 数量未达 `max_num_seqs`。
- 先查前缀缓存：`get_computed_blocks` 返回能复用的块和命中的 Token 数，命中部分**直接跳过、不占预算**。
- 剩余 Prompt 若超过剩余预算，就只调度装得下的部分——这就是 Chunked Prefill 在 V1 里"天然发生"的地方。

用一个具体例子（设 `max_num_batched_tokens = 1024`）：

```text
running: A(Decode)  B(Decode)  C(Chunked Prefill 还剩 700 token)
waiting: D(新请求, Prompt 900 token, 前缀缓存命中 400)

分配:  A: 1      → 预算剩 1023
       B: 1      → 预算剩 1022
       C: 700    → 预算剩 322   (C 本步完成 Prefill)
       D: 322    → 预算剩 0     (D 命中 400 免算, 剩 500 里先算 322,
                                  余下 178 留给下一步)
本步实际计算: 1 + 1 + 700 + 322 = 1024 token, 一次前向混合了
Decode 与两段 Prefill —— 这正是统一调度器的日常。
```

📌 **关键点**：这套机制里**没有任何"prefill step / decode step"的分支判断**。所有请求在同一把尺子（Token 数）下排队分预算——这就是 2.2 节 Continuous Batching 和 2.4 节 Chunked Prefill 在 V1 源码里的统一归宿。

### 3.3 抢占：触发条件与恢复方式

预算管"算力"，但还有另一种资源可能先耗尽：**KV 块**。当 `allocate_slots` 发现空闲块不够时（典型场景：一批长请求同时进入 Decode 后期，每个都在持续吃块），调度器启动抢占：

- **触发**：为某请求分配新块失败。
- **选谁**：从 running 列表**队尾**开刀（后来的先牺牲，近似 LIFO；开启优先级调度时按优先级选）。被抢占的请求释放其全部 KV 块，退回 waiting 队列**队头**，等待优先恢复。
- **恢复**：V1 采用**重计算（Recompute）**——恢复时把该请求"原始 Prompt + 已生成的 Token"当作新 Prompt 重新 Prefill。V0 时代还有换出到 CPU（Swap）的选项，V1 把路径统一成了重计算：实现简单、不占 CPU 内存，而且**有 Prefix Cache 兜底**——被抢占请求的完整块若还没被驱逐，恢复时哈希直接命中，实际重算的往往只有尾部一小段。

⚠️ **注意**：抢占保证的是"显存不足时请求排队而非失败"，但被抢占的请求 Token 会重复计算、延迟明显拉长。它是兜底机制，**频繁触发就是容量报警**：说明 KV 块池太小或并发压得太满。

### 3.4 用指标观测抢占

生产上判断"是否压得太满"，看这几个信号：

- **Prometheus 指标**：`vllm:num_preemptions_total`（累计抢占次数，持续增长就要警惕）、`vllm:num_requests_waiting`（排队深度）、`vllm:gpu_cache_usage_perc`（KV 块池使用率，长期贴着 100% 说明块紧张）。
- **日志**：vLLM 在发生抢占时会打 WARNING，提示可能影响端到端延迟。

处置思路按顺序：调高 `gpu-memory-utilization` 给块池扩容 → 调低 `max-num-seqs` 限并发 → 缩短 `max-model-len` 降低单请求块上限 → 加卡或换更大显存的卡。

## 4. 关键配置调优：吞吐、延迟与显存的旋钮

理解了架构和调度，参数调优就不再是背表格，而是推导。先给全景表，再讲两个最核心的机理。

### 4.1 参数全景表

| 参数 | 作用机理 | 调大的效果 | 调大的代价 |
|---|---|---|---|
| `--gpu-memory-utilization` | 划给 vLLM 实例的显存比例，权重与激活之外**全部注入 KV 块池**（默认约 0.9） | 块池更大 → 更高并发、更少抢占、Prefix Cache 存得更多 | 余量变小，易 OOM（尤其还有其它进程占卡时） |
| `--max-num-seqs` | 每步最多同时推进的请求数（并发闸门） | 批更大，Decode 吞吐更高 | 单请求交错变多，ITL（Token 间延迟）上升 |
| `--max-num-batched-tokens` | 每步 Token 总预算（3.2 节那把尺子） | 每步能塞进更大的 Prefill 段，吞吐更高、TTFT 更低 | 单步变慢，Decode 请求的 ITL 变差 |
| `--block-size` | KV 块粒度（2.1 节，常见默认 16） | 块表更短、管理开销更小 | 尾块内部碎片变大、前缀命中粒度变粗 |
| `--enable-prefix-caching` | 前缀块哈希复用（V1 默认开启） | 共享前缀场景省掉重复 Prefill | 近零（2.3 节），仅精确复现实验时才关 |
| `--max-model-len` | 单请求最大上下文长度 | 支持更长输入 | 单请求块占用上限变大，同显存下并发变少 |

### 4.2 `gpu-memory-utilization`：KV 块池大小是这样算出来的

启动时 vLLM 做一次**显存画像（profiling）**：先加载权重，再用最大配置跑一次假前向测出激活值峰值，然后：

$$\text{KV 块池} = \text{总显存} \times \text{utilization} - \text{权重} - \text{激活峰值}$$

启动日志里那行 `# GPU blocks: xxxx` 就是这个池子的块数。由此能推出两个实用结论：

- 这个参数是"**给实例的总闸**"而不是"给 KV 的比例"——权重是固定成本，所以从 0.90 调到 0.95，KV 块池的**相对增幅远大于** 5%（小模型大显存时尤其明显）。
- 同卡跑多个 vLLM 实例时，各实例的 utilization 之和必须留出余量，否则第二个实例起不来。

### 4.3 一对核心矛盾：吞吐 vs TTFT/ITL

`max-num-batched-tokens` 是理解 vLLM 延迟特性的钥匙。回看 3.2 节的例子：一个 700 Token 的 Prefill 段和两个 Decode 请求同批执行时，这两个 Decode 请求的下一个 Token 要等整步算完才出来。于是：

- **预算调大**：Prefill 大段大段地算，新请求 TTFT 更低、整体吞吐更高；但混在批里的 Decode 请求每步都陪着大 Prefill 段跑，ITL 变差，用户看到的"打字速度"变卡。
- **预算调小**：Prefill 被切成细块，每步以 Decode 为主，ITL 平滑；但 Prefill 要更多步才能算完，吞吐与 TTFT 变差。

🔑 **核心概念**：**`max-num-batched-tokens` 本质上是在"Prefill 的推进速度"和"Decode 的流畅度"之间分时间片。** 在线交互服务向小调，离线批处理向大调——这是 vLLM 调优里最值得记住的一条。

### 4.4 场景化配置

**场景 A：高并发短请求**（客服问答、通用 Chat API：Prompt 几百 Token、大量并发、带统一 System Prompt）：

```bash
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --gpu-memory-utilization 0.92 \
  --max-num-seqs 256 \
  --max-num-batched-tokens 8192 \
  --max-model-len 4096 \
  --enable-prefix-caching
```

思路：请求短，单步预算充裕，Prefill 不会长期霸占批次，预算可以给大以提高吞吐；`max-model-len` 收紧到业务实际上限，让同样的块池装下更多并发；统一 System Prompt 靠 Prefix Cache 白拿一段免费 Prefill。重点盯 `num_preemptions_total`，一旦频繁抢占就先降 `max-num-seqs`。

**场景 B：长文档摘要（在线）**（万 Token 级输入、并发不高、但有交互式用户在等流式输出）：

```bash
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --gpu-memory-utilization 0.95 \
  --max-num-seqs 32 \
  --max-num-batched-tokens 2048 \
  --max-model-len 32768
```

思路：单请求 KV 占用巨大，必须压低并发上限、拉高块池比例，避免 Decode 后期集体抢块；预算调小，把万 Token 的 Prefill 切成细块，保证已在生成中的请求不被新文档的 Prefill 卡住。若同样负载是**离线批处理**（没人盯着流式输出），则反过来把 `max-num-batched-tokens` 调大（如 16384），让 Prefill 尽快推完、追求总吞吐。

💡 **提示**：调参的正确顺序是"先定显存（utilization、max-model-len），再定并发（max-num-seqs），最后用 max-num-batched-tokens 微调延迟曲线"，每改一项压测一轮 TTFT/ITL/吞吐三条曲线，不要一次全动。

### 4.5 三个常见误区

- **误区一："`gpu-memory-utilization=0.9` 就是 90% 显存给 KV Cache"。** 不是。它是给整个实例的总闸，权重和激活先扣，剩下的才是 KV 块池（第 4.2 节）。同一个 0.9，8B 模型在 80GB 卡上 KV 池巨大，70B 模型在同一张卡上可能所剩无几。
- **误区二："`max-num-seqs` 越大吞吐越高"。** 并发上限只有在 KV 块和 Token 预算都跟得上时才能兑现成吞吐。块池不够时调大它只会更早触发抢占，重计算反而把有效吞吐吃回去——先看 `gpu_cache_usage_perc` 再决定要不要加并发。
- **误区三："显存紧张时先关 Prefix Cache 省显存"。** 关了基本不省：缓存复用的是**本来就空闲**的块（2.1 节的"释放不等于清空"），不额外占池子；关掉只会失去免费的 Prefill 节省。显存紧张的正解是排查 `max-model-len` 是否虚高、utilization 是否还有余量。

## 5. 框架横向对比：vLLM、SGLang 与 TensorRT-LLM

推理框架三强各有清晰的"性格"，面试和技术选型都常考。先看架构差异，再给决策表。

### 5.1 三家的架构差异

| 维度 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 核心显存/缓存设计 | PagedAttention 块表 + 哈希 Prefix Cache | **RadixAttention**：基数树组织 KV 前缀，跨请求自动复用，树结构天然契合多轮/分叉 | Paged KV Cache（同类思想的 NVIDIA 实现） |
| 执行方式 | Python 运行时 + `torch.compile` / 分段 CUDA Graph（2.5 节） | Python 运行时 + **零开销调度器**：CPU 调度与 GPU 执行重叠，连调度本身都藏进前向时间里 | **预先编译**：模型经 TensorRT 图优化/算子融合编译成引擎，C++ Runtime 执行 In-flight Batching |
| 结构化输出 | 支持（外接 grammar 后端） | **压缩有限状态机**约束解码为一等公民，JSON/语法约束下可跳步生成，速度优势明显 | 支持（guided decoding） |
| 硬件覆盖 | 最广：NVIDIA、AMD、Intel、TPU、AWS 芯片等 | NVIDIA 为主，AMD 等在扩展 | 仅 NVIDIA，换代（FP8/FP4、新架构）跟进最快最深 |
| 生态与易用性 | 模型支持最全、新模型 day-0 适配、社区最大；HuggingFace 权重直接跑 | 对 DeepSeek 系（MLA、大规模 EP/PD 分离）优化激进；前端 DSL 便于编排复杂 LLM 程序 | 需构建引擎的工作流较重（LLM API 在简化中）；与 Triton Inference Server / NIM 配套部署 |
| 二次开发 | Python 分层清晰（第 1 节），改调度/接模型门槛低 | Python 为主，同样友好 | C++ 内核 + 编译栈，定制门槛最高 |

三句话概括三家的设计哲学：

- **vLLM 押注"通用"**：用干净的 Python 分层 + 极致的 CPU 开销消除，换来最广的模型/硬件覆盖和最低的上手与定制成本。
- **SGLang 押注"LLM 程序"**：假设未来的负载不是孤立请求而是带共享前缀、分叉、约束输出的 Agent 程序，于是把 KV 复用（基数树）和约束解码（FSM）做进最底层。
- **TensorRT-LLM 押注"编译"**：牺牲灵活性换极致性能，让 NVIDIA 自家软硬件垂直整合的红利全部兑现。

### 5.2 选型决策表

| 你的场景 | 首选 | 理由 |
|---|---|---|
| 通用在线 API 服务、模型更换频繁 | vLLM | 生态最全、新模型跟进最快、运维资料最多 |
| Agent / 多轮对话 / 大量结构化（JSON）输出 | SGLang | RadixAttention 对树状共享前缀命中率高，FSM 约束解码快 |
| NVIDIA 全栈、追求极限延迟或极致单卡成本 | TensorRT-LLM | 编译优化 + FP8/FP4 + 新硬件特性兑现最彻底 |
| 非 NVIDIA 硬件（AMD/TPU/自研芯片） | vLLM | 硬件后端抽象最成熟 |
| 需要深度定制调度器 / 快速接自研模型 | vLLM 或 SGLang | Python 源码可改，分层清晰；TRT-LLM 编译栈难下手 |
| DeepSeek 系模型大规模部署（MLA、EP、PD 分离） | SGLang（vLLM 也在快速跟进） | 官方合作调优最激进，相关特性落地最早 |

⚠️ **注意**：三个框架都在高速迭代，性能对比结论的保质期极短——今天 A 快 10%，下个版本可能反过来。**选型时架构契合度和团队维护能力比一次 benchmark 数字更重要**；真要对比性能，用自己的模型、自己的流量分布实测，不要引用别人的数字。

## 📝 总结

- vLLM V1 分五层：`LLM`/`AsyncLLM` 入口 → `EngineCore` 忙循环 → `Scheduler` 调度 → `KVCacheManager` 块管理 → `Executor`/`Worker`/`ModelRunner` 执行；**决策与执行分离**，`SchedulerOutput` 是两者间的工单。
- V1 重构五要点：**进程隔离**（Tokenize/Detokenize 与 GPU 循环重叠）、**统一 Token 预算调度**（Chunked Prefill 天然融入）、**零开销 Prefix Cache**（默认开启）、**Persistent Batch**（只传增量）、**分段 CUDA Graph**（2.5 节）；官方口径吞吐较 V0 提升约 1.7 倍。
- 调度器每步：先保 running、再放 waiting，所有请求在同一份 `max_num_batched_tokens` 预算下按 Token 数分配；KV 块不足时从队尾抢占、退回 waiting 队头，V1 统一用**重计算**恢复，且常被 Prefix Cache 摊薄代价。
- 抢占频繁 = 容量报警，用 `vllm:num_preemptions_total`、`gpu_cache_usage_perc` 观测。
- 调参三步走：`gpu-memory-utilization`/`max-model-len` 定块池 → `max-num-seqs` 定并发 → `max-num-batched-tokens` 在吞吐与 TTFT/ITL 之间找平衡；在线调小、离线调大。
- 选型：通用服务选 vLLM，Agent/结构化输出选 SGLang，NVIDIA 栈极限性能选 TensorRT-LLM；架构契合度重于一次性 benchmark。

<details>

**4. 能说明统一 Token 预算调度如何抹平 Prefill/Decode 边界，Chunked Prefill 为何成为"自然结果"**

<details>
<summary>参考答案</summary>

V1 扔掉了 V0 "这一步是 Prefill step 还是 Decode step"的二分法：调度产出就是一张 `{请求: Token 数}` 分配表，唯一约束是本步所有请求 Token 数之和不超过 token budget（`max_num_batched_tokens`）。调度器眼里 Prefill 只是"要算很多 Token 的请求"，Decode 只是"算 1 个 Token 的请求"；预算装不下整段 Prompt 就只调度装得下的部分、剩下的下一步继续——Chunked Prefill 因此不再是特性而是自然结果。这套统一表示还让 Prefix Cache 命中（跳过若干 Token）、投机解码（一步验证多个 Token）都能塞进同一框架。（对应正文第 2.2 节）

</details>

**5. 能解释 V1 的 Prefix Cache 为什么敢默认开启**

<details>
<summary>参考答案</summary>

V0 的 Prefix Cache 在命中率低时哈希与管理开销白付、反而拖慢系统，所以默认关闭。V1 重写后把"没命中时的开销"压到可忽略：以 Block 为粒度算哈希（哈希值 = 前序块哈希 + 本块 Token），查询是常数时间的字典查找；驱逐零成本——`ref_cnt` 归零的块只是回到空闲链表、内容不清空，无需额外数据结构维护。官方博客结论：命中率为 0% 时吞吐下降不到 1%，命中率高时大幅提速——代价近零、收益可观。（对应正文第 2.3 节）

</details>

**6. 能说出 Persistent Batch 与分段 CUDA Graph 这对搭档各消掉哪部分开销**

<details>
<summary>参考答案</summary>

Persistent Batch 消掉"准备输入"的开销：V0 每步在 CPU 上从头构建整个批次张量，V1 让批次张量常驻缓存、每步只应用 diff（谁进来、谁结束、各追加哪个 Token），并用 Numpy 向量化替代 Python 循环。分段 CUDA Graph 消掉"发射 Kernel"的开销：在 Attention 算子处切图，规整部分录制重放、Attention 保持 eager，它发生在 `GPUModelRunner` 的前向执行里，对调度层完全透明。两头一起把 Decode 步的 CPU 时间榨干。（对应正文第 2.4/2.5 节）

</details>

**7. 能按两轮次序描述 `schedule()` 的预算分配，并复算正文 1024 预算的例子**

<details>
<summary>参考答案</summary>

第一轮先保 running：Decode 请求要 1 个 Token（开投机解码则多几个），Chunked Prefill 进行中的要"剩余 Prompt 与剩余预算的较小值"，逐个 `allocate_slots` 并扣预算，预算扣完则后面的本步轮空。第二轮预算有余再从 waiting 队头收新请求：受剩余预算和 `max_num_seqs` 两道闸约束，先查前缀缓存、命中部分直接跳过不占预算，Prompt 装不下就截断成 chunk。例子：running 中 A/B（Decode）各 1、C（Chunked Prefill）700，waiting 中 D（Prompt 900、命中 400）分到 322，合计 1 + 1 + 700 + 322 = 1024——一次前向混合 Decode 与两段 Prefill，全程没有 prefill/decode step 的分支判断。（简答，另见 Q2；对应正文第 3.2 节）

<details>
<summary>参考答案</summary>

启动时 vLLM 先做显存画像：加载权重、用最大配置跑一次假前向测激活峰值，然后 $\text{KV 块池} = \text{总显存} \times \text{utilization} - \text{权重} - \text{激活峰值}$，启动日志的 `# GPU blocks: xxxx` 即池子块数。误读纠正："0.9 就是 90% 显存给 KV Cache"不对——它是给整个实例的总闸，权重与激活先扣、剩下才是块池；权重是固定成本，所以从 0.90 调到 0.95 块池相对增幅远大于 5%，同一个 0.9 下 8B 与 70B 模型在同卡上的块池天差地别。另外：显存紧张时关 Prefix Cache 基本不省显存，缓存复用的是本来就空闲的块。（对应正文第 4.2/4.5 节）

</details>

**10. 能解释 `max-num-batched-tokens` 背后的吞吐 vs TTFT/ITL 矛盾，并说出三个框架的选型逻辑**

<details>
<summary>参考答案</summary>

该参数本质是在"Prefill 的推进速度"和"Decode 的流畅度"之间分时间片：调大则 Prefill 大段推进、TTFT 更低、吞吐更高，但同批 Decode 请求每步陪着大 Prefill 段跑、ITL 变差；调小则 ITL 平滑、吞吐与 TTFT 变差——在线交互向小调、离线批处理向大调。选型：通用在线服务、模型更换频繁或非 NVIDIA 硬件选 vLLM（生态与硬件覆盖最广、Python 定制门槛低）；Agent/多轮对话/结构化输出选 SGLang（RadixAttention 基数树复用共享前缀、FSM 约束解码）；NVIDIA 全栈追求极限性能选 TensorRT-LLM（预先编译 + C++ Runtime）。架构契合度重于一次性 benchmark。（简答，另见 Q5/Q8；对应正文第 4.3/5 节）

</details>

## 🎯 高频面试题解析

以下真题均出自本站面经库（`docs/interview/`），解析要点与正文小节对应。

**Q1：vLLM 在推理调度和 KV Cache 管理方面的核心设计思路是什么？**（蚂蚁 AI Infra 实习一面）
两条主线合起来答：调度上，V1 用**统一 Token 预算**抹平 Prefill/Decode 边界——每步在 `max_num_batched_tokens` 预算内给 running/waiting 请求分 Token 数，Continuous Batching 与 Chunked Prefill 都是这套机制的自然结果（见第 2.2、3.2 节）；KV 管理上，PagedAttention 分块 + 块表映射消灭碎片，`KVCacheManager`/`BlockPool` 以引用计数支撑共享与 Prefix Cache（见第 1.2 节及 2.1 节）。加分项：点出"调度只做决策、执行只跑工单"的分层哲学。

**Q2：描述 vLLM 中 scheduler 的调度流程。**（小厂 AI Infra 实习）
按第 3.2 节顺序讲：waiting/running 两条队列 → 每步先遍历 running（Decode 要 1 个 Token、未完成的 Chunked Prefill 要一段），逐个 `allocate_slots` 并扣预算 → 预算有余再从 waiting 收新请求，先查前缀缓存命中、命中部分免算，Prompt 装不下就截断成 chunk → 产出 `{请求: Token 数}` 的 SchedulerOutput 交给执行层。最好当场画出 3.2 节那个 1024 预算的分配例子。

**Q3：vLLM 中请求被抢占后的后续处理机制是什么？**（小厂 AI Infra 实习）
见第 3.3 节：KV 块分配失败触发抢占，从 running 队尾选牺牲者，释放其全部块、退回 waiting 队头优先恢复；V1 统一用**重计算**——把"原 Prompt + 已生成 Token"当新 Prompt 重新 Prefill，并靠 Prefix Cache 命中未被驱逐的完整块来摊薄重算成本。可对比 V0 还支持 Swap 到 CPU 的历史方案及其 PCIe 开销权衡（2.1 节）。

**Q4：是否阅读过 vLLM 和 SGLang 的底层源码？对其架构有何理解？**（小米 AI Infra 校招）
vLLM 侧按第 1 节五层结构答：入口/EngineCore/Scheduler/KVCacheManager/Worker-ModelRunner，各层核心类与职责，强调 V1 双进程与忙循环；SGLang 侧抓两个招牌：RadixAttention 用基数树管 KV 前缀复用、零开销调度器把 CPU 调度藏进 GPU 执行时间（见第 5.1 节）。答"读过源码"就要能说出类名和数据流向，泛泛说概念反而露怯。

**Q5：vLLM 和 SGLang 有哪些差别？SGLang 的优势体现在哪里？为什么它在推理类大模型上表现更好？**（Teleai AI Infra 实习一面）
差别按第 5.1 节表格的三个维度展开：KV 复用结构（哈希块 vs 基数树）、调度重叠方式、结构化输出支持。SGLang 的优势场景是**共享前缀密集**（多轮对话、Agent 分叉、few-shot 模板）与**约束解码**。推理类大模型（长思维链、DeepSeek 系）表现好的原因：多轮/多采样下 RadixAttention 命中率高，且 SGLang 对 MLA、大规模 EP/PD 分离的优化落地早（见第 5.1、5.2 节）。

**Q6：vLLM 近期有哪些值得关注的新特性？**（阿里巴巴控股集团 AI Infra 一面）
拿 V1 引擎当主菜（见第 2 节）：进程隔离、统一调度、零开销 Prefix Cache 默认开启、Persistent Batch、`torch.compile` + 分段 CUDA Graph，官方口径吞吐约 1.7 倍于 V0。再各补一句延伸：投机解码持续增强（第 5 章）、PD 分离与多机部署生态。这类"开放题"考的是你是否持续跟进社区，答出 V1 架构级变化远好于罗列零碎 feature。

**Q7：如果需要对 vLLM 进行功能定制或二次开发，可以从哪些模块或层面入手？**（Teleai AI Infra 实习一面）
用第 1.2 节的分层对号入座：改请求准入/优先级/SLA 策略 → `Scheduler`；改 KV 复用/驱逐策略 → `KVCacheManager`/`BlockPool`；接自研模型结构 → 模型注册与 `ModelRunner` 层（实现模型类、注册权重映射）；换 Attention 实现 → Attention 后端接口（2.5 节）；改 API 协议/前后处理 → API Server 进程，完全不碰引擎。能按层报出"改哪类需求动哪层"，比背目录结构有说服力得多。

**Q8：比较 TensorRT-LLM 与 vLLM 的源码实现差异。**（腾讯 AI Infra 校招一面）
核心差异一句话：**vLLM 是"运行时解释"路线，TensorRT-LLM 是"预先编译"路线**（见第 5.1 节）。展开三点：执行方式（Python 运行时 + 分段 CUDA Graph vs 编译成 TensorRT 引擎 + C++ Runtime）、灵活性与定制成本（HF 权重直接跑、Python 改调度 vs 构建引擎流程重、C++ 门槛高）、硬件策略（多后端抽象 vs NVIDIA 垂直整合、FP8/FP4 兑现最快）。结论落在选型逻辑（第 5.2 节）而非"谁更强"。
