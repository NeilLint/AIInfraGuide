## 1. 从 Demo 到生产差在哪

一个能跑的推理进程和一个生产服务之间，隔着四个必须回答的问题：

| 问题 | Demo 阶段 | 生产阶段 |
|------|-----------|----------|
| 怎么部署 | 手动 SSH + 命令行 | 镜像化、声明式编排、滚动升级、故障自愈 |
| 怎么知道服务健康 | 肉眼看日志 | 指标、看板、告警、日志聚合 |
| 流量涨了怎么办 | 重新手动起进程 | 自动扩缩容 + 负载均衡 |
| 要花多少钱 | 一张卡先跑着 | 从 SLO 反推集群规模与成本 |

贯穿四个问题的一条主线是 **LLM 推理服务与传统无状态 Web 服务的差异**：

1. **启动极慢**：拉几十 GB 权重、加载到显存、CUDA Graph 捕获，冷启动是分钟级而非秒级——探针、扩容策略、发布策略都要为此重新设计；
2. **单请求成本极高且方差大**：一个请求可能生成 10 个 token 也可能生成 4000 个，按"请求数"做负载均衡和限流会严重失真，要按 token 和并发序列数思考；
3. **有状态**：Prefix Cache、会话内多轮的 KV 复用让"请求打到哪个副本"影响性能，完全随机的负载均衡会浪费缓存；
4. **资源不可超卖**：GPU 显存没有 swap 可言，超了就是 OOM 或抢占，容量规划必须留出确定性的余量。

## 2. 容器化与 Kubernetes 部署

### 2.1 镜像：优先用官方镜像

vLLM 官方提供开箱即用的镜像 `vllm/vllm-openai`，入口就是 OpenAI 兼容 API Server，容器启动参数直接透传给它。除非要打进自定义依赖（私有模型代码、监控 sidecar 依赖等），否则不必自己写 Dockerfile：

```bash
docker run --gpus all \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  -p 8000:8000 --ipc=host \
  vllm/vllm-openai:v0.10.1 \
  --model Qwen/Qwen2.5-7B-Instruct \
  --gpu-memory-utilization 0.90
```

两个容易踩的点：

- **固定镜像版本**。vLLM 迭代很快，`latest` 会导致"昨天还好好的"式故障，生产镜像 tag 必须钉死；
- **共享内存**。张量并行时进程间通过共享内存通信，Docker 默认 `/dev/shm` 只有 64MB，需要 `--ipc=host` 或 `--shm-size`；对应到 K8s 是挂一块 `medium: Memory` 的 emptyDir 到 `/dev/shm`。

需要自建镜像时，Dockerfile 保持最薄：

```dockerfile
FROM vllm/vllm-openai:v0.10.1
# 只叠加自己的依赖，不动基础环境
COPY requirements-extra.txt /tmp/
RUN pip install --no-cache-dir -r /tmp/requirements-extra.txt
```

### 2.2 GPU 资源请求与调度

K8s 原生不认识 GPU，需要节点上装 NVIDIA 驱动 + [NVIDIA Device Plugin](https://github.com/NVIDIA/k8s-device-plugin)（或直接用 GPU Operator 全家桶），之后 GPU 以**扩展资源** `nvidia.com/gpu` 的形式暴露给调度器：

```yaml
resources:
  limits:
    nvidia.com/gpu: "1"
```

和 CPU/内存不同，扩展资源有两条特殊规则：

- **必须写在 limits 里**，且 request 若写必须等于 limit——GPU 不可压缩、不可超卖，没有"request 0.5 卡 limit 1 卡"的说法；
- **默认按整卡分配**。要切分需要 MIG（硬件级切分）或 time-slicing（时间片，无显存隔离），LLM 推理一般整卡起步，不建议 time-slicing。

集群里有多种 GPU 时，用节点标签把 Pod 钉到目标卡型上（GPU Operator 的 gpu-feature-discovery 会自动打上 `nvidia.com/gpu.product` 这类标签）：

```yaml
nodeSelector:
  nvidia.com/gpu.product: NVIDIA-A100-SXM4-80GB
```

### 2.3 模型权重：挂载与拉取策略

几十 GB 的权重放哪里，直接决定冷启动时长。三种主流做法：

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 启动时在线拉取 | 容器起来后从 HF Hub / 对象存储下载 | 最简单，无额外设施 | 冷启动最慢且受外网带宽波动影响；每个副本重复下载 |
| 共享存储挂载 | 权重放 NFS/JuiceFS/OSS-FUSE 等，PVC 挂进容器 | 一份权重多副本共享；发布新模型只换路径 | 共享存储带宽可能成为多副本同时启动时的瓶颈 |
| 节点本地缓存 | initContainer 或 DaemonSet 预热到节点本地 NVMe，再 hostPath/local PV 挂载 | 加载最快，扩容最友好 | 需要额外的预热与淘汰管理 |

生产上常见组合是"对象存储做权重的 source of truth + 节点本地 NVMe 缓存"，并把 HF 缓存目录挂成卷（`HF_HOME` 指过去），保证容器重建不重新下载。**把权重打进镜像是反模式**：镜像会膨胀到几十 GB，镜像仓库、节点磁盘、分发时间全部遭殃，且模型更新被迫重新构建镜像。

### 2.4 探针：模型加载是分钟级的

vLLM 暴露 `/health` 端点，服务器就绪后返回 200。探针设计的核心矛盾：**模型加载 + 显存分配 + CUDA Graph 捕获可能耗时几分钟，而 K8s 探针默认参数是为秒级启动的 Web 服务设计的**。如果只配 livenessProbe 且阈值默认，Pod 会在模型还没加载完时被反复杀掉重启，陷入 CrashLoopBackOff。

正确姿势是三种探针分工：

- **startupProbe** 负责"容忍慢启动"：把 `failureThreshold × periodSeconds` 放大到覆盖最坏加载时长（如 15 分钟），startupProbe 通过之前 liveness/readiness 不生效；
- **readinessProbe** 负责"能不能接流量"：不通过就从 Service 端点摘除，但不杀 Pod；
- **livenessProbe** 负责"进程是否僵死"：连续失败才重启容器，阈值要保守，避免高负载下探针超时引发误杀——雪崩往往就是这么来的（负载高 → 探针超时 → 重启 → 剩余副本负载更高）。

### 2.5 完整 Deployment 示例

把上面的点组装成一份可用的清单（单卡 7B 模型）：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-qwen25-7b
  labels:
    app: vllm-qwen25-7b
spec:
  replicas: 2
  selector:
    matchLabels:
      app: vllm-qwen25-7b
  template:
    metadata:
      labels:
        app: vllm-qwen25-7b
    spec:
      containers:
        - name: vllm
          image: vllm/vllm-openai:v0.10.1
          args:
            - --model=Qwen/Qwen2.5-7B-Instruct
            - --host=0.0.0.0
            - --port=8000
            - --gpu-memory-utilization=0.90
            - --max-model-len=8192
          env:
            - name: HF_HOME
              value: /model-cache
          ports:
            - name: http
              containerPort: 8000
          resources:
            requests:
              cpu: "4"
              memory: 32Gi
              nvidia.com/gpu: "1"
            limits:
              cpu: "8"
              memory: 64Gi
              nvidia.com/gpu: "1"
          volumeMounts:
            - name: model-cache
              mountPath: /model-cache
            - name: shm
              mountPath: /dev/shm
          startupProbe:
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 10
            failureThreshold: 90      # 最长容忍 15 分钟启动
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 6
      volumes:
        - name: model-cache
          persistentVolumeClaim:
            claimName: model-cache-pvc
        - name: shm
          emptyDir:
            medium: Memory
            sizeLimit: 8Gi
---
apiVersion: v1
kind: Service
metadata:
  name: vllm-qwen25-7b
spec:
  selector:
    app: vllm-qwen25-7b
  ports:
    - name: http
      port: 8000
      targetPort: http
```

滚动升级还要注意一点：新副本要几分钟才 Ready，`maxUnavailable` 建议设为 0、`maxSurge` 设为 1，用"先起新再杀旧"避免升级期间容量缺口——代价是升级期间需要额外的 GPU 空余。

### 2.6 vLLM Production Stack 与 KServe 的定位

裸写 Deployment 适合理解原理，规模化之后可以借助上层方案：

- **[vLLM Production Stack](https://github.com/vllm-project/production-stack)**：vLLM 社区官方的 K8s 部署方案（Helm 一键部署），核心增值在**推理感知的 Router**——支持前缀感知路由、会话亲和、按 vLLM 引擎指标做负载感知分发，外加打包好的 Prometheus/Grafana 观测栈和 KV Cache 跨副本共享（对接 LMCache）能力。它解的是"多副本 vLLM 怎么被聪明地路由和观测"这层问题。
- **[KServe](https://kserve.github.io/website/)**：Kubernetes 上通用的模型服务平台，提供 `InferenceService` CRD、标准化推理协议、Serverless 缩容到零、金丝雀发布等平台能力，vLLM 可以作为它的一种 runtime 接进去。它解的是"公司里几十种模型（不只 LLM）如何统一托管"这层问题。

选型直觉：只服务 LLM、追求 vLLM 特性利用最充分，用 Production Stack；已有多模型统一 Serving 平台诉求或已在用 Kubeflow 生态，用 KServe 托管 vLLM。

## 3. 可观测性

### 3.1 vLLM /metrics 端点的关键指标

vLLM 的 OpenAI 兼容 Server 原生在 `/metrics` 暴露 Prometheus 格式指标（前缀 `vllm:`），这是运维的"仪表盘信号源"。关键指标逐个过：

| 指标 | 类型 | 含义与运维视角 |
|------|------|----------------|
| `vllm:e2e_request_latency_seconds` | Histogram | 请求端到端延迟分布。用户体感的最终口径，SLO 对账用它 |
| `vllm:time_to_first_token_seconds` | Histogram | TTFT 分布。恶化通常意味着排队变长或 prefill 压力大 |
| `vllm:time_per_output_token_seconds` | Histogram | TPOT（出字间隔）分布。恶化意味着 decode batch 过大或被 prefill 干扰 |
| `vllm:request_queue_time_seconds` | Histogram | 请求在调度队列里的等待时间。TTFT 高时先看它，区分"排队慢"还是"算得慢" |
| `vllm:num_requests_running` | Gauge | 正在 decode 的并发序列数。对照 `max_num_seqs` 看饱和度 |
| `vllm:num_requests_waiting` | Gauge | 等待调度的请求数。**最直接的过载信号**，持续大于 0 说明容量不够，是扩容的首选指标 |
| `vllm:gpu_cache_usage_perc` | Gauge | KV Cache 已用比例（0~1）。逼近 1.0 意味着即将发生抢占或无法接新请求 |
| `vllm:num_preemptions_total` | Counter | 累计抢占次数。KV 空间不足时请求被换出重算，抢占率上升 = 有效算力在被重复计算浪费，必须处理 |
| `vllm:prompt_tokens_total` / `vllm:generation_tokens_total` | Counter | 累计处理的输入/输出 token 数，`rate()` 之后就是实时吞吐（tokens/s） |
| `vllm:request_success_total` | Counter | 完成请求计数，带 `finished_reason` 标签（stop/length/abort），可观察异常截断与客户端断连比例 |

几条常用 PromQL：

```promql
# P99 TTFT（5 分钟窗口）
histogram_quantile(0.99,
  sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))

# 集群实时生成吞吐 tokens/s
sum(rate(vllm:generation_tokens_total[1m]))

# 每副本平均等待队列长度
avg(vllm:num_requests_waiting)
```

采集侧用 Prometheus Operator 的话，一个 PodMonitor 即可（端口名对应 2.5 节的 `http`）：

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: vllm-qwen25-7b
spec:
  selector:
    matchLabels:
      app: vllm-qwen25-7b
  podMetricsEndpoints:
    - port: http
      path: /metrics
      interval: 15s
```

### 3.2 Grafana 看板思路

看板不是指标的堆砌，按"回答问题"来组织，自上而下四行：

1. **用户在经历什么**：QPS、错误率、E2E/TTFT/TPOT 的 P50/P95/P99 曲线——SLO 达成情况一眼可见；
2. **引擎有多满**：running/waiting 请求数、`gpu_cache_usage_perc`、抢占速率——回答"该不该扩容"；
3. **吞吐结构**：prompt tokens/s 与 generation tokens/s 分开画——输入输出比例变化往往解释了延迟的突变（比如某客户开始灌长文档）；
4. **资源底座**：DCGM 的 GPU 利用率、显存、温度/功耗，节点 CPU 与网络——定位是引擎问题还是基础设施问题。

vLLM 仓库 `examples` 目录和 Production Stack 都提供现成的 Grafana Dashboard JSON，可以直接导入再裁剪。

### 3.3 日志与告警

日志侧：开 `--uvicorn-log-level warning` 压掉访问日志噪音，业务侧在网关打印结构化的 request_id / 用户 / token 用量日志；vLLM 自身的关键日志（抢占警告、CUDA OOM、watchdog）要进日志聚合系统并配关键字告警。

告警规则示例（阈值均为示例，按自己的 SLO 调整）：

```yaml
groups:
  - name: vllm-alerts
    rules:
      - alert: VllmHighTTFT
        expr: |
          histogram_quantile(0.99,
            sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m]))) > 2
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "P99 TTFT 超过 2s，检查队列与容量"
      - alert: VllmQueueBacklog
        expr: sum(vllm:num_requests_waiting) > 20
        for: 3m
        labels: { severity: critical }
        annotations:
          summary: "等待队列持续积压，容量不足或副本异常"
      - alert: VllmPreemptionStorm
        expr: sum(rate(vllm:num_preemptions_total[5m])) > 0.5
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "KV Cache 抢占频发，考虑降 max_num_seqs 或扩容"
```

告警分层的原则：**症状告警（SLO 违约）打电话，原因指标（KV 利用率高、队列长）发消息**——只对用户可感知的问题升级到 on-call。

## 4. 自动扩缩容与负载均衡

### 4.1 HPA：别用 GPU 利用率，用负载指标

LLM 推理副本只要有流量，GPU 利用率长期接近 100%，**用 GPU 利用率做扩缩容指标基本不可用**；CPU 利用率更是无关信号。正确的扩容信号是"引擎排队程度"：

- `vllm:num_requests_waiting`（首选：队列长度直接反映容量缺口）；
- `vllm:gpu_cache_usage_perc`（KV 利用率持续高位 = 逼近抢占）；
- 每副本并发数或 P95 TTFT（更贴 SLO，但噪声大）。

自定义指标进 HPA 有两条路：Prometheus Adapter 把 PromQL 映射成 custom metrics API，或者用 KEDA 直接查 Prometheus。KEDA 写法更直观：

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: vllm-qwen25-7b
spec:
  scaleTargetRef:
    name: vllm-qwen25-7b       # 指向 Deployment
  minReplicaCount: 2
  maxReplicaCount: 12
  cooldownPeriod: 600           # 缩容冷却 10 分钟
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc:9090
        query: |
          sum(vllm:num_requests_waiting{app="vllm-qwen25-7b"})
        threshold: "10"          # 平均每副本积压 10 个请求即扩容
```

### 4.2 扩容必须考虑冷启动

新副本从调度到 Ready 要经历"调度 → 拉镜像 → 加载权重 → 引擎初始化"，动辄 5~10 分钟。这改变了扩缩容策略的设计：

- **提前扩**：阈值要留出冷启动窗口的余量，宁可早扩少量，不可临界才扩；对有规律的流量（工作日早高峰）直接上定时扩容（CronHPA / KEDA cron trigger），预测优于响应；
- **缩容要慢**：激进缩容 + 流量回弹 = 为一次抖动付出 10 分钟的容量缺口，缩容冷却窗口设长（10 分钟级）、每次只缩一个；
- **压缩冷启动本身**：镜像预拉取（DaemonSet 预热）、权重节点本地缓存（2.3 节）、必要时保留少量"温备"副本。

### 4.3 前缀感知路由：负载均衡不只是均匀

K8s Service 的默认负载均衡是随机/轮询，对无状态服务没问题，对 LLM 推理却会**系统性地打散 Prefix Cache**：同一 Agent 系统的几千个请求共享同一个长 System Prompt，如果均匀撒到 8 个副本，每个副本都要各自 prefill 一遍这个前缀；如果按前缀路由到固定副本，后续请求直接命中缓存，TTFT 大幅下降。

前缀感知（Prefix-aware）路由的做法：路由层对请求前缀（或会话 ID）做一致性哈希，把相同前缀的请求粘到同一副本，同时叠加负载上限防止热点副本过载——"缓存亲和"与"负载均衡"两个目标加权折中。vLLM Production Stack 的 Router、SGLang 的 cache-aware routing 都是这个思路的实现。多轮对话场景同理：会话粘性让第 N 轮命中前 N-1 轮的 KV。

### 4.4 网关层：认证与 TLS，不能裸奔

⚠️ **vLLM 的 OpenAI 兼容服务默认没有任何认证**。`--api-key` 只提供单一静态 key 的最低限度校验，也不做限流、计费、审计。把 vLLM 端口直接暴露公网，等于把 GPU 算力和模型开放给全网扫描器——生产部署的铁律是 vLLM 只监听集群内网，前面必须有一层网关（Ingress + API Gateway，如 Kong/APISIX/Higress，或云厂商网关）：

- **认证**：API Key / JWT / mTLS，按租户区分；
- **TLS 终结**：证书在网关层统一管理（cert-manager 自动签发轮转）；
- **限流与配额**：按租户限 QPS 和 token 配额，防止单一用户打爆队列拖垮所有人的 SLO；
- **审计与计费**：网关日志记录 request_id、用户、输入输出 token 数（vLLM 响应的 `usage` 字段）。

## 5. 容量规划

### 5.1 方法：从 SLO 反推，而不是拍脑袋

容量规划回答"满足 SLO 需要几张卡"，标准推演链路是四步：

1. **定义 SLO 与流量模型**：延迟目标（如 P99 TTFT、P99 TPOT）+ 峰值 QPS + 请求形状（平均输入/输出 token 数及其分布）。请求形状必须来自真实流量采样，输入 200 token 和 2000 token 的容量结论差好几倍；
2. **单副本压测出"SLO 内极限吞吐"**：用固定的请求形状，从低到高扫 request rate，找到 P99 延迟恰好还满足 SLO 的最大 QPS。注意要的不是"引擎最大吞吐"（那是延迟爆表时的数字），而是**满足延迟约束下的吞吐**；
3. **乘冗余系数**：覆盖突发流量、滚动发布占用、单点故障（N+1）、指标测量误差，常取 1.3~1.5；
4. **算副本数与成本**：

$$
N_{replicas} = \left\lceil \frac{QPS_{peak} \times k_{redundancy}}{QPS_{per\_replica}^{SLO}} \right\rceil
$$

压测工具直接用 vLLM 自带的 benchmark（旧版本对应 `benchmarks/benchmark_serving.py` 脚本）：

```bash
vllm bench serve \
  --model Qwen/Qwen2.5-7B-Instruct \
  --base-url http://vllm-qwen25-7b:8000 \
  --dataset-name random \
  --random-input-len 1200 --random-output-len 350 \
  --request-rate 4 --num-prompts 500
```

对 `--request-rate` 取 1/2/3/4/5… 逐档执行，记录每档的 P99 TTFT/TPOT，画出"延迟-负载"曲线，SLO 线与曲线的交点就是单副本极限。

### 5.2 一个完整的数值推演

**以下所有数字均为示例假设，用于演示方法，不代表任何真实机型/模型的实测结果。**

场景设定（示例假设）：

- 模型：7B 级对话模型，单卡 80GB GPU 一副本；
- SLO：P99 TTFT ≤ 2s，P99 TPOT ≤ 60ms，错误率 < 0.1%；
- 流量：峰值 30 QPS，平均输入 1200 token、输出 350 token。

第一步，单副本压测（示例假设的结果）：

| request rate (QPS) | P99 TTFT | P99 TPOT | 是否满足 SLO |
|---:|---:|---:|:---:|
| 2 | 0.6s | 35ms | ✅ |
| 3 | 0.9s | 42ms | ✅ |
| 4 | 1.5s | 55ms | ✅（临界） |
| 5 | 3.8s | 78ms | ❌ 队列开始积压 |

结论：单副本 SLO 内极限吞吐 ≈ **4 QPS**（示例假设）。

第二步，取冗余系数 1.5（覆盖突发 + 滚动发布期 maxSurge 占用 + 任一副本故障后其余副本仍不违约）：

$$
N = \left\lceil \frac{30 \times 1.5}{4} \right\rceil = \lceil 11.25 \rceil = 12 \text{ 副本} = 12 \text{ 张卡}
$$

第三步，算成本（示例假设：每卡每小时 $2 的云价）：

$$
12 \text{ 卡} \times \$2/\text{h} \times 720 \text{ h/月} \approx \$17{,}280/\text{月}
$$

第四步——这一步最能体现容量规划的价值——**敏感性分析**：如果通过开启 Prefix Cache（System Prompt 命中率高）+ 调优把单副本极限从 4 QPS 提到 6 QPS，副本数降到 $\lceil 45/6 \rceil = 8$，月成本降到约 $11,520，省 1/3。这就是前几章所有优化技术在财务报表上的样子：**优化单副本吞吐 = 直接砍集群账单**。

### 5.3 显存维度的约束检查

吞吐推演之外还要验证显存装得下：权重 + 激活 + KV Cache 预算决定了 `max_model_len` 与 `max_num_seqs` 的可行组合（估算公式见第 1 章：权重 ≈ 参数量 × 每参数字节数，KV ≈ 2 × 层数 × token 数 × KV 头数 × head_dim × 字节数 × 并发数）。如果压测中 `gpu_cache_usage_perc` 早早顶满、抢占频发，说明瓶颈在 KV 空间而不是算力，此时的解法是换大显存卡型、量化 KV Cache、或降低单副本并发并靠加副本补吞吐——三个方案的成本不同，要重新过一遍上面的推演。

---

## 6. 总结

1. LLM 推理服务是"启动分钟级、单请求昂贵、有状态、资源不可超卖"的特殊服务，四个特性决定了部署、观测、扩缩容、容量规划都不能照搬无状态 Web 服务的做法；
2. K8s 部署三件关键小事：`nvidia.com/gpu` 写在 limits、权重走共享存储/本地缓存而非打进镜像、用 startupProbe 容忍分钟级冷启动；
3. 可观测性以 vLLM `/metrics` 为核心信号源：延迟三件套（E2E/TTFT/TPOT 直方图）看体验，waiting 队列与 KV 利用率看饱和，抢占计数看资源浪费；
4. 扩缩容用队列长度/KV 利用率而非 GPU 利用率，策略要为冷启动留提前量；负载均衡要前缀感知；vLLM 无认证，公网前面必须有网关做认证 + TLS + 限流；
5. 容量规划的标准链路：SLO + 请求形状 → 单副本 SLO 内极限压测 → 冗余系数 → 副本数与成本，并用敏感性分析把"推理优化"翻译成"成本节约"。

## ✅ 自我检验清单

**1. 能说出 LLM 推理服务区别于无状态 Web 服务的四个特性，及每条的运维含义**

<details>
<summary>参考答案</summary>

- **启动极慢**：拉几十 GB 权重 + 加载显存 + CUDA Graph 捕获，冷启动是分钟级——探针、扩容策略、发布策略都要为此重新设计。
- **单请求成本高且方差大**：一个请求可能生成 10 个也可能生成 4000 个 token，按"请求数"做负载均衡和限流会严重失真，要按 token 与并发序列数思考。
- **有状态**：Prefix Cache 与会话内多轮 KV 复用让"请求打到哪个副本"影响性能，完全随机的负载均衡会浪费缓存。
- **资源不可超卖**：GPU 显存没有 swap，超了就是 OOM 或抢占，容量规划必须留确定性余量。四条合起来决定部署、观测、扩缩容、容量规划都不能照搬无状态服务的做法。（对应第 1、6 节）

</details>

**2. 能解释 K8s 中 GPU 作为扩展资源的两条特殊规则，以及 vLLM 容器化的两个易踩点**

<details>
<summary>参考答案</summary>

- 扩展资源 `nvidia.com/gpu`（由 NVIDIA Device Plugin / GPU Operator 暴露）的两条规则：必须写在 limits 里、request 若写必须等于 limit——GPU 不可压缩、不可超卖；默认按整卡分配，切分要 MIG（硬件级）或 time-slicing（无显存隔离，LLM 推理不建议），多卡型集群用 `nvidia.com/gpu.product` 节点标签钉卡型。
- 容器化易踩点一：镜像 tag 必须钉死版本，`latest` 会造成"昨天还好好的"式故障。
- 易踩点二：张量并行进程间靠共享内存通信，Docker 默认 `/dev/shm` 只有 64MB，需 `--ipc=host` 或 `--shm-size`；对应 K8s 是挂 `medium: Memory` 的 emptyDir 到 `/dev/shm`。（对应 2.1、2.2 节；另见 Q3）

</details>

**3. 能对比三种权重加载策略，并说出为什么"权重打进镜像"是反模式**

<details>
<summary>参考答案</summary>

- 三种策略：启动时在线拉取（最简单，但冷启动最慢、每副本重复下载）；共享存储挂载（一份权重多副本共享，但多副本同时启动时共享存储带宽可能成瓶颈）；节点本地 NVMe 缓存（加载最快、扩容最友好，需额外的预热与淘汰管理）。
- 生产常见组合："对象存储做 source of truth + 节点本地 NVMe 缓存"，HF 缓存目录挂成卷（`HF_HOME` 指过去）保证容器重建不重新下载。
- 打进镜像是反模式：镜像膨胀到几十 GB，镜像仓库、节点磁盘、分发时间全部遭殃，且模型更新被迫重新构建镜像。（对应 2.3 节）

</details>

**4. 能设计适配分钟级模型加载的三探针分工，并说出误配引发雪崩的链路**

<details>
<summary>参考答案</summary>

- 核心矛盾：模型加载 + 显存分配 + CUDA Graph 捕获可能耗时几分钟，而 K8s 探针默认参数是为秒级启动设计的——只配默认阈值的 livenessProbe，Pod 会在加载完成前被反复杀掉，陷入 CrashLoopBackOff。
- 三探针分工：startupProbe 容忍慢启动（`failureThreshold × periodSeconds` 放大到覆盖最坏加载时长，如 15 分钟，它通过前 liveness/readiness 不生效）；readinessProbe 决定能否接流量（不通过只摘除端点、不杀 Pod）；livenessProbe 判进程僵死（连续失败才重启，阈值保守）。
- 雪崩链路：负载高 → 探针超时 → 重启 → 剩余副本负载更高。滚动升级另配 `maxUnavailable=0`、`maxSurge=1`，先起新再杀旧，代价是升级期需额外 GPU 空余。（对应 2.4、2.5 节）

</details>

**5. 能从 vLLM /metrics 里挑出定位问题的关键指标并说明读法**

<details>
<summary>参考答案</summary>

- 延迟三件套 Histogram：`e2e_request_latency` 对账 SLO，TTFT 恶化通常是排队变长或 prefill 压力大，TPOT 恶化是 decode batch 过大或被 prefill 干扰。
- TTFT 高先看 `request_queue_time_seconds`，区分"排队慢"还是"算得慢"；`num_requests_waiting` 是最直接的过载信号，持续大于 0 说明容量不够，是扩容首选指标。
- `gpu_cache_usage_perc` 逼近 1.0 意味着即将抢占；`num_preemptions_total` 上升 = 有效算力在被重复计算浪费，必须处理；`prompt/generation_tokens_total` 做 `rate()` 得实时吞吐。（对应 3.1 节；另见 Q1）

</details>

**6. 能按"回答问题"组织 Grafana 四层看板，并说出告警分层原则**

**7. 能解释为什么 GPU 利用率不能做扩缩容指标、正确信号是什么、冷启动如何改变扩缩容策略**

<details>
<summary>参考答案</summary>

- LLM 副本只要有流量 GPU 利用率就长期接近 100%，没有区分度，CPU 利用率更是无关信号；正确信号是"引擎排队程度"：`num_requests_waiting`（首选）、`gpu_cache_usage_perc`、每副本并发或 P95 TTFT（贴 SLO 但噪声大），经 Prometheus Adapter 或 KEDA 接进 HPA。

**8. 能解释前缀感知路由的动机与做法，以及 vLLM 端口"裸奔"的风险与网关职责**

<details>
<summary>参考答案</summary>

- 动机：随机/轮询会系统性打散 Prefix Cache——共享同一长 System Prompt 的几千个请求均匀撒到 8 个副本，每个副本都要各自 prefill 一遍前缀；按前缀路由到固定副本则后续请求直接命中缓存，TTFT 大幅下降。

- 安全：vLLM 默认没有任何认证，`--api-key` 只是单一静态 key，不做限流/计费/审计；铁律是只监听集群内网，前置网关做认证（API Key/JWT/mTLS）、TLS 终结、按租户限流配额、审计计费（记录 `usage` 字段的 token 数）。（对应 4.3、4.4 节）

## 7. 高频面试题解析

**Q1：在高并发条件下，如何对推理服务进行压力测试以确定其能承受的最大并发量？需要重点监控哪些指标？**（Teleai 实习一面原题）
分两层答。方法：固定请求形状（输入/输出长度分布取自真实流量），用 `vllm bench serve` 之类的压测工具从低到高逐档扫 request rate / 并发数，每档跑足量请求，画"延迟-负载"曲线；"最大并发量"要给两个口径——延迟不设约束的引擎饱和吞吐，和满足 SLO（P99 TTFT/TPOT 阈值）的极限吞吐，生产容量按后者算。指标：客户端侧看 QPS、错误率、P50/P99 的 TTFT/TPOT/E2E 延迟与总吞吐（tokens/s）；引擎侧看 running/waiting 请求数（实际 batch 饱和度与排队）、`gpu_cache_usage_perc`、抢占次数；硬件侧看 GPU 利用率与显存。判断饱和的信号是 waiting 持续大于 0、延迟曲线拐点、或抢占开始出现（呼应 5.1、3.1 节）。

**Q2：是否用 vLLM 部署过模型？实测吞吐量为多少？**（小米校招原题）
这题考的是你有没有真部署过——报吞吐数字必须带条件，否则就是没做过的信号。规范答法：模型与精度、卡型与并行度、请求形状（输入/输出长度）、并发/request rate、开了哪些特性（Prefix Cache、Chunked Prefill 等），然后分别报饱和吞吐（tokens/s）与 SLO 内吞吐（QPS），再补一句瓶颈定位（如"KV 利用率先顶满，属显存瓶颈"）。参考 5.1 节的压测方法与 5.2 节的报告口径。

**Q3：K8s 中 request 与 limit 的底层实现原理是什么？**（百度校招原题）
request 作用于**调度期**：scheduler 只把 Pod 放到"节点可分配量 −已有 request 之和"装得下的节点，不管实际用量。limit 作用于**运行期**，由 kubelet 通过 cgroup 落实：CPU limit 写入 CFS 带宽控制（cgroup v2 的 `cpu.max`，即配额/周期），超了被节流不被杀；CPU request 写入 `cpu.weight`（v1 的 `cpu.shares`），决定争抢时的相对份额；内存 limit 写入 `memory.max`，超限触发 OOM Kill。而 `nvidia.com/gpu` 是扩展资源，只参与调度记账并由 device plugin 分配具体设备，没有 cgroup 级的算力隔离，且 request 必须等于 limit、不可超卖（呼应 2.2 节）。

**Q4：K8s 中 Pod 的创建流程是怎样的？CSI 与 CNI 分别在哪个阶段被调用？**（百度校招原题）
流程：kubectl/控制器写入 apiserver → 持久化到 etcd → scheduler watch 到未绑定 Pod，过滤打分后写 binding → 目标节点 kubelet watch 到 Pod，依次做准入检查、卷准备、通过 CRI 创建 sandbox 与容器、启动探针。两个插件的时机：**CSI 在容器启动前**由 kubelet 的 volume 管理流程调用（controller 侧 attach，node 侧 stage/mount），卷挂好才会起容器；**CNI 在创建 pause/sandbox 容器时**由容器运行时调用，负责给 Pod 配网卡和 IP。所以顺序上大体是：调度 → 卷 attach/mount（CSI）→ sandbox 创建与网络配置（CNI）→ 业务容器启动（呼应 2.5 节的部署清单在集群里的落地过程）。

**Q5：Kubernetes 的基本架构是什么？**（文远知行校招一面原题）
控制面：apiserver（唯一入口与状态存取）、etcd（状态存储）、scheduler（选节点）、controller-manager（把实际状态向期望状态收敛）；数据面每节点：kubelet（管 Pod 生命周期）、kube-proxy（Service 转发规则）、容器运行时。核心对象自下而上：容器 < Pod（最小调度单位，同 Pod 容器共享网络与卷）< Deployment/ReplicaSet（副本与滚动升级）< Service/Ingress（服务发现与接入）。答完基础可以主动延伸一句 GPU 场景的差异（device plugin 扩展资源、探针要适配分钟级启动），把问题拉回本节主场（呼应 2.2、2.4 节）。

**Q6：V100 的显存是多少？32B 模型 INT8 量化后能否在 V100 上运行？部署方案是什么？**（Teleai 实习一面原题）
V100 有 16GB 和 32GB 两种规格。32B 模型 INT8 权重约 32GB（每参数 1 字节），还要加激活、KV Cache 和运行时开销——32GB 单卡也放不下，16GB 更不行。可行方案：两张 V100-32G 做 TP=2，每卡权重约 16GB，剩余十几 GB 给 KV Cache，能跑但上下文与并发有限；或者 INT4 权重量化（约 16GB）后单卡 32G 勉强可行。还要主动提硬件代际约束：V100 是 Volta 架构，无 INT8 Tensor Core 加速的现代量化 kernel 支持普遍较差（很多 W8A8/FP8 方案不支持 Volta），实际常退化为 weight-only 量化 + FP16 计算，收益主要在省显存而非提速。这题的完整答法就是 5.3 节的显存约束检查：权重 + KV + 激活逐项列预算，再给并行/量化组合方案。
