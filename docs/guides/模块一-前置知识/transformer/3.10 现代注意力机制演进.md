## 1. 演进的两条主线

标准 Multi-Head Attention 在推理时代暴露出两个相互独立的瓶颈：

**瓶颈一：KV Cache 显存**。自回归生成时每个 token 的 K/V 都要缓存。以 MHA、128 头、head_dim 128、FP16 计算，单 token 单层的 KV Cache 就是 $2 \times 128 \times 128 \times 2\text{B} = 64\text{KB}$，61 层模型在 128K 上下文下单条请求就要吃掉数百 GB 显存。KV Cache 的大小直接决定了推理引擎能组多大的 batch，进而决定吞吐上限。

**瓶颈二：$O(L^2)$ 计算复杂度**。注意力分数矩阵的计算量随序列长度平方增长。在 128K 以内，FlashAttention 类 kernel 还能靠 IO 优化硬扛；到了百万 token 级别，平方复杂度在算力上就是不可接受的——这也是"长上下文/Agent 时代"逼着注意力机制重新设计的根本原因。

围绕这两个瓶颈，演进出两条主线（外加一条激进路线）：

| 主线 | 思路 | 代表工作 |
|------|------|----------|
| **压缩 KV 表示** | 减少每个 token 缓存的 KV 大小 | MQA → GQA → MLA |
| **稀疏化注意力** | 每个 query 只看一部分 KV | SWA → MoBA / NSA → DSA → CSA/HCA |
| **线性化（激进路线）** | 放弃 softmax 精确注意力，状态压缩成固定大小 | Lightning Attention、Gated DeltaNet、KDA |

理解这张图后，后面每一节都可以定位到"它在哪条主线上、解决哪个瓶颈"。DeepSeek 的路线特别值得关注：**V2/V3 用 MLA 解决 KV 显存（主线一），V3.2 用 DSA 解决平方计算（主线二），V4 用 CSA+HCA 把两条主线合并**——这条演进链是当前面试最爱考的叙事。

## 2. 快速回顾 MHA MQA GQA

这部分 3.3 节第 9 章已详细展开，这里只留一张对照表作为后文的基准：

| 机制 | KV 头数 | 单 token 单层 KV Cache（FP16，128 头 × 128 维） | 代表模型 |
|------|---------|------------------------------------------|----------|
| MHA | $h = 128$ | $2 \times 128 \times 128 \times 2\text{B} = 64\text{KB}$ | GPT-3、早期 LLaMA |
| GQA | $g = 8$ | $2 \times 8 \times 128 \times 2\text{B} = 4\text{KB}$ | LLaMA-2/3、Qwen2.5、Mistral |
| MQA | $1$ | $2 \times 1 \times 128 \times 2\text{B} = 0.5\text{KB}$ | PaLM、Falcon |

记住一个基准数字：**BF16 的 GQA-8（head_dim 128）是当前"常规注意力"的典型配置**，后文 DeepSeek V4 的"KV Cache 降到 GQA8 基线的约 2%"就是相对它而言的。

## 3. MLA 深入理解与矩阵吸收

MLA（Multi-head Latent Attention，DeepSeek-V2 提出，V3/R1 沿用）是面试出现频率最高的注意力变种，考法从"讲思路"到"手写实现"再到"分析 decode 计算访存比"都有。这一节不着急上公式，先把"KV Cache 里到底存了什么"算清楚，再一步步推到矩阵吸收。

### 3.1 先算清楚问题：KV Cache 到底在存什么

自回归生成时，每个新 token 的 query 都要和**前面所有 token** 的 K、V 做注意力。前面 token 的 K/V 每一步都会被用到、而且永远不变——重算太亏，所以全部缓存下来，这就是 KV Cache。

它有多大？以 DeepSeek-V3 的规格（128 个头、每头 128 维）算，**每个 token 每一层**要存：

$$
\underbrace{2}_{K\ 和\ V\ 各一份} \times \underbrace{128}_{\text{头数}} \times \underbrace{128}_{\text{每头维度}} = 32768 \text{ 个数}
$$

乘上 61 层、128K 上下文、FP16 两字节——**一条请求约 490 GB**。一张 80GB 的显卡连一条都装不下，更别提组 batch。所以第 1 节说的"压缩 KV"主线，砍的就是这个 32768。

MQA/GQA 的砍法是砍"头数"那一项（128 → 8 → 1），代价是牺牲头的多样性。MLA 的砍法完全不同：**头一个不砍，把"每个 token 存的内容"整体换成一个压缩包**。

### 3.2 低秩联合压缩：不存 256 份成品，存 1 份浓缩原料

关键观察：128 个头的 K 和 V（共 256 份向量）全都是从**同一个**隐状态 $\mathbf{h}_t$ 用不同矩阵投影出来的——同一份原料的 256 种加工品，彼此高度冗余。那么与其缓存 256 份成品，不如只存一小份"浓缩原料"，要用哪个头的 K/V 就现场加工哪个。

落到公式上，就是先把 $\mathbf{h}_t$（V3 中 7168 维）降维成一个很小的 latent 向量：

$$
\mathbf{c}_t^{KV} = W^{DKV} \mathbf{h}_t \in \mathbb{R}^{512} \qquad \text{（7168 维} \to \text{512 维，所有 128 个头共享这一份）}
$$

需要时再"解压"回每个头的 K 和 V：

$$
\mathbf{k}_t^{C} = W^{UK} \mathbf{c}_t^{KV}, \quad \mathbf{v}_t^{C} = W^{UV} \mathbf{c}_t^{KV} \qquad (W^{UK}, W^{UV}: 512 \to 128\text{头} \times 128\text{维})
$$

$D$ 是 down（压缩）、$U$ 是 up（解压）。这就是"低秩联合压缩"：**低秩**指 512 远小于原始维度，**联合**指 K 和 V 共用同一个压缩包。（query 侧也做了类似压缩，降到 1536 维，但那只为省训练显存，与 KV Cache 无关，可以先忽略。）

到这里账面很漂亮：每 token 似乎只要存 512 个数了？还差一步——**位置信息还没处理**，这是 MLA 最精妙、也最容易被面试官追问的地方。

### 3.3 RoPE 卡在哪里：为什么要单开一条位置分支

一句话回顾 RoPE：它把"第几个位置"编码成**旋转角度**，直接把 Q、K 向量转过相应角度，注意力分数就自动携带了相对距离信息。

问题来了：RoPE 的旋转要打在 K 上，可**压缩包里的 K 是"还没出生"的**——它要等解压才存在。两条路都走不通：

- 解压之后再旋转？那每次读缓存都必须真的解压，下一节的"免解压"优化就彻底做不了了；
- 把旋转预先"焊"进解压矩阵？也不行——旋转角度取决于 query 和 key 的**相对距离** $t-s$，是查询发生时才知道的量，没法提前固化进一个静态矩阵。形式上看：$q_t^T k_s = (W^{UQ}\mathbf{c}_t)^T\, R_{t-s}\, (W^{UK}\mathbf{c}_s)$，中间那个随距离变化的 $R_{t-s}$ 把两侧的矩阵隔开，谁也合并不了。

MLA 的解法很务实——**位置信息不进压缩包，单开一条小分支**：额外投影一个 64 维的 $\mathbf{k}_t^{R}$（所有头共享，只有它携带 RoPE），每个头做注意力时把"压缩分支解压出的内容"和"位置分支"**拼接**起来用：

$$
\mathbf{k}_{t,i} = [\underbrace{\mathbf{k}_{t,i}^{C}}_{\text{内容，128 维}};\ \underbrace{\mathbf{k}_t^{R}}_{\text{位置，64 维}}], \qquad \mathbf{q}_{t,i} = [\mathbf{q}_{t,i}^{C};\ \mathbf{q}_{t,i}^{R}]
$$

这就是"解耦 RoPE"（decoupled RoPE）。于是每个 token 每层真正要缓存的只有两样：

$$
\underbrace{\mathbf{c}_t^{KV}}_{512} + \underbrace{\mathbf{k}_t^{R}}_{64} = 576 \text{ 个数} \qquad \text{vs MHA 的 } 32768 \text{ 个数} \Rightarrow \text{压缩约 } 93.3\%
$$

——这就是 DeepSeek-V2 论文里那个著名数字的来源。

### 3.4 矩阵吸收：其实根本不用解压

面试高频追问："每步都要把压缩包解压回 K/V，不是更慢吗？"答案是：**解压这一步可以在数学上被消掉**，这就是矩阵吸收（matrix absorption）。

先看一个类比：把人民币换成日元，可以先换美元再换日元（两步），也可以事先把两段汇率乘好，直接用"人民币→日元"的一张汇率表（一步）。矩阵乘法满足结合律，同样的合并对注意力分数成立——"先解压 K、再与 q 点积"等价于"把解压矩阵**预先乘进 q 的投影**里"：

$$
(\mathbf{q}_{t,i}^{C})^T \mathbf{k}_{s,i}^{C} = (W_i^{UQ} \mathbf{c}_t^{Q})^T (W_i^{UK} \mathbf{c}_s^{KV}) = \mathbf{c}_t^{Q,T} \underbrace{(W_i^{UQ,T} W_i^{UK})}_{\text{离线提前算好}} \mathbf{c}_s^{KV}
$$

合并之后，query 直接在 512 维压缩空间里与缓存的 $\mathbf{c}^{KV}$ 做内积——**压缩包从头到尾没被解开过**。V 侧同理：$W^{UV}$ 可以吸收进输出投影 $W^O$。（这也解释了 3.3 节为什么必须把 RoPE 解耦出去：位置分支若混在里面，中间就会卡一个随距离变化的旋转矩阵，合并不了。）

吸收之后，decode 阶段的注意力变成了什么样子？

- 缓存里只有一份 $[\mathbf{c}^{KV}; \mathbf{k}^R]$（576 维）——**相当于只有 1 个 KV 头**；
- 128 个 query 头（投影已各自吸收成 576 维）**都对着这同一份缓存**做注意力。

——结构上就是一个 **head_dim = 576 的 MQA**。这直接回答了另一道面经题（"给定 hidden_size 和 RoPE 维度，MLA 对应多少个 GQA head？"）：按缓存量折算，$576 / (2 \times 128) = 2.25$，即 MLA 的缓存只相当于 **2.25 组 GQA**——但注意，2 组的 GQA 表达能力会明显下降，而 MLA 的 128 个头各自保有独立的注意力分布。"效果接近 MHA、缓存接近 MQA"，就是靠"压缩包 + 免解压"这两步实现的。

### 3.5 意外之喜：decode 从"搬运工"变成"计算工"

进阶面经题："如何分析 MLA decode 的计算访存比？"先补一个背景：GPU 的算力远大于显存带宽——从显存每搬 1 个字节的时间，够做几十次浮点运算。所以 decode 阶段谁快谁慢，往往不看算得多快，而看**每搬一个数能干多少活**（算术强度）。

- MQA/GQA decode：每读入一个 KV 数，只有对应的那（几）个 query 头用它做 1 次乘加——算术强度约为 1，GPU 绝大部分时间在等数据（memory-bound），算力闲置；
- MLA 吸收后：128 个 query 头**共享同一份** 576 维缓存，每读入一个数，要与 128 个头各做一次乘加——**算术强度直接 ×128**，decode 被从"等搬运"拉向"忙计算"（compute-bound）。

追问要点：这个比值与序列长度基本无关（每个位置的计算/访存模式相同），与 batch size 也解耦（分子分母同步放大）；真正决定它的是 **query 头数 $h$**。这也是 FlashMLA 这类专用 kernel 能在 Hopper 上跑出很高 MFU 的原因。

### 3.6 手写 MLA 的最小实现

字节等公司考过"手写 MLA"。抓住三个要点即可：低秩压缩、解耦 RoPE、拼接后做标准注意力（训练态写法，不含吸收优化）：

```python
class MLA(nn.Module):
    def __init__(self, d=7168, n_heads=128, d_head=128, d_c=512, d_cq=1536, d_rope=64):
        super().__init__()
        self.n_heads, self.d_head, self.d_rope = n_heads, d_head, d_rope
        # KV 压缩分支：h_t -> c_kv (512)，这是唯一要缓存的主体
        self.w_dkv = nn.Linear(d, d_c, bias=False)
        self.w_uk  = nn.Linear(d_c, n_heads * d_head, bias=False)   # 解压 K
        self.w_uv  = nn.Linear(d_c, n_heads * d_head, bias=False)   # 解压 V
        # Q 压缩分支（省训练显存用）
        self.w_dq  = nn.Linear(d, d_cq, bias=False)
        self.w_uq  = nn.Linear(d_cq, n_heads * d_head, bias=False)
        # 解耦 RoPE 分支：k_rope 所有头共享（缓存 64 维），q_rope 每头独立
        self.w_kr  = nn.Linear(d, d_rope, bias=False)
        self.w_qr  = nn.Linear(d_cq, n_heads * d_rope, bias=False)
        self.w_o   = nn.Linear(n_heads * d_head, d, bias=False)

    def forward(self, h, rope):                      # h: (B, S, d)
        B, S, _ = h.shape
        c_kv = self.w_dkv(h)                          # (B, S, 512)  <- 缓存
        k_r  = rope(self.w_kr(h)).unsqueeze(2)        # (B, S, 1, 64) <- 缓存
        c_q  = self.w_dq(h)
        k_c = self.w_uk(c_kv).view(B, S, self.n_heads, self.d_head)
        v   = self.w_uv(c_kv).view(B, S, self.n_heads, self.d_head)
        q_c = self.w_uq(c_q).view(B, S, self.n_heads, self.d_head)
        q_r = rope(self.w_qr(c_q).view(B, S, self.n_heads, self.d_rope))
        q = torch.cat([q_c, q_r], dim=-1)             # (B, S, h, 128+64)
        k = torch.cat([k_c, k_r.expand(-1, -1, self.n_heads, -1)], dim=-1)
        # SDPA 要求 (B, h, S, d)；V 的 head_dim (128) 与 QK (192) 不同是允许的
        q, k, v = (x.transpose(1, 2) for x in (q, k, v))
        o = scaled_dot_product_attention(q, k, v, is_causal=True)
        return self.w_o(o.transpose(1, 2).reshape(B, S, -1))
```

## 4. 滑动窗口注意力与 Attention Sink

稀疏化主线上最朴素的做法：**每个 query 只看最近 $w$ 个 token**（Sliding Window Attention，SWA）。复杂度从 $O(L^2)$ 降到 $O(Lw)$，KV Cache 封顶为 $w$。

- **Mistral-7B** 是工程化的先行者（$w = 4096$），配合层数堆叠，感受野理论上逐层扩大。
- **Gemma 3** 采用 **5:1 的局部:全局混合**——每 5 层 SWA（$w = 1024$）夹 1 层全局注意力，全局层负责长程信息通路，KV Cache 大头被局部层摊薄。
- **GPT-OSS** 交替使用 SWA（$w = 128$）与全局层，并引入**可学习的 attention sink**。

**Attention Sink** 是必须掌握的概念：StreamingLLM 发现 softmax 注意力总要"把概率分给某处"，模型学会把大量注意力倾倒在开头几个 token（通常是 BOS）上作为"垃圾桶"。如果滑窗把开头 token 挤出缓存，模型会立刻崩坏。解法有二：

1. **保留 sink token**：永久缓存开头几个 token 的 KV（StreamingLLM 的做法）；
2. **可学习 sink logit**：给每个头加一个可学习标量 $z'_h$ 进 softmax 分母：

$$
s_{h,i,j} = \frac{\exp(z_{h,i,j})}{\sum_k \exp(z_{h,i,k}) + \exp(z'_h)}
$$

这让每个头可以"什么都不注意"（注意力总和小于 1），不再需要真实 token 当垃圾桶。GPT-OSS 和后文的 DeepSeek V4 都采用了这种形式——这是一个从观察现象（sink 现象）到显式建模（sink logit）的漂亮案例，面试讲出这条线会非常加分。

SWA 的根本局限：**信息只能沿层传播有限距离，精确的长程检索（如大海捞针）能力弱**。所以它通常作为混合架构里的"便宜层"，而不是独立方案。

## 5. 线性注意力与混合架构

激进路线：把 softmax 注意力换成线性/循环形式，将历史压缩进**固定大小的状态矩阵**，decode 每步 $O(1)$ 计算、$O(1)$ 缓存。2024 年后它以"混合架构"的形式真正进入了主流生产模型：

| 模型 | 线性层 | 混合比例（线性:全注意力） |
|------|--------|--------------------------|
| MiniMax-01 | Lightning Attention | 7:1 |
| Qwen3-Next | Gated DeltaNet | 3:1（全注意力层为带门控的 GQA） |
| Kimi Linear | KDA（Kimi Delta Attention） | 3:1（全注意力层为 MLA） |

共同的设计判断：**纯线性注意力的精确检索能力不足**（固定大小状态必然有损），但让 3/4 以上的层用线性注意力扛住"日常"建模，少数全注意力层负责精确检索，可以在长上下文场景把 KV Cache 和计算都砍掉大半。面试中能说清"为什么是混合而不是纯线性"（检索能力 vs 效率的权衡）即可，不必展开线性注意力的数学细节。

## 6. 可训练稀疏注意力 NSA MoBA 与 DSA

滑窗是"死规矩"式的稀疏——不管内容是什么，一律只看最近的。但长文档里真正相关的内容往往在很远处（想想大海捞针）。2025 年的关键跨越是**让模型自己学会"该看哪里"**：稀疏的位置由内容决定、且从训练阶段就参与学习。面经原题"DeepSeek-DSA、NSA 与 MoBA 之间的区别是什么？"考的就是这条线上的三个代表工作，先各用一句话定位：

- **NSA**：一层里同时开三条通道——粗读全文摘要、精读挑出来的重点块、细读最近的内容——再学一个门控把三路加权；
- **MoBA**：像 MoE 路由一样干活——把上下文切成块，query 挑几个最相关的块进去读，其余不看；
- **DSA**：给**每一个** token 单独打分，挑 top-2048 个精读——粒度最细，也是第一个进入 DeepSeek 主线生产模型的稀疏注意力。

### 6.1 NSA：三分支门控的层级稀疏

NSA（Native Sparse Attention，DeepSeek 2025.02）的核心是**每个 query 并行走三条分支，结果用可学习门控加权求和**：

1. **压缩分支（cmp）**：把 KV 按块（块长 32）用小 MLP 池化成粗粒度"块摘要"，query 对块摘要做注意力——提供全局粗视野；
2. **选择分支（slc）**：借用压缩分支的注意力分数给块打分，选 top-16 个细粒度块（块长 64），query 对这些块内的**原始 token** 做精确注意力——提供细粒度检索。同一 GQA 组内所有头共享选块结果，保证访存连续；
3. **滑窗分支（win）**：最近 512 个 token——兜底局部依赖。

$$
\mathbf{o}_t = \sum_{c \in \{\text{cmp, slc, win}\}} g_t^c \cdot \text{Attn}(\mathbf{q}_t, \tilde{K}^c, \tilde{V}^c), \quad g_t^c = \sigma(\cdot)
$$

NSA 的两个关键词是**硬件对齐**（块粒度选择让 kernel 访存连续，配套 Triton kernel）和**原生可训练**（从预训练第一步就是稀疏的，而不是训完再剪）。论文在 27B MoE 模型上报告 64K 上下文下 decode 约 11.6 倍、训练前向约 9 倍/反向约 6 倍的注意力加速，且长文本基准不降反升。

### 6.2 MoBA：无参数的块级路由

MoBA（Mixture of Block Attention，月之暗面 2025.02）思路更简洁，像 MoE 一样做"块级路由"：

- 上下文切成 $n$ 个块，每个块的 key 做 **mean pooling** 得到块摘要；
- query 与块摘要做内积得亲和分数，选 **top-k 个块**做块内精确注意力；
- 当前块必选（保因果与局部性），**全程无新增参数**，可与全注意力层随时切换。

### 6.3 三者对比（面经原题答案）

| 维度 | NSA | MoBA | DSA |
|------|-----|------|-----|
| 稀疏粒度 | 块（压缩+选择+滑窗三分支） | 块 | **单 token（最细）** |
| 选择机制 | 压缩注意力分数选块 + 可学习门控 | 无参数 mean-pool 路由 | 可学习 Lightning Indexer 打分 |
| 与 KV 压缩的关系 | 独立于 GQA/MQA 使用 | 独立使用 | **叠加在 MLA 之上** |
| 训练方式 | 从零原生稀疏训练 | 可全/稀疏切换训练 | 在已训好的 V3.1 上继续训练引入 |
| 代表落地 | 论文验证（27B MoE） | Kimi 系列 | DeepSeek-V3.2-Exp 生产模型 |

### 6.4 DSA：Lightning Indexer 与 top-k 稀疏

DSA（DeepSeek Sparse Attention，V3.2-Exp，2025.09）是稀疏注意力第一次进入 DeepSeek 主线生产模型，也是理解 V4 的必要前置。

核心思路一句话：**在完整注意力前面加一道"粗筛"**。粗筛由一个叫 **Lightning Indexer** 的迷你打分器完成——可以把它理解成一个"极简版注意力"：头数很少、每头维度小、打分函数用 ReLU 而不是 softmax、以 FP8 低精度运行。它不负责"读懂"内容，只负责快速回答一个问题："对当前 query 来说，历史上哪些 token **可能**重要？"：

$$
I_{t,s} = \sum_{h=1}^{n_h^I} w_{t,h} \cdot \mathrm{ReLU}(\mathbf{q}_{t,h}^{I} \cdot \mathbf{k}_s^{I}) \qquad \text{（给第 } s \text{ 个历史 token 打的分）}
$$

流程就是"先粗筛、再精读"：indexer 给全部历史 token 打分 → 挑出 **top-k = 2048** 个 → 只有这 2048 个 token 的 latent KV 进入完整精度的主注意力（DSA 叠在 MLA 之上，读的是 MLA 的压缩缓存）。

算一笔复杂度账：主注意力从 $O(L^2)$ 降到 $O(L \cdot k)$——128K 上下文时每个 query 只精读 2048 个而不是 13 万个 token。有人会问：indexer 自己不还是要给所有 token 打分（$O(L^2)$）吗？是的，但它的**常数小了几个数量级**（少头、小维度、ReLU、FP8），这笔"便宜的全量打分"换掉了"昂贵的全量精读"，整体大赚。

训练分两阶段，白话版：indexer 是新加的模块，一开始根本不知道"重要"长什么样。所以先**冻结主干做 dense warmup**——完整注意力正常跑，让 indexer 对着完整注意力的分数分布"当学徒"（KL 蒸馏），学会模仿"真正的注意力会看哪里"；学出师了再开启稀疏模式，全模型继续训练。V3.2-Exp 用与 V3.1 严格对齐的配置证明了长上下文成本大降而质量基本持平——直接体现是 API 价格砍半。**"V3.2 相较前代的创新点"这道面经题，答案主体就是 DSA + 两阶段训练策略。**

## 7. DeepSeek V4 的混合注意力 CSA 与 HCA

DeepSeek-V4（2026.04 预览，V4-Pro 1.6T 总参/49B 激活，V4-Flash 284B/13B，上下文 **100 万 token**）是当前面试"最新注意力机制"的标准答案。它没有继续在 MLA 上修补，而是重新设计了注意力层：**Compressed Sparse Attention（CSA）与 Heavily Compressed Attention（HCA）逐层交错**。

### 7.0 先想通一件事：V4 和 MLA 压的不是同一个东西

把 KV Cache 想成一摞笔记：每个 token 一条记录。前面几代的思路对齐着看，就能明白 V4 在干嘛：

```text
MLA（V2/V3）：100 万条记录，每条从 32768 个数压薄到 576 个数
              → 压的是"每条记录的厚度"，条数一条没少
DSA（V3.2）： 100 万条记录，每次只挑 2048 条来读
              → 读的时候稀疏了，但记录还是 100 万条，缓存没变小
CSA（V4）：   每 4 个 token 合订成 1 条 → 只剩 25 万条，再从中挑 512 条精读
HCA（V4）：   每 128 个 token 压成 1 条"章节摘要" → 只剩 8192 条，干脆全读
```

一句话：**MLA 压"厚度"，DSA 省"读的次数"，CSA/HCA 直接压"条数"**——条数少了，计算和缓存同时变小，这是 1M 上下文能落地的根本原因。

### 7.1 CSA：压缩 → 挑重点 → 精读，三步流水线

CSA 的一层就是这条流水线，每步先讲人话再看公式。

**第一步：每 4 个 token 的 KV 合成 1 条（m = 4）。**

怎么合？不能简单取平均——4 个 token 里有主有次（比如一个实词带三个虚词）。V4 学了一个打分小网络：给窗口内 4 个 token 各打一个分（再叠加一个"我是窗口里第几个"的可学习位置偏置 $B$），softmax 归一化成权重后加权求和，得到 1 条压缩记录：

$$
S_{mi:m(i+1)-1} = \mathrm{Softmax}_{\text{row}}(Z_{mi:m(i+1)-1} + B), \qquad C_i^{\text{Comp}} = \sum_{j} S_j \odot C_j
$$

（$Z$ 就是那组打出来的分，$C$ 是各 token 的 KV 条目，$S$ 是归一化后的权重。）

还有一个容易被问到的细节：实现里用了**两组错位半步的压缩序列** $C^a$、$C^b$。原因很直白——4 个一组硬切的话，第 4 个和第 5 个 token 哪怕语义再紧密，也会被切进两条不同的记录；再叠一组错开位置的压缩窗口，边界就被互相覆盖住了。仅"4 合 1"这一步，后续注意力的计算量和 KV Cache 就同时除以 4。

**第二步：Lightning Indexer 挑出 top-k 条重点。**

思路完全继承 DSA 的"先粗筛再精读"（见 6.4），只是打分对象从"单个 token"换成了"压缩记录"：迷你打分器给 25 万条记录逐条打分，挑出 **top-k 条**（V4-Flash k=512，V4-Pro k=1024；一条记录对应 4 个原始 token，所以 512 条覆盖约 2048 个 token 的信息量）：

$$
I_{t,s} = \sum_{h=1}^{n_h^I} w_{t,h}^{I} \cdot \mathrm{ReLU}(\mathbf{q}_{t,h}^{I} \cdot K_s^{\text{IComp}})
$$

indexer 的打分计算以 **FP4** 精度执行——打分不需要数值精确，排序大致对就行，精度全省给速度。

**第三步：共享 KV 的 MQA 精读。**

挑出来的压缩记录 $C^{\text{SprsComp}}$ 有个特别的设计：**同一条记录既当 K 又当 V**——既是"用来匹配的索引"，也是"读出来的内容"。K/V 不再是两套投影两份缓存，缓存直接再省一半：

$$
\mathbf{o}_{t,i} = \mathrm{Attn}(\text{query} = \mathbf{q}_{t,i},\ \text{key} = C^{\text{SprsComp}},\ \text{value} = C^{\text{SprsComp}})
$$

query 侧：$n_h$ 个头（Flash 64 头 / Pro 128 头，head_dim 512）从一个共享 latent 上投影出来，**全部对着同一份记录读**。停一秒——"很多 query 头共享一条大 KV"，这不就是 3.4 节 MLA 矩阵吸收之后的形态吗？没错：**MLA 靠吸收技巧在推理时"变成"的结构，V4 直接把它设计成了出厂结构**，连吸收这一步都省了。

输出侧还有个纯工程的小优化：64 头 × 512 维拼接起来是 32768 维，直接投影回 4096 维的矩阵太大，于是把 64 个头分成 8 组（Pro 16 组），每组先各自缩到 1024 维、再合并投影回 $d$——这就是**分组输出投影**，只为省计算，不影响理解主线。

**兜底分支：最近 128 个 token 保留原件。**

"4 合 1"之后，一条记录内部谁先谁后就模糊了，而语言模型最依赖的恰恰是最近几个 token 的精确信息。所以 CSA 始终额外保留最近 $n_{\text{win}} = 128$ 个**未压缩** token 的 KV，与压缩记录一起参与注意力——和 NSA 的滑窗分支异曲同工。

### 7.2 HCA：128 合 1 的章节摘要，全读不挑

HCA 用的是与 CSA 同一套零件，只是拧到另一个极端：

- 压缩率 $m' = 128$：每 128 个 token 压成 1 条（单序列、不做重叠）——1M token 压完只剩 **8192 条**；
- **不挑了**：8192 条这个量级全部读一遍也很便宜，再上 Indexer 打分反而是多余开销，所以直接对全部压缩记录做稠密注意力；
- 其余同 CSA：共享 KV 的 MQA、分组输出投影、128 token 滑窗兜底。

直觉对比：**CSA 是"中等分辨率 + 挑重点精读"，HCA 是"极低分辨率 + 全局扫一眼"**。两者逐层交错（V4-Flash 前 2 层是纯滑窗层，V4-Pro 前 2 层是 HCA，之后一层 CSA 一层 HCA 交替）：CSA 层负责把细节找回来，HCA 层负责便宜地维持全局视野。设计哲学与 NSA 的"压缩分支 + 选择分支"一脉相承，只是从"一层内三分支"变成了"跨层分工"。

### 7.3 值得记住的工程细节

这些细节是区分"读过论文"和"听过名词"的地方，也是 Infra 面试的深挖点：

- **部分 RoPE + 输出侧反向 RoPE**：只对 query 和 KV 条目的**最后 64 维**施加 RoPE。由于 KV 条目既当 K 又当 V，注意力输出会携带绝对位置信息，V4 再对输出 $\mathbf{o}_{t,i}$ 的对应维度施加位置为 $-i$ 的 RoPE，把绝对位置抵消成相对位置。
- **QK RMSNorm 替代 QK-Clip**：对每个 query 头和 KV 条目在核心注意力前做 RMSNorm，从结构上杜绝注意力 logit 爆炸（因此 V4 用 Muon 优化器时不再需要 QK-Clip）。
- **可学习 attention sink**：即第 4 节的 sink logit 方案，允许注意力总和趋近 0。
- **KV Cache 混合精度存储**：RoPE 维度存 BF16，其余维度存 **FP8**，缓存体积再省近一半；indexer 计算用 **FP4**。
- **训练策略**：先用**稠密注意力训练前 1T token**，在 64K 序列长度阶段引入稀疏（含 indexer 短暂 warmup），之后全程稀疏——与 V3.2 的两阶段思路一致，说明"先稠密教会模型注意力该长什么样，再稀疏化"已成为可复用的方法论。

### 7.4 效率账本

| 指标（1M token 上下文） | 相对基准 | 数字 |
|------|------|------|
| V4-Pro 单 token 推理 FLOPs | vs V3.2（MLA+DSA） | **27%** |
| V4-Pro KV Cache | vs V3.2 | **10%** |
| V4-Flash 单 token 推理 FLOPs | vs V3.2 | **10%** |
| V4-Flash KV Cache | vs V3.2 | **7%** |
| V4 系列 KV Cache | vs BF16 GQA-8（head_dim 128）基线 | **约 2%** |

注意对比对象：V3.2 本身已经是"MLA + DSA"的高效架构，V4 在它之上又砍掉了 3/4 到 9/10——来源就是序列维压缩（÷4 或 ÷128）、共享 KV（K/V 合一）、更小的 top-k 和低精度存储的乘积效应。这组数字是"为什么 V4 能把 1M 上下文做成日常可用"的定量答案。

## 8. 全景对比与选型思路

| 机制 | 压缩什么 | 主注意力复杂度 | KV Cache | 代表模型 |
|------|----------|----------------|----------|----------|
| MHA | 无 | $O(L^2)$ | $2 h d_h$/token | GPT-3 |
| GQA | KV 头数 | $O(L^2)$ | $2 g d_h$/token | LLaMA-3、Qwen2.5 |
| MLA | 每 token 表示维度 | $O(L^2)$ | 576 元素/token | DeepSeek-V2/V3/R1 |
| SWA | 时间范围 | $O(Lw)$ | 封顶 $w$ | Mistral、Gemma 3 |
| 线性混合 | 历史→固定状态 | $O(L)$（线性层） | 固定状态+少量全注意力层 | MiniMax-01、Qwen3-Next |
| NSA | 稀疏化（块级三分支） | $O(L \cdot k)$ | 全量（算得少存不少） | 论文模型 |
| DSA | 稀疏化（token 级 top-k） | $O(Lk) + O(L^2)_{\text{indexer}}$ | 同 MLA | DeepSeek-V3.2 |
| **CSA** | **序列维 ÷4 + top-k 稀疏 + KV 合一** | $O(L k)$（在 $L/4$ 序列上） | 约 GQA8 的 2% | **DeepSeek-V4** |
| **HCA** | **序列维 ÷128 + KV 合一** | $O(L \cdot L/128)$ | 极小 | **DeepSeek-V4** |

一条容易记住的演进叙事线（面试可以直接讲）：

1. **省显存**：MQA/GQA 减头数 → MLA 减维度（低秩 latent + 矩阵吸收）；
2. **省计算**：SWA 固定模式稀疏 → NSA/MoBA 可学习块稀疏 → DSA 可学习 token 级稀疏；
3. **合流**：V4 的 CSA/HCA 把"压缩表示"和"稀疏选择"叠加，再加 KV 合一与低精度存储，支撑 1M 上下文。

## ✅ 自我检验清单

**1. 能画出注意力演进的两条主线与一条激进路线，并说出各自针对的瓶颈**

<details>
<summary>参考答案</summary>

- 瓶颈一：KV Cache 显存——它决定推理引擎能组多大 batch，进而决定吞吐上限；对应主线"压缩 KV 表示"（MQA → GQA → MLA）。
- 瓶颈二：$O(L^2)$ 计算——百万 token 级别平方复杂度在算力上不可接受；对应主线"稀疏化注意力"（SWA → MoBA/NSA → DSA → CSA/HCA）。
- 激进路线：线性化，放弃 softmax 精确注意力、把历史压成固定大小状态（Lightning Attention、Gated DeltaNet、KDA）。

DeepSeek 的演进链：V2/V3 用 MLA 解决 KV 显存、V3.2 用 DSA 解决平方计算、V4 用 CSA+HCA 把两条主线合并。（对应第 1 节）

</details>

**2. 能算出 MLA 每 token 每层只缓存 576 个数的账，并说出压缩比**

<details>
<summary>参考答案</summary>

MHA 基准：每 token 每层存 $2 \times 128 \times 128 = 32768$ 个数（V3 规格，61 层、128K 上下文单条请求约 490 GB）。MLA 只缓存两样：低秩联合压缩的 latent $\mathbf{c}_t^{KV}$（7168 维降到 512 维，128 个头共享一份、K/V 联合）加解耦 RoPE 分支的 $\mathbf{k}_t^R$（64 维，所有头共享），共 $512 + 64 = 576$ 个数，压缩约 93.3%。（对应第 3.1~3.3 节；另见 Q1）

</details>

**3. 能说清 RoPE 为什么与压缩缓存冲突、解耦 RoPE 如何绕开**

<details>
<summary>参考答案</summary>

RoPE 的旋转要打在 K 上，但压缩包里的 K 要解压才存在：解压后再旋转，就必须每次真的解压，免解压优化做不了；把旋转预先焊进解压矩阵也不行——旋转角度取决于查询时才知道的相对距离 $t-s$，$q_t^T k_s$ 中间卡着随距离变化的 $R_{t-s}$，两侧矩阵谁也合并不了。MLA 的解法：位置信息不进压缩包，单开一条 64 维共享位置分支携带 RoPE，各头做注意力时与压缩分支解压出的内容拼接。（对应第 3.3 节；另见 Q2）

</details>

**4. 能推导矩阵吸收，并解释吸收后 MLA decode 为什么等价于 head_dim 576 的 MQA**

<details>
<summary>参考答案</summary>

矩阵乘法结合律：$(W_i^{UQ}\mathbf{c}_t^{Q})^T(W_i^{UK}\mathbf{c}_s^{KV}) = \mathbf{c}_t^{Q,T}(W_i^{UQ,T}W_i^{UK})\mathbf{c}_s^{KV}$，解压矩阵离线预乘进 q 的投影，query 直接在 512 维压缩空间与缓存内积——压缩包从头到尾没被解开；V 侧 $W^{UV}$ 同理吸收进输出投影 $W^O$。吸收后缓存只有一份 576 维的 $[\mathbf{c}^{KV}; \mathbf{k}^R]$（相当于只有 1 个 KV 头），128 个 query 头都对着它做注意力，结构上就是 head_dim = 576 的 MQA；按缓存量折算 $576/(2 \times 128) = 2.25$ 组 GQA，但 128 个头各自保有独立的注意力分布。（对应第 3.4 节）

</details>

**5. 能分析 MLA decode 的计算访存比：为什么高、由什么决定**

<details>
<summary>参考答案</summary>

MQA/GQA decode 每读入一个 KV 数只有对应的那（几）个 query 头做 1 次乘加，算术强度约 1，GPU 绝大部分时间在等数据（memory-bound）；MLA 吸收后 128 个 query 头共享同一份 576 维缓存，每读一个数要做 128 次乘加，算术强度直接 ×128，decode 被拉向 compute-bound。这个比值与序列长度基本无关、与 batch size 解耦，真正决定它的是 query 头数 $h$——这也是 FlashMLA 这类专用 kernel 能在 Hopper 上跑出很高 MFU 的原因。（对应第 3.5 节）

</details>

**6. 能解释 Attention Sink 现象及两种处理方案的差别**

<details>
<summary>参考答案</summary>

softmax 强制注意力总和为 1，模型学会把多余注意力倾倒在开头几个 token（通常是 BOS）上当"垃圾桶"；滑窗一旦把这些 token 挤出缓存，模型立刻崩坏（StreamingLLM 的发现）。解法一：永久缓存开头几个 sink token 的 KV（StreamingLLM）；解法二：给每个头加可学习 sink logit $z'_h$ 进 softmax 分母，允许注意力总和小于 1、不再需要真实 token 当垃圾桶——GPT-OSS 与 DeepSeek V4 均采用后者。（对应第 4 节；另见 Q7）

</details>

**7. 能说出主流线性混合架构的配比，并回答"为什么是混合而不是纯线性"**

<details>
<summary>参考答案</summary>

MiniMax-01（Lightning Attention，7:1）、Qwen3-Next（Gated DeltaNet，3:1，全注意力层为带门控的 GQA）、Kimi Linear（KDA，3:1，全注意力层为 MLA）。共同的设计判断：固定大小状态必然有损，纯线性注意力的精确检索能力不足；让 3/4 以上的层用线性注意力扛住"日常"建模、少数全注意力层负责精确检索，长上下文场景把 KV Cache 和计算都砍掉大半。（对应第 5 节）

</details>

**8. 能从粒度、选择机制、与 KV 压缩的关系、训练方式四个维度区分 NSA、MoBA、DSA**

<details>
<summary>参考答案</summary>

- **NSA**：块级，压缩/选择/滑窗三分支加可学习门控加权，从零原生稀疏训练，块粒度选择保证 kernel 访存连续（论文在 27B MoE 上验证）；
- **MoBA**：块级，key 做 mean pooling 出块摘要、query 选 top-k 块做块内精确注意力，全程无新增参数，可全/稀疏切换训练（Kimi 系落地）；
- **DSA**：单 token 级最细粒度，可学习 Lightning Indexer 打分取 top-2048，叠加在 MLA 之上，在已训好的 V3.1 上继续训练引入（V3.2-Exp 生产模型）。（对应第 6 节；另见 Q3）

</details>

**9. 能讲清 DSA"先粗筛再精读"的流程与两阶段训练策略**

<details>
<summary>参考答案</summary>

Lightning Indexer 是极简打分器（头数很少、每头维度小、ReLU 代替 softmax、FP8 运行），给全部历史 token 打分 → 取 top-k = 2048 → 只有这些 token 的 latent KV 进入完整精度主注意力（DSA 叠在 MLA 之上，读的是压缩缓存），主注意力 $O(L^2) \to O(L \cdot k)$；indexer 自身仍是 $O(L^2)$ 但常数小几个数量级（另见 Q8）。训练两阶段：先冻结主干做 dense warmup，让 indexer 对完整注意力的分数分布做 KL 蒸馏"当学徒"，学成后开启稀疏、全模型继续训练——长上下文成本大降（API 降价约一半）而质量对齐 V3.1。（对应第 6.4 节；另见 Q4）

</details>

**10. 能用"厚度 vs 条数"说清 CSA/HCA 与 MLA/DSA 的本质区别，并复述 CSA 三步流水线与 V4 效率数字**

<details>
<summary>参考答案</summary>

MLA 压每条记录的"厚度"（32768 → 576 个数），条数一条没少；DSA 只省"读的次数"，缓存不变小；CSA/HCA 直接压"条数"——CSA 每 4 个 token 合 1 条再挑重点，HCA 每 128 个 token 压 1 条"章节摘要"全读不挑，计算与缓存同时变小，这是 1M 上下文能落地的根本原因。CSA 三步：学习打分的 softmax 加权池化做 4 合 1（两组错位半步的压缩序列覆盖边界）→ FP4 Lightning Indexer 选 top-512（Flash）/1024（Pro）条 → 共享 KV 的 MQA 精读（同一条记录既当 K 又当 V），另保留最近 128 个未压缩 token 兜底；两者逐层交错。效率账本：1M 上下文下 V4-Pro 推理 FLOPs 为 V3.2 的 27%、KV Cache 为 10%，V4 系列 KV Cache 约为 BF16 GQA-8 基线的 2%。（对应第 7 节；另见 Q5/Q6）

</details>

## 9. 高频面试题解析

**Q1：MLA 相比 MHA/GQA 的优势是什么？**
低秩联合压缩使每 token 每层只缓存 576 个元素（压缩约 93.3%），同时保留全部 query 头的独立注意力分布，质量接近 MHA；配合矩阵吸收，decode 等价于 head_dim 576 的 MQA，算术强度远高于 GQA，decode kernel 从 memory-bound 变为接近 compute-bound（见 3.4/3.5 小节）。

**Q2：MLA 为什么需要解耦 RoPE？**
RoPE 的旋转矩阵位置相关，若直接作用在解压后的 K 上，会卡在 $W^{UQ,T} R_{t-s} W^{UK}$ 中间使矩阵吸收失效。因此单独开一条 64 维的共享位置分支携带 RoPE，与压缩分支拼接（见 3.3 小节）。

**Q3：DSA、NSA、MoBA 的区别？**
粒度（token 级 vs 块级）、选择机制（可学习 indexer vs 压缩分数+门控 vs 无参数 mean-pool 路由）、与 KV 压缩的关系（DSA 叠在 MLA 上）、训练方式（继续训练引入 vs 原生稀疏训练 vs 可切换）——展开见第 6.3 节对比表。

**Q4：DeepSeek V3.2 相较前代的创新点？**
在 MLA 之上引入 DSA：FP8 Lightning Indexer 对每 query 打分取 top-2048 做稀疏主注意力，主注意力复杂度 $O(L^2) \to O(Lk)$；配合"dense warmup 蒸馏 indexer → sparse 继续训练"的两阶段策略，长上下文推理成本大幅下降（API 降价约一半）而质量对齐 V3.1。

**Q5：DeepSeek V4 的注意力机制是什么？为什么能支撑 1M 上下文？**
CSA 与 HCA 逐层交错的混合注意力。CSA：每 4 个 token 的 KV 经 softmax 加权池化压成 1 个条目，Lightning Indexer（FP4）选 top-512/1024 个压缩条目，再做共享 KV 的 MQA（条目既当 K 又当 V），辅以 128 token 滑窗分支；HCA：每 128 个 token 压成 1 条，全量稠密注意力。加上 FP8 KV 存储与部分 RoPE，1M 上下文下 KV Cache 仅为 BF16 GQA8 基线的约 2%、推理 FLOPs 为 V3.2 的 27%（Pro）——计算与显存同时被压到平方复杂度不可及的量级。

**Q6：为什么 V4 不继续用 MLA？**
MLA 只压缩每个 token 的表示维度，KV Cache 和注意力计算仍随 $L$ 线性/平方增长，在 1M 上下文下依然不可承受。CSA/HCA 直接压缩序列长度（÷4 / ÷128），并把 MLA 吸收后的"多 query 头共享大 KV"形态显式设计进架构（共享 KV MQA），可视为 MLA 思想在序列维度上的推广而非否定。

**Q7：Attention Sink 是什么？如何处理？**
softmax 强制注意力总和为 1，模型把多余注意力倾倒在开头 token 上；滑窗若驱逐这些 token 会导致输出崩坏。解法：保留 sink token（StreamingLLM）或加可学习 sink logit 进 softmax 分母（GPT-OSS、DeepSeek V4），后者允许注意力总和小于 1（见第 4 节）。

**Q8：稀疏注意力的 indexer 为什么不会成为新瓶颈？它还是 $O(L^2)$ 的。**
复杂度同阶但常数差几个数量级：indexer 头数极少、head_dim 小、用 ReLU 代替 softmax、以 FP8（DSA）甚至 FP4（V4）执行；且 V4 中 indexer 作用在压缩后的 $L/4$ 序列上，二次项再除以 16。工程上真正的开销大头（主注意力的 KV 搬运与 PV 计算）已经变成 $O(Lk)$。
