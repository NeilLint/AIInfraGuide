## 1. MTP 是训练技术还是推理技术

标准答案：**首先是训练目标，推理时可以"顺便"复用为投机解码的草稿头，也可以完全丢弃**。

标准语言模型训练只做 next-token prediction：位置 $t$ 只预测 $t+1$。MTP 在此基础上增加辅助目标：位置 $t$ 还要预测 $t+2$（甚至 $t+3, \dots$）。DeepSeek-V3 技术报告给出的动机有两个：

1. **训练信号密度更高**：同一份数据，每个位置多出一份监督信号，提升数据效率；
2. **迫使模型"预规划"**：要预测两步之后的 token，隐状态必须编码更长远的语义规划，而不是只顾眼前——这被认为能提升表示质量。

关键结论先行：**MTP 的收益在训练时已经固化进主干权重**。推理时即使不加载 MTP 模块，模型质量也不受影响；加载它，则免费获得一个与主模型天然对齐的草稿头。

## 2. DeepSeek MTP 的结构细节

面试常考"DeepSeek 的 MTP 和 Medusa 的多头有什么区别"，核心差异在于**是否保持因果链**。

Medusa 用 $D$ 个**并行**的解码头，从同一个隐状态独立预测 $t+1, t+2, \dots$——第 $k$ 个头看不到第 $k-1$ 个头的预测结果，位置越靠后越"盲猜"。

DeepSeek MTP 则用 $D$ 个**顺序**的 MTP 模块，每个深度是一个完整的小型 Transformer 层：

- 第 $k$ 个 MTP 模块接收两个输入：主模型（或前一个 MTP 模块）的隐状态 $\mathbf{h}^{(k-1)}$，和目标位置 token 的 embedding；
- 两者各自 RMSNorm 后拼接，经投影矩阵 $M_k$ 融合，再过一个 Transformer block；
- **共享主模型的 embedding 层和输出头**（省参数，也保证分布对齐）。

$$
\mathbf{h}^{(k)}_t = \mathrm{TRM}_k\!\left( M_k \left[ \mathrm{RMSNorm}(\mathbf{h}^{(k-1)}_t);\ \mathrm{RMSNorm}(\mathrm{Emb}(x_{t+k})) \right] \right)
$$

因为每个深度都拿到了"上一步的真实 token embedding"，**完整的因果链在每个预测深度都被保留**——这是它接受率显著高于 Medusa 类并行头的根本原因。

训练时，每个深度的交叉熵损失取平均后乘权重 $\lambda$ 计入总损失。具体配置（记住这些数字，面试可以直接报）：

| 配置 | DeepSeek-V3 | DeepSeek-V4 |
|------|-------------|-------------|
| MTP 深度 $D$ | 1（预测 $t+2$） | 1（配置与 V3 完全相同） |
| MTP 损失权重 $\lambda$ | 前期 0.3，学习率衰减期 0.1 | 前期 0.3，衰减期 0.1 |

V4 技术报告明确说明"MTP 策略在 V3 中已被验证，V4 不做修改沿用"——可见这套配置的稳定性。

## 3. MTP 作为自带草稿的投机解码

推理时把 MTP 模块留下，就得到一个**自投机解码（self-speculative decoding）**系统，社区一般称为 **MTP-1**（用深度为 1 的 MTP 头做草稿）：

1. 主模型 decode 一步，产出 token $x_{t+1}$ 和隐状态；
2. MTP 模块基于隐状态和 $x_{t+1}$ 的 embedding，猜出 $x_{t+2}$；
3. 下一个 decode step 同时验证 $x_{t+2}$：接受则这一步产出 2 个 token，拒绝则只产出主模型自己的 token——**正确性由本章 5.1《投机解码核心原理详解》的 Rejection Sampling 框架保证，无损**。

它相对外挂方案的优势：

- **分布天然对齐**：草稿头和主模型出自同一次预训练，见过完全相同的数据，接受率天然高——DeepSeek-V3 报告 MTP-1 的接受率在 **80%~90%**，对应约 **1.8 倍**的解码 TPS 提升；
- **零额外工程**：不需要选型、训练、部署第二个模型；
- **共享主干计算**：草稿只多花一个 Transformer block 的代价。

vLLM 和 SGLang 都内置了 DeepSeek 系模型的 MTP 支持，以 vLLM 为例：

```bash
vllm serve deepseek-ai/DeepSeek-V3.2 \
  --speculative-config '{"method": "deepseek_mtp", "num_speculative_tokens": 1}'
```

局限也很明显，这正是 DSpark 要解决的问题：

1. **草稿深度浅**：$D=1$ 每步最多产出 2 个 token，加速上限 2 倍。想草稿更长，就要级联多次 MTP 模块（自回归式），草稿延迟随深度线性涨；
2. **验证长度固定**：不管上下文是"接受率 95% 的代码补全"还是"接受率 50% 的开放闲聊"，都验证同样多的草稿 token。单请求场景多验证几乎免费，**高并发下被拒绝的草稿 token 白白占用了本可服务其他请求的 batch 容量**，可能反而降低总吞吐。

## 4. 投机解码在生产系统中的三个矛盾

DSpark 论文用一个简洁的框架统一了所有投机解码的优化方向。设 $\tau$ 为每轮平均接受 token 数，则**每 token 平均延迟**：

$$
L = \frac{T_{\text{draft}} + T_{\text{verify}}}{\tau}
$$

一切方案都在拉三个杠杆：**降 $T_{\text{draft}}$（草稿打得快）、升 $\tau$（草稿打得准）、降有效 $T_{\text{verify}}$（验证花得省）**。由此看清两大流派的先天矛盾：

| 流派 | 代表 | 优势 | 矛盾 |
|------|------|------|------|
| **自回归草稿** | EAGLE 系列、MTP 级联 | 每步以已采样 token 为条件，$\tau$ 高 | $T_{\text{draft}} \propto \gamma$（草稿长度），被迫用短草稿、浅结构 |
| **并行草稿** | Medusa、DFlash | 一次前向出全部 $\gamma$ 个草稿，$T_{\text{draft}}$ 与 $\gamma$ 无关 | 各位置独立预测，无法建模 token 间依赖，越靠后接受率衰减越快 |

并行草稿的失败模式值得单独记住（面试好例子）：上下文同时允许 "of course" 和 "no problem" 两种续写时，并行草稿可能拼出 **"of problem"** 或 **"no course"**——每个位置各自边缘化了前驱，产生跨模式碰撞（cross-mode collision）。

第三个矛盾独立于草稿方式：**验证长度**。理想验证长度同时取决于数据侧（代码类请求接受率天然高于闲聊）和系统侧（引擎轻载时多验证几个 token 几乎免费，重载时每个被拒 token 都在挤占别人的算力）。静态阈值无法同时应对两者。

## 5. DSpark 半自回归草稿与置信度调度

DSpark（DeepSeek-AI，2026.06 开源，论文 arXiv 2607.05147，全称 Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation）针对上面三个矛盾各给了一个部件。它已在 DeepSeek-V4 生产服务中替代 MTP-1 成为默认投机方案，官方同时开源了 V4-Flash/V4-Pro 的 DSpark 检查点和训练框架 **DeepSpec**（内含 EAGLE-3、DFlash、DSpark 三种草稿算法的完整训练/评估代码）。

先别管内部结构，**用一个带数字的完整回合把 DSpark 的工作流程走一遍**，后面每个小节再拆开讲每一步里的部件是怎么造的。

### 5.1 先走一遍完整的解码回合

假设草稿块长 $\gamma = 4$，上一轮结束时目标模型刚生成了 token `D`：

```text
第 0 步（上一轮遗留）：目标模型生成 D —— D 就是本轮草稿的"锚点"

第 1 步 打草稿（draft 模块一次前向，便宜）：
        输入:  D  [MASK] [MASK] [MASK]
        输出:   E     F      G      H     ← 4 个候选 token
        置信度: 0.92  0.85   0.60   0.25  ← 每个 token 自报的"通过验证概率"

第 2 步 调度（决定送几个去验证，纯 CPU 逻辑）：
        前缀存活概率 = 置信度连乘：
        [E]=0.92  [E,F]=0.78  [E,F,G]=0.47  [E,F,G,H]=0.12
        当前引擎较忙 → 只保留 E、F、G 送验，H 直接丢弃（省下它的验证算力）

第 3 步 验证（目标模型一次前向，同时算 4 个位置）：
        输入 D E F G，得到 4 个位置的目标分布
        E ✓ 接受    F ✓ 接受    G ✗ 拒绝 → 按残差分布当场重采出 G*
        本轮产出 3 个 token：E、F、G*；G* 成为下一轮的锚点
```

三个要点：

1. **一次目标模型前向产出了 3 个 token**——这就是投机解码的收益来源（decode 是 memory-bound，一次前向算 4 个位置和算 1 个位置代价接近）；
2. **拒绝不亏**：G 被拒时，目标模型顺手给出修正 token G*，这一步至少不比普通 decode 慢；正确性由本章 5.1《投机解码核心原理详解》的 Rejection Sampling 框架保证，输出分布与目标模型逐 token 生成严格一致；
3. DSpark 的三个创新分别落在三步里：**第 1 步草稿怎么打得又快又准（5.2）、置信度从哪来（5.3）、第 2 步怎么决定送验几个（5.4）**。

### 5.2 草稿怎么打：并行主干加轻量顺序头

回顾第 4 节的两难：自回归草稿准但慢（打 $\gamma$ 个 token 要跑 $\gamma$ 次），并行草稿快但不准（各位置互相看不见）。DSpark 的草稿模块分两级，各取一半。

**第一级：并行主干（DFlash 结构）——负责"快"。**

把打草稿当成**完形填空**：输入是锚点 `D` 加上 $\gamma - 1$ 个 `[MASK]` 占位符，草稿网络一次前向，所有位置同时吐出各自的候选分布（记作基础 logits $U_1, \dots, U_\gamma$）。不管 $\gamma$ 是 4 还是 16，都只跑一次前向——这就是"快"的来源。两个让它"不至于太不准"的设计：

- **KV 注入（KV injection）**：草稿网络很小，只看 token 序列容易猜偏。DFlash 在 prefill 时把**目标模型若干层的隐状态**抽出来，投影拼接后作为额外的 K/V 喂给草稿层——相当于学生答题时不光能看题目，还能看老师的草稿纸。形式上：$H_{\text{ctx}} = \mathrm{RMSNorm}(W_c[H^{(l_1)}; \dots; H^{(l_m)}])$；
- **共享 embedding 和输出头**（冻结）：草稿和目标模型用同一套"词 → 向量"和"向量 → 词"映射，输出分布天然对齐，还省掉了草稿模型里参数量最大的两块。

**并行主干的死穴，用具体数字看**。假设上文既可以接 "of course" 也可以接 "no problem"，两种续写各 50% 概率。并行主干各位置**独立**预测，看到的只是边缘分布：

```text
位置 1 的分布： of: 0.5   no: 0.5
位置 2 的分布： course: 0.5   problem: 0.5   ← 它不知道位置 1 采了什么！
```

独立采样就有 25% 概率拼出 **"of problem"**、25% 拼出 **"no course"**——单看每个位置都"对"，连起来却是胡话。这种组合到验证阶段必然被拒，位置越靠后错误累积越狠，这就是并行草稿接受率快速衰减的机理。

**第二级：轻量顺序头（sequential head）——负责"准"。**

修法不是把主干改成串行（那就退回自回归的慢），而是在并行 logits 上**补一个便宜的修正分**。采样按从左到右进行，第 $k$ 个位置的分布是"主干底分 + 看过前面已采 token 后的加减分"：

$$
p_k(v \mid x_0, x_{<k}) = \frac{\exp\big(\underbrace{U_k(v)}_{\text{主干底分}} + \underbrace{B_k(x_0, x_{<k}, v)}_{\text{顺序修正分}}\big)}{\sum_{u \in \mathcal{V}} \exp\big(U_k(u) + B_k(x_0, x_{<k}, u)\big)}
$$

关键在于 $B_k$ 必须**极其便宜**（它要串行跑 $\gamma$ 步，每步代价必须远小于主干那一次前向）。论文给了两种实现：

- **Markov 头**：只看前一个 token 的"二元语法修正表"。理想情况是学一张 $V \times V$ 的转移表（"上一个词是 X 时，这个词是 Y 的加减分"），但词表 129K，全表存不下，于是低秩分解：$B(x_{k-1}, \cdot) = W_1[x_{k-1}] W_2$，秩 $r = 256$——每步就是一次查表加两个小矩阵乘。回到例子：位置 1 一旦采出 "of"，Markov 头立刻给 "course" 加分、给 "problem" 减分，"of problem" 被当场掐灭；
- **RNN 头**：Markov 头只记得住一步，RNN 头用一个 256 维的门控循环状态把块内已采样的**完整前缀**都压进来，能处理跨多步的依赖，每步代价仍是小向量运算。

这就是名字里"**半自回归**"的含义：**贵的计算全并行（一次前向出底分），串行的只剩查表级的修正循环**——草稿延迟基本不随 $\gamma$ 增长，接受率却接近真正的自回归草稿。

### 5.3 置信度从哪来：预测"通过率"并校准

5.1 节流程里每个草稿 token 自报的置信度（0.92、0.85、0.60、0.25）是**条件存活概率** $c_k$："在前面的 token 全被接受的前提下，我这个 token 能通过验证的概率"。它由一个极小的线性头顺手算出（输入是主干隐状态和前一 token 的 Markov embedding，过一个 sigmoid）：

$$
c_k = \sigma\big(w^\top [h_k;\ W_1[x_{k-1}]]\big)
$$

**训练标签不用等真实验证**。回忆 rejection sampling 的性质：一个草稿 token 被接受的概率有解析解——把草稿分布 $p^d$ 和目标分布 $p^t$ 画成两条柱状图，**重叠部分的面积就是接受率**：

$$
c_k^* = 1 - \tfrac{1}{2} \lVert p_k^d - p_k^t \rVert_1 \quad (\text{两分布差得越多，重叠越少，越容易被拒})
$$

蒸馏训练时目标模型的分布本来就在手边，所以每个位置的"真实通过率"可以直接算出来当回归目标——比 0/1 标签信息量大得多。

**为什么还要校准？** 神经网络的置信度普遍**过度自信**：嘴上说 90% 把握，实际只兑现 75%。如果只是拿置信度排个序（谁先谁后），过度自信无所谓；但下一节的调度器要拿它**算期望收益**，数值本身必须准——说 0.8 就得真有八成。DSpark 的做法叫**逐位温度校准**（Sequential Temperature Scaling）：在验证集上，从位置 1 到位置 $\gamma$ 逐个搜一个温度系数去缩放置信度，使"预测存活率"与"实际存活率"对齐（最小化 ECE，即分桶统计预测概率与实际频率的平均偏差）。温度缩放是保序变换——只把数值拉准，不打乱排序。

### 5.4 调度器：验证几个 token，按引擎负载现算

现在草稿和置信度都有了，剩最后一个决策：**送几个 token 去验证？** 把它看成一笔账：

- **收益**：验证第 $k$ 个 token 的期望产出 = 它的前缀存活概率 $\prod_{i \le k} c_i$（它前面全过、自己也过，才真正多产出一个 token）；
- **成本**：往目标模型的 batch 里多塞一个位置的边际代价——**这不是常数，取决于引擎当前多忙**。

用 5.1 节的数字算两种场景：

```text
草稿:            E      F      G      H
前缀存活概率:    0.92   0.78   0.47   0.12

场景 A（深夜低峰，batch 远未满，算力在空转）：
  多验证一个位置的边际成本 ≈ 0
  → 连 0.12 的 H 都值得捎上：反正白验，万一中了赚一个 token
  → 全长送验，单用户延迟压到最低

场景 B（高峰满载，batch 每个位置都有请求在排队）：
  G 占一个位置却只有 47% 概率产出，53% 概率白占——
  这个位置给别的请求用，是 100% 产出一个 token
  → 截断到 E、F，把位置让出来，总吞吐不塌
```

结论：**不存在一个固定的"置信度阈值"**——同样是 0.47 的 token，轻载时该验，重载时该丢，阈值本身是负载的函数。这就是 EAGLE-2 那类"静态置信度阈值"方案做不到的事。工程实现上，DSpark 离线为每种硬件/引擎压测出吞吐曲线（batch 中第 $N$ 个 token 的边际代价），在线时对每个请求独立解"期望收益 > 边际成本"的不等式来截断草稿——所以叫 **hardware-aware** 前缀调度器。

### 5.5 效果数字

离线基准（Qwen3-4B/8B/14B 为目标模型，数学/代码/闲聊多域宏平均接受长度）：

- 比 **EAGLE-3**（最强自回归草稿）分别高 **30.9% / 26.7% / 30.0%**；
- 比 **DFlash**（最强纯并行草稿）分别高 **16.3% / 18.4% / 18.3%**。

生产环境（DeepSeek-V4 真实流量，对比原 MTP-1 基线，同等总吞吐水平下的单用户生成速度）：

- **V4-Flash：+60%~85%**；
- **V4-Pro：+57%~78%**；
- 在严苛 SLA 档位（Flash 120 TPS / Pro 50 TPS 单用户），MTP-1 基线容量急剧劣化，DSpark 靠调度器压住验证开销守住吞吐——论文称之为"移动了 LLM serving 的帕累托前沿"。

## 6. 方案全景对比

| 方案 | 草稿方式 | 草稿延迟随 $\gamma$ | token 间依赖 | 验证长度 | 额外训练 |
|------|----------|--------------------|--------------|----------|----------|
| 独立小模型 | 自回归 | 线性增长 | 完整 | 固定 | 需选/训小模型 |
| Medusa | 并行多头 | 常数 | 无 | 固定（树验证） | 训多头 |
| EAGLE-2/3 | 特征级自回归 | 线性增长 | 完整 | 动态草稿树 | 训草稿层 |
| MTP（DeepSeek） | 预训练自带顺序模块 | 线性（深度浅） | 完整 | 固定 | 预训练内置，零额外 |
| DFlash | 并行块 + KV 注入 | 常数 | 无（块内双向） | 固定 | 蒸馏训练 |
| **DSpark** | **并行主干 + 轻量顺序头** | **常数** | **块内自回归分解** | **置信度 × 负载动态调度** | 蒸馏训练（DeepSpec） |

一句话总结这条演进线：**MTP 证明了"草稿能力可以内置于预训练"，DSpark 证明了"草稿与验证必须作为 serving 系统问题来联合设计"**。

## ✅ 自我检验清单

**1. 能回答"MTP 是训练技术还是推理技术"，并说出两个训练动机**

<details>
<summary>参考答案</summary>

首先是训练目标，推理时可"顺便"复用、也可完全丢弃。训练时在 next-token prediction 之外增加辅助目标：位置 $t$ 还要预测 $t+2$（甚至更远）。两个动机：训练信号密度更高（同一份数据每个位置多一份监督，提升数据效率）；迫使模型"预规划"（隐状态必须编码更长远的语义规划而非只顾眼前）。收益在训练时已固化进主干权重——推理不加载 MTP 模块质量不受影响，加载则免费获得一个与主模型天然对齐的草稿头。（对应第 1 节；另见 Q1）

</details>

**2. 能从"是否保持因果链"讲清 DeepSeek MTP 与 Medusa 多头的结构差异**

<details>
<summary>参考答案</summary>

Medusa 用 $D$ 个并行解码头从同一隐状态独立预测，第 $k$ 个头看不到第 $k-1$ 个头的结果，位置越靠后越"盲猜"。DeepSeek MTP 用 $D$ 个顺序模块：第 $k$ 个模块接收前一深度的隐状态与目标位置 token 的 embedding，两者各自 RMSNorm 后拼接、经投影矩阵 $M_k$ 融合、再过一个 Transformer block，并共享主模型的 embedding 层与输出头（省参数、保证分布对齐）。每个深度都拿到上一步的真实 token embedding，因果链完整——这是其接受率显著高于并行头的根本原因。（对应第 2 节；另见 Q2）

</details>

**3. 能直接报出 V3/V4 的 MTP 配置数字**

<details>
<summary>参考答案</summary>

V3 与 V4 配置完全相同：MTP 深度 $D = 1$（只预测 $t+2$）；损失权重 $\lambda$ 前期 0.3、学习率衰减期 0.1（各深度交叉熵取平均后乘 $\lambda$ 计入总损失）。V4 技术报告明确说明"MTP 策略在 V3 中已被验证，V4 不做修改沿用"。（对应第 2 节）

</details>

**4. 能描述 MTP-1 自投机的工作流程、收益数字与两个局限**

<details>
<summary>参考答案</summary>

流程：主模型 decode 一步产出 $x_{t+1}$ 与隐状态 → MTP 模块基于两者猜出 $x_{t+2}$ → 下一个 decode step 同时验证，接受则一步产出 2 个 token；正确性由 5.1 的 Rejection Sampling 框架保证，无损。V3 报告接受率 80%~90%、约 1.8 倍解码 TPS。优势：分布天然对齐（同一次预训练）、零额外工程、草稿只多一个 Transformer block 的代价。两个局限：$D=1$ 每步最多 2 个 token、加速上限 2 倍，级联加深则草稿延迟线性涨；验证长度固定，高并发下被拒草稿白占 batch 容量、可能反降总吞吐。（对应第 3 节）

</details>

**5. 能用 $L = (T_{\text{draft}} + T_{\text{verify}})/\tau$ 框架说出三个优化杠杆与两大草稿流派的先天矛盾**

<details>
<summary>参考答案</summary>

三个杠杆：降 $T_{\text{draft}}$（草稿打得快）、升 $\tau$（打得准）、降有效 $T_{\text{verify}}$（验证花得省）。自回归草稿（EAGLE 系列、MTP 级联）每步以已采样 token 为条件、$\tau$ 高，但 $T_{\text{draft}} \propto \gamma$，被迫用短草稿、浅结构；并行草稿（Medusa、DFlash）一次前向出全部草稿、$T_{\text{draft}}$ 与 $\gamma$ 无关，但各位置独立预测、越靠后接受率衰减越快。第三个矛盾独立于草稿方式：理想验证长度同时取决于数据侧（代码类接受率天然高于闲聊）与系统侧（轻载多验几乎免费、重载每个被拒 token 都在挤占算力），静态阈值无法兼顾两者。（对应第 4 节）

</details>

**6. 能举"of problem"的数字例子解释并行草稿的跨模式碰撞**

<details>
<summary>参考答案</summary>

上下文同时允许 "of course" 与 "no problem" 各 50% 时，并行草稿各位置只看到边缘分布：位置 1 是 of/no 各 0.5，位置 2 是 course/problem 各 0.5——位置 2 不知道位置 1 采了什么。独立采样就有 25% 概率拼出 "of problem"、25% 拼出 "no course"：单看每个位置都"对"，连起来却是胡话，到验证阶段必然被拒；位置越靠后错误累积越狠，这就是并行草稿接受率快速衰减的机理。（对应第 4、5.2 节；另见 Q4）

</details>

**7. 能拆解 DSpark"半自回归"草稿的两级结构：并行主干负责什么、顺序头负责什么**

<details>
<summary>参考答案</summary>

第一级并行主干（DFlash 结构）负责"快"：锚点加 $\gamma - 1$ 个 `[MASK]` 的完形填空式一次前向出全部基础 logits $U_k$，不管 $\gamma$ 多大都只跑一次；辅以 KV 注入（prefill 时抽目标模型若干层隐状态、投影拼接后作为额外 K/V 喂给草稿层）和冻结共享的 embedding/输出头。第二级轻量顺序头负责"准"：从左到右采样时给每个位置加前缀相关的修正分 $B_k$——Markov 头（129K 词表全表存不下，低秩分解 $r=256$ 的二元转移修正）或 RNN 头（256 维门控循环状态压进块内完整前缀）。贵的计算全并行、串行只剩查表级修正——草稿延迟基本不随 $\gamma$ 增长，接受率却接近真正的自回归草稿。（对应第 5.2 节）

</details>

**8. 能说清置信度 $c_k$ 的定义、训练标签的解析来源，以及为什么必须做温度校准**

<details>
<summary>参考答案</summary>

$c_k$ 是条件存活概率："前面的 token 全被接受的前提下，本 token 通过验证的概率"，由极小线性头（输入主干隐状态与前一 token 的 Markov embedding，过 sigmoid）顺手算出。标签不用等真实验证：rejection sampling 下接受概率有解析解 $c_k^* = 1 - \tfrac{1}{2}\lVert p_k^d - p_k^t \rVert_1$（草稿与目标分布的重叠面积），蒸馏训练时目标分布本就在手边、可直接当回归目标，比 0/1 标签信息量大。必须校准的原因：调度器要拿置信度算期望收益，数值本身必须准，而神经网络置信度普遍过度自信；逐位温度校准（Sequential Temperature Scaling）逐位置搜温度系数压 ECE，且温度缩放是保序变换、只拉准数值不打乱排序。（对应第 5.3 节；另见 Q5）

</details>

**9. 能解释为什么"不存在固定的置信度阈值"，以及 hardware-aware 调度器怎么决定送验几个**

<details>
<summary>参考答案</summary>

收益：验证第 $k$ 个 token 的期望产出等于前缀存活概率 $\prod_{i \le k} c_i$；成本：往目标模型 batch 里多塞一个位置的边际代价——不是常数，取决于引擎当前负载。轻载时边际成本近似 0，连 0.12 存活率的草稿都值得捎上、全长送验压延迟；重载时 0.47 概率产出的草稿不如把位置让给 100% 产出的排队请求。同一个 0.47，轻载该验、重载该丢——阈值本身是负载的函数，这是 EAGLE-2 那类静态置信度阈值做不到的。工程实现：离线为每种硬件/引擎压测吞吐曲线（batch 中第 $N$ 个 token 的边际代价），在线对每个请求独立解"期望收益 > 边际成本"的不等式来截断草稿。（对应第 5.4 节；另见 Q3）

</details>

**10. 能报出 DSpark 的关键效果数字与它在 V4 生产中的定位**

<details>
<summary>参考答案</summary>

离线基准（Qwen3-4B/8B/14B 为目标模型，多域宏平均接受长度）：比最强自回归草稿 EAGLE-3 分别高 30.9%/26.7%/30.0%，比最强纯并行草稿 DFlash 高 16.3%/18.4%/18.3%。生产环境（DeepSeek-V4 真实流量，同等总吞吐下单用户生成速度对比 MTP-1 基线）：V4-Flash +60%~85%、V4-Pro +57%~78%；严苛 SLA 档位（Flash 120 TPS / Pro 50 TPS 单用户）下 MTP-1 容量急剧劣化，DSpark 靠调度器压住验证开销守住吞吐——论文称之为"移动了 LLM serving 的帕累托前沿"。DSpark（2026.06 开源）已替代 MTP-1 成为 V4 生产默认投机方案，开源检查点与 DeepSpec 训练框架（含 EAGLE-3/DFlash/DSpark）开箱即用。（对应第 5.5 节）

</details>

## 7. 高频面试题解析

**Q1：DeepSeek-MTP 应用于训练还是推理？具体工作流程？**
两者皆是。训练阶段：$D$ 个顺序 MTP 模块（共享 embedding/输出头）在保持因果链的前提下预测 $t+2$ 起的未来 token，损失以 $\lambda$（0.3→0.1）计入总目标，提升数据效率并迫使表示"预规划"；收益固化在主干里。推理阶段可选：丢弃 MTP 模块（质量不损）或保留作自投机草稿头，V3 报告接受率 80%~90%、约 1.8 倍 TPS（见第 1~3 节）。

**Q2：MTP 与 Medusa 的本质区别？**
Medusa 的多头**并行**独立预测，位置间无依赖，深度越大越盲猜；MTP 模块**顺序**执行，每个深度都拿到上一位置的真实 token embedding，因果链完整，接受率显著更高。代价是草稿深度增加时延迟线性增长，所以 V3/V4 都只用 $D=1$。

**Q3：投机解码为什么在高并发下可能反而降低吞吐？**
验证草稿 token 占用目标模型的 batch 容量。轻载时这些算力本来就闲置，验证近乎免费；重载时每个被拒绝的草稿 token 都挤占了本可服务其他请求的容量。这是 DSpark 引入"置信度 × 系统负载"动态调度验证长度的直接动机（见第 4、5.4 节）。

**Q4：并行草稿为什么接受率衰减快？DSpark 怎么解决？**
并行草稿各位置独立边缘化前驱分布，会拼出"of problem"式的跨模式碰撞，位置越靠后错误累积越快。DSpark 用半自回归结构：DFlash 并行主干出基础 logits，再由轻量 Markov/RNN 头补一个前缀相关转移偏置，把块分布变成自回归分解——草稿延迟仍与块长无关，依赖建模却接近自回归方案（见第 5.2 节）。

**Q5：DSpark 的置信度头为什么用总变差距离做监督，还要做温度校准？**
调度器要计算"多验证一个 token 的期望收益"，需要的是**绝对量级正确**的概率而非仅排序正确。解析接受率 $1 - \frac{1}{2}\|p^d - p^t\|_1$ 恰是 rejection sampling 下该 token 的真实通过概率；神经置信度普遍过自信，故再用逐位温度缩放把累积存活概率的 ECE 压下去——温度缩放保序，不破坏已学到的排序（见第 5.3 节）。
